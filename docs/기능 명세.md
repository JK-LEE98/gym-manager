# 기능 명세 - gym-manager

## 프로젝트 개요

NestJS 기반 헬스장 회원관리 백엔드 서비스.
운영자(ADMIN), 트레이너(TRAINER), 회원(MEMBER) 3가지 역할로 구분되며,
회원관리, 회원권, 출석, PT 관리 등 헬스장 운영 전반을 지원한다.

---

## 역할 정의 (2026-07-27 개정 — 멀티테넌시 반영)

| 역할 | 성격 | gymId | 설명 |
|------|------|-------|------|
| SUPER_ADMIN | 개인 | null | 서비스 운영자. 헬스장 등록, OWNER 계정 발급 |
| OWNER | **공용 운영 계정** | 필수 | 헬스장 운영 전반. 프론트 데스크에서 직원 공유 |
| TRAINER | 개인 | 필수 | PT 일정/계약이 귀속되는 개인 계정 |
| MEMBER | 개인 | 필수 | 일반 회원 |

> 기존 `ADMIN`은 `OWNER`로 대체되었고, 그 위에 서비스 운영자인 `SUPER_ADMIN`이 추가됐다.
> 상세 근거는 ADR-004(멀티테넌시), ADR-005(OWNER 계정 분리) 참고.

### 계정 생성 흐름
```
SUPER_ADMIN → Gym 등록 + OWNER 계정 발급
MEMBER      → 공개 회원가입 API로 스스로 가입
TRAINER     → MEMBER로 가입 후 OWNER가 역할 승격 → TrainerProfile 자동 생성
```

## 기능 명세

### 1. 인증 (Auth)

- **아이디 + 비밀번호** 로그인 (이메일 아님 → ADR-009)
- JWT Access Token / Refresh Token 발급
- Access Token 만료 시 Refresh Token으로 재발급
- 로그아웃 (Refresh Token 무효화)

---

### 2. 회원 관리 (Users) - ADMIN

- 회원 등록 (이름, 아이디, 비밀번호, 전화번호, 역할)
- 비밀번호 초기화 (상위 역할이 하위 역할 대상으로. 임시 비밀번호 발급 → ADR-009)
- 회원 수정 (이름, 전화번호)
- 회원 삭제 (soft delete)
- 회원 단건 조회
- 회원 목록 조회 및 검색
  - 필터: 이름, 역할, 회원권 만료 여부, 활성 상태

---

### 3. 회원권 관리 (Memberships)

#### 회원권 종류 (MembershipType) - ADMIN
- 종류 등록 (이름, **카테고리**, 기간(일), 가격, **홀딩 횟수·1회 최대 일수**)
- 종류 수정 / 비활성화 (삭제하지 않는다. 판매된 회원권이 참조 중)
- 종류 목록 조회 (기본은 판매 중인 것만)

> **카테고리**가 이어붙이기의 기준이다. 같은 카테고리면 이어지고, 다르면 동시 진행된다.
> 헬스 + 락커를 함께 끊는 것이 실제로 흔하다.

#### 회원권 부여 (UserMembership) - ADMIN
- 회원에게 회원권 부여 (종류 선택, 시작일 지정)
- 종료일 자동 계산 (**시작일 + 기간 - 1**)
- 시작일 생략 시 같은 카테고리의 마지막 종료일 다음날부터 (이어붙이기)
- 판매 금액 직접 입력 (정가는 기본값 제안일 뿐)
- 회원권 연장 (**사유 필수**)
- 회원권 취소 (환불·착오 등록. 이력은 남는다)
- 잔여일수 조회 (저장하지 않고 계산. D-day 표기)

> **만료 상태값을 두지 않는다.** `종료일 < 오늘`로 판단한다.
> 같은 사실을 두 곳에 저장하면 반드시 어긋난다. → ADR-010

#### 홀딩(휴회) - MEMBER·ADMIN
- 홀딩 등록 (회원 셀프 / 데스크 대행)
- 홀딩 일정 변경 · 취소
- 현재 홀딩 중인 목록 / 오늘 종료 예정 목록 조회
- 홀딩 일수만큼 회원권 종료일 자동 연장

| | MEMBER | OWNER |
|---|--------|-------|
| 대상 | 본인 회원권만 | 헬스장 전체 |
| 날짜 | 미래만 | 과거 소급 가능 |
| 취소 | 시작 전만 | 진행 중도 가능 |

> **"정지 / 재활성화"를 이것으로 대체했다.** 상태 토글로는
> "언제부터 언제까지" 쉬었는지가 남지 않아 종료일을 정확히 밀 수 없다. → ADR-011

#### 양도 - ADMIN
- 잔여 기간을 다른 회원에게 이전
- 양도 수수료 입력 (가족 무료 / 지인 5만원 등. 0이면 결제 기록 없음)
- 양도 이력 조회 (준 것 + 받은 것)

> 원본을 삭제하지 않고 `TRANSFERRED`로 종료한다. 양도인 이력에 남는다.
> 진행 중인 홀딩은 **취소가 아니라 조기 종료**해 지나간 일수를 보존한다.
> 양도로 받은 회원권은 홀딩할 수 없다. → ADR-012

#### 결제 (Payment) - 추후 PG 연동 대비 설계
- 회원권 부여 시 Payment 레코드 자동 생성
- 현재는 method: MANUAL로 처리
- status: PENDING | COMPLETED | FAILED | REFUNDED
- pgTransactionId 필드 확보 (PG 연동 시 사용)

> 양도 수수료는 별도 Payment로 기록한다. **원본 결제를 복제하지 않는다.**
> 복제하면 같은 돈이 매출에 두 번 잡힌다.

### 4. 출석 관리 (Attendance)

- QR 토큰 발급 (MEMBER 본인 요청, 유효시간 30초, `type` 필드로 용도 분리)
- QR 스캔 → 출석 체크 (토큰 검증 후 출석 기록 저장)
- 수동 출석 처리 (ADMIN) — 배터리 방전 등 QR을 못 쓰는 상황
- 출석 이력 조회 (회원별, 기간별)
- **헬스장별 출입 정책 설정** — 하루 입장 횟수, 재출입 유예 시간

#### 입장 차단 조건

| 상황 | 안내 문구 |
|------|----------|
| 휴회 중 | 현재 휴회중인 회원입니다. 휴회를 철회한 후 이용해주세요 |
| 회원권 없음 | 이용 가능한 회원권이 없습니다. 데스크에 문의해주세요 |
| 횟수 초과 | 오늘 입장 가능 횟수를 초과했습니다. 문제가 있으면 헬스장에 문의해주세요 |

> **문구가 스펙이다.** QR을 찍어야 문이 열리는 헬스장에서는
> 이 문장이 회원이 보는 유일한 화면이다.

#### 재출입

QR의 역할이 헬스장마다 다르다.

```
형식적 스캔형   데스크가 있고 QR은 기록용        reentryGraceMinutes = 0
출입 통제형     QR을 찍어야 문이 열린다 (24시)   reentryGraceMinutes = 30
```

유예 시간 안의 재스캔은 **같은 입장**으로 본다. 흡연하러 나갔다 온 회원이
"오늘 횟수를 다 썼다"고 막히면 안 되기 때문이다.
기록은 남기되(`isReentry=true`) 입장 횟수에는 세지 않는다.

> **퇴실은 기록하지 않는다.** 회원 대부분이 그냥 나가서 재실 인원이 항상 틀린다.
> 신뢰할 수 없는 데이터는 없느니만 못하다. → ADR-013

#### 출입구 화면

```
이*규 회원님 반갑습니다
회원권이 87일 후에 만료됩니다
```

문 앞 화면은 지나가는 사람에게도 보이므로 **서버가 이름을 마스킹해서 보낸다.**

- 트레이너 목록 조회
- 담당 회원 목록 조회 (PT 계약 기준)

### 6. PT 관리 (PT)

#### PT 계약 (PTContract) - ADMIN
- 계약 등록 (회원 + 트레이너 + 총 횟수 + 금액 + 기간)
- **Payment 동시 생성** (한 트랜잭션). 회원권 부여와 같은 패턴
- 계약 조회 (회원별, 트레이너별), 잔여 횟수 조회
- 계약 취소

> **트레이너는 계약 시 배정되고 1:1로 고정된다.** 변경은 이례적이라 향후 과제.

#### PT 예약 (PTSchedule) - TRAINER
- 예약 등록 (계약 기준, 시작 시각 + 소요 시간)
- **반복 예약 일괄 등록** — "매주 화·목 19시, 9월 한 달"
- 일정 이동 / 취소
- 완료 확정 → 잔여 횟수 차감
- 노쇼 처리 → **차감 여부를 트레이너가 선택**
- 미확인 목록 조회 (수업 시간이 지났는데 확인 안 된 건)
- status: `SCHEDULED` | `COMPLETED` | `NO_SHOW` | `CANCELLED`

> **빈 슬롯 개념이 없다. 행 하나 = 예약 하나.**
> 예약은 카톡·전화로 정해지고 트레이너가 입력한다.
> 회원이 화면에서 빈 시간을 고르는 구조가 아니다.

> **차감은 확인 버튼으로 한다. 자정 일괄 처리는 하지 않는다.**
> 출석과 달리 수업이 실제로 진행됐다는 증거가 없어
> 일괄 처리하면 하지 않은 수업도 차감된다.

> **트레이너 시간 겹침은 PostgreSQL `EXCLUDE` 제약이 막는다.**
> 애플리케이션에서 조회해 판단하지 않는다. → ADR-014

#### 회원이 할 수 있는 것
- 본인 일정 조회, 잔여 횟수 조회
- 본인 예약 취소

> **회원이 직접 예약하지 않는다.** 선착순은 경쟁 범위가 열려 있어야 성립하는데,
> 담당 트레이너가 정해져 있으면 놓쳐도 대안이 없어
> 특정 시간대만 가능한 회원이 계속 밀린다.

### 7. 만료 관리 (회원 필터 조회) - ADMIN

**재등록을 놓치는 것이 곧 매출 손실**이라 만료 전후로 연락을 돌린다.
우리는 **"누구에게 보낼지" 목록까지** 만들고, 실제 발송은 외부 서비스가 한다.

- 만료 임박 회원 조회 — **정확히 N일 남은 회원** (카테고리별)
- 만료 후 회원 조회 — N일 이내에 만료된 회원 (복귀 홍보용)
- 신규 회원 조회 — 운동을 시작한 지 N일 된 회원 (쿠폰·만족도 조사)
- 출입구 화면에 카테고리별 잔여일 표시 (락커 만료를 회원이 직접 확인)

> **"정확히 N일"이 핵심이다.** "7일 이내"로 만들면 D-7·D-5·D-3이 섞여
> 매일 돌릴 때 한 사람에게 문자가 여러 번 간다. 중복 발송 방지가 이 기능의 존재 이유다.

> ~~**알림 (SSE)**~~ — **제거됨.** MEMBER용 클라이언트가 없어 수신자가 연결을 유지할 수 없고,
> 앱이 생겨도 백그라운드에서는 SSE가 동작하지 않아 FCM으로 대체해야 한다.
> 필요한 것은 실시간 통지가 아니라 **데스크가 대상을 뽑아낼 수 있는 조회**였다. → ADR-015

### 8. 통계 (Stats) - ADMIN

- 월별 매출 — **결제일 기준**, 목적별(회원권 / PT / 양도 수수료)
- 월별 신규 회원 수
- 트레이너별 PT 완료·노쇼 횟수

> **매출은 판 달에 전액 인식한다.** 8월에 55만원짜리 12개월권을 팔면 8월 매출이 55만원이다.
> 회계상으로는 월 4.5만원씩 나누는 이연 인식이 맞지만,
> 데스크가 보고 싶은 것은 **"이번 달에 얼마 들어왔나"** 다.

#### 회원별 이용 일수 (통계 아님 — 회원 상세에 표시)

```
이용 일수   4일 / 10일
```

**회원권별로 나누지 않는다. 회원 한 명당 하나다.**

출석 기록에는 어느 회원권 때문에 왔는지가 없다. QR을 찍으면 "왔다"는 행 하나가 남을 뿐이다.
헬스와 락커를 함께 끊은 회원의 출석 4건을 둘로 쪼갤 근거가 없어,
회원권별로 붙이면 **락커에도 `4/10`이 찍힌다.** 락커는 회원이 오든 안 오든 계속 점유 중인데도.

카테고리로 거를 수도 없다. `category`는 헬스장이 자유롭게 입력하는 `varchar(50)`이라
`'헬스'`를 코드에 박으면 "피트니스"·"GYM"으로 쓰는 헬스장에서 통째로 빠진다.

> 회원권별로 필요한 것은 **남은 일수**(`daysUntilExpiry`)이고 그것은 이미 있다.
> 출석은 회원 단위 사실이므로 회원 단위로 둔다.

```
기준 기간     = 현재 이용 중인 회원권들의 합집합 (가장 이른 시작일 ~ min(오늘, 가장 늦은 종료일))
이용 가능 일수 = 기준 기간의 일수 − 그 기간의 ACTIVE 홀딩 일수
이용 일수      = 그 기간의 출석일 수 (같은 날 여러 번 찍어도 1일)
```

홀딩 중에는 나올 수 없으므로 분모에서 뺀다. 만료된 회원권은 자동으로 전체 기간이 된다.

**퍼센트로 만들지 않는다.** 휴무일을 반영하지 않으므로 100%가 애초에 불가능한데,
퍼센트로 보여주면 "100%가 정상"이라는 착각이 생긴다.
두 숫자를 그대로 주면 데스크가 "10일 중 1일? 연락해야겠다"로 바로 판단한다.

> ~~**월별 출석률**~~ — **제거됨.** 전체 집계보다 **개인의 이용 일수**가 실제로 쓰인다.
> 30일권 중 3일만 나온 회원은 재등록하지 않는다. 이탈 신호를 잡는 것이 목적이다.

> **헬스장 휴무일은 반영하지 않는다.** 휴무 설정 자체가 별개 기능이다. → 향후 과제

## NestJS 선택 이유

헬스장 회원관리 서비스 특성상 QR 입장, 출석 기록, 회원권 조회 같은 I/O 중심의 처리가 많다.
Node.js 기반의 NestJS는 이벤트 루프 구조로 이런 I/O 바운드 작업에서 Spring Boot 대비 경량으로 처리할 수 있고,
초기 B2B SaaS 단계에서 서버 비용 절감도 고려했다.
또한 NestJS는 Spring과 동일하게 모듈/서비스/컨트롤러 계층 구조와 DI를 사용해
