## 001. Git push 거부 (fetch first)

**증상**
```
! [rejected]  main -> main (fetch first)
error: failed to push some refs to 'https://github.com/JK-LEE98/gym-manager.git'
```

**원인**
GitHub에서 레포 생성 시 README/.gitignore가 자동 생성되어, 로컬에 없는 커밋이 원격에 존재.
로컬 NestJS 프로젝트와 원격 저장소의 히스토리가 서로 무관한 상태였음.

**해결**
```bash
git pull origin main --allow-unrelated-histories
# .gitignore, README.md 충돌 수동 해결
git add .
git commit -m "resolve merge conflict"
git push origin main
```

**배운 점**
GitHub 레포 생성 시 "Initialize with README" 옵션을 끄면 이 문제를 애초에 피할 수 있음.

## 002. TypeORM DB 연결 실패 — `role "gym" does not exist`

**증상**
```
ERROR [TypeOrmModule] Unable to connect to the database. Retrying (1)...
error: role "gym" does not exist
```
Docker 컨테이너는 정상 구동 중(`docker ps` 확인), 컨테이너 로그도 `database system is ready to accept connections` 출력.
`docker compose down -v`로 볼륨 삭제 후 재기동해도 동일 증상 반복.

**원인 파악 과정**
1. 컨테이너 로그 확인 → PostgreSQL 정상, `gym` 유저/DB 생성됨
2. `docker exec ... psql -U postgres` 시도 → `role "postgres" does not exist` 에러
   → **컨테이너 안이 아니라 다른 PostgreSQL에 붙고 있다는 신호**
3. 포트 점유 확인
```bash
lsof -i :5432
```
```
postgres   1673   jk  ...  TCP localhost:postgresql (LISTEN)   ← 로컬 설치본
com.docke 70234   jk  ...  TCP *:postgresql (LISTEN)           ← Docker
```

**진짜 원인**
Mac에 **로컬 PostgreSQL이 이미 설치되어 5432 포트를 선점**하고 있었음.
NestJS가 `localhost:5432`로 접속하면 Docker 컨테이너가 아닌 로컬 PostgreSQL로 연결되어,
Docker에서 만든 `gym` 계정을 찾지 못한 것.

**해결 (1차) — 포트 우회**
Docker의 호스트 포트를 5433으로 변경하여 충돌 회피.

```yaml
# docker-compose.yml
ports:
  - '5433:5432'   # host:container
```
```env
DB_PORT=5433
```

**해결 (2차, 최종) — 로컬 PostgreSQL 중지**
포트 우회는 임시방편이라 판단. 로컬 PostgreSQL을 사용하지 않으므로 서비스를 내리고 5432를 회수.

```bash
brew services list | grep postgres
brew services stop postgresql@16
lsof -i :5432          # com.docke 만 남는지 확인
```
`docker-compose.yml`과 `.env`를 5432로 원복.

> `brew services stop`은 데이터를 삭제하지 않는다. 필요 시 `start`로 복구 가능.

**배운 점**
- 컨테이너가 "떠 있다"는 것과 "내 앱이 그 컨테이너에 붙는다"는 별개의 문제.
- `docker ps`만 보고 판단하면 안 되고, `lsof -i :<port>`로 실제 포트 점유 주체를 확인해야 함.
- 컨테이너 내부 접속 시 예상과 다른 유저 에러가 나면 → 애초에 다른 서버에 붙고 있는지 의심할 것.
- 로컬에 동일 DB가 설치된 개발 환경에서는 Docker 포트를 다르게 매핑하는 게 안전.

## 003. TypeORM `DataTypeNotSupportedError` — nullable 컬럼 타입 추론 실패

**증상**
Entity 작성 후 서버 기동 시 DB 연결 단계에서 실패.

```
DataTypeNotSupportedError: Data type "Object" in "Gym.address"
is not supported by "postgres" database.
```

**원인**

TypeScript는 `emitDecoratorMetadata` 옵션으로 각 프로퍼티의 타입 정보를 `design:type` 메타데이터에 심는다.
TypeORM은 `@Column`에 `type`이 없으면 이 메타데이터를 읽어 컬럼 타입을 추론한다.

그런데 **유니온 타입(`string | null`)은 메타데이터에 `Object`로 기록된다.**
런타임 리플렉션으로는 유니온을 표현할 방법이 없기 때문이다.

```typescript
// ❌ design:type = Object → 추론 실패
@Column({ length: 255, nullable: true })
address: string | null;
```

nullable 컬럼을 `T | null`로 선언하면 전부 이 문제에 걸린다.

**해결**

nullable 컬럼에는 `type`을 명시한다.

```typescript
// ✅
@Column({ type: 'varchar', length: 255, nullable: true })
address: string | null;
```

수정 대상: `Gym.address`, `Gym.phone`, `User.phone`, `TrainerProfile.specialty`, `RefreshToken.deviceInfo`

> 이미 `type`을 명시했던 `User.gymId`(uuid), `TrainerProfile.bio`(text),
> `RefreshToken.revokedAt`(timestamp)는 영향 없었다.

**배운 점**

- Java/JPA에는 유니온 타입이 없어 발생하지 않는 문제다. `String`은 항상 `String`이다.
- TypeScript의 타입은 컴파일 후 대부분 소거되고, 데코레이터 메타데이터로 남는 정보는 제한적이다.
  ORM처럼 런타임 리플렉션에 의존하는 라이브러리를 쓸 때는 이 한계를 인지해야 한다.
- **규칙**: nullable 컬럼에는 `type`을 항상 명시한다.

## 004. Refresh Token 중복 발급 — 같은 초에 갱신하면 500

**증상**

E2E 테스트 작성 후 `POST /auth/refresh`에서 500이 발생했다.

```
QueryFailedError: duplicate key value violates unique constraint "UQ_..."
  at TokenService.issueTokenPair (token.service.ts:53)
  at AuthService.refresh (auth.service.ts:119)
```

**손으로 curl을 칠 때는 한 번도 재현되지 않았다.**

**원인**

Refresh Token의 payload는 `{ sub: userId }`뿐이고, JWT 표준 클레임 `iat`(발급 시각)는 **초 단위**다.

```
로그인   → sign({ sub: 'abc' })  iat=1785803124  → "eyJ...A"
즉시 갱신 → sign({ sub: 'abc' })  iat=1785803124  → "eyJ...A"   ← 완전히 동일
```

같은 시크릿·같은 payload·같은 `iat`이면 **서명 결과가 글자 하나까지 같다.**
따라서 SHA-256 해시도 같아지고, `refresh_tokens.token_hash`의 unique 제약을 위반한다.

수동 테스트에서는 명령 사이에 최소 1초가 지나 `iat`이 달라졌기 때문에 드러나지 않았다.
E2E는 밀리초 단위로 연속 호출하므로 즉시 재현됐다.

> **운영에서도 발생 가능한 버그다.** 사용자가 로그인 직후 곧바로 갱신하면 500이 떨어진다.

**해결**

JWT 표준 클레임 `jti`(JWT ID)에 UUID를 넣어 매 발급마다 다른 토큰을 보장한다.

```typescript
const refreshToken = await this.jwt.signAsync(
  { sub: user.id, jti: randomUUID() },
  this.refreshSignOptions(),
);
```

부수 효과로 보안도 소폭 개선된다. 발급 시각을 알아도 토큰을 예측할 수 없다.

**배운 점**

- **수동 테스트는 느려서 못 잡는 버그가 있다.** 사람이 명령을 치는 속도가
  자연스러운 지연을 만들어 타이밍 의존 버그를 가려버린다.
- JWT의 `iat`는 초 단위다. payload가 고정적이면 같은 초에 발급된 토큰은 동일하다.
  토큰의 유일성이 필요하면 `jti`를 넣어야 한다.
- E2E 테스트를 도입한 첫날 회수한 값어치다.

## 006. PT 잔여 횟수 lost update — 동시에 누르면 두 번 차감되지 않는다

> **이건 발견한 버그가 아니라 일부러 만들어 본 버그다.**
> 조건부 UPDATE로 바로 짜면 "왜 이렇게 쓰는지"가 남지 않아
> 순진한 구현 → 재현 → 수정 순서로 진행했다. (#30)

**증상**

잔여 1회인 계약에서 두 수업을 동시에 완료 처리하면 **둘 다 성공한다.**

```
Expected: [200, 409]
Received: [200, 200]
```

수업 2회가 소진됐는데 차감은 1회만 됐다.

**원인 — lost update**

읽고(SELECT) → 판단하고 → 쓰는(UPDATE) 사이가 비어 있다.

```typescript
const contract = await this.contractRepo.findOne(...);        // ① 읽는다
if (contract.remainingSessions <= 0) throw ...;               // ② 판단한다
await this.contractRepo.update(id, {                          // ③ 쓴다
  remainingSessions: contract.remainingSessions - 1,          //   ← 읽은 값으로 계산
});
```

```
A: ① 읽음 remaining=1
B: ① 읽음 remaining=1     ← A가 아직 안 썼다
A: ② 1 > 0 통과
B: ② 1 > 0 통과           ← B도 통과한다
A: ③ 1 - 1 = 0 저장
B: ③ 1 - 1 = 0 저장       ← A의 갱신을 덮어쓴다
```

**두 가지가 동시에 잘못됐다.**

| | 문제 |
|---|------|
| 조건이 애플리케이션에 | 판단과 쓰기 사이에 다른 트랜잭션이 끼어든다 |
| 계산이 애플리케이션에 | 읽은 시점의 값으로 빼서 남의 갱신을 덮어쓴다 |

**재현 방법**

동시성 버그는 재현이 잘 안 된다. `Promise.all`로 두 요청을 날려도
운이 나쁘면 순차 처리되어 통과해버린다.

```typescript
// 검증 코드에 일시적으로 넣어 틈을 눈에 보이게 늘린다
await sleep(50);
```

실제로는 이 틈이 마이크로초라 **100번 중 한 번 터진다.**
그래서 더 위험하다 — 재현이 안 되니 원인을 못 찾는다.

**해결 — 조건부 UPDATE**

조건과 계산을 **둘 다** SQL 안으로 옮긴다.

```typescript
const result = await manager.update(
  PTContract,
  { id: contractId, remainingSessions: MoreThan(0) },        // 조건
  { remainingSessions: () => '"remaining_sessions" - 1' },   // 계산
);

if (result.affected === 0) {
  throw new BusinessException(ErrorCode.NO_REMAINING_SESSIONS);
}
```

**락도 재시도도 필요 없다.**

```
UPDATE는 실행되는 순간 그 행에 배타 락을 잡고,
락을 잡은 뒤에 WHERE 조건을 다시 평가한다.

A: UPDATE … WHERE remaining > 0  →  락 획득, 조건 참  → 1 row
B: UPDATE … WHERE remaining > 0  →  A 커밋 대기 → 재평가 → 거짓 → 0 row
```

`SELECT ... FOR UPDATE`가 하는 일을 **`UPDATE` 한 문장이 이미 하고 있다.**

**중복 클릭도 같은 방식으로 막는다**

```typescript
await manager.update(
  PTSchedule,
  { id, status: PTScheduleStatus.SCHEDULED },   // 조건
  { status: PTScheduleStatus.COMPLETED, ... },
);
// affected === 0 → 이미 처리됨
```

**배운 점**

- **`affected`를 확인하지 않는 UPDATE는 조건을 건 의미가 없다.** 0 row도 성공으로 보인다
- `remaining - 1`을 애플리케이션이 계산하면 `WHERE`를 걸어도 소용없다. **둘 다 옮겨야 한다**
- 이전 프로젝트(JabaClass)의 재고 차감도 문서에는 "비관적 락"으로 적혀 있었지만
  **실제 코드는 조건부 UPDATE**였다 → `UPDATE … WHERE capacity >= :quantity`
- 동시성 버그는 **일부러 재현시켜 본 뒤에 고쳐야** 왜 그렇게 쓰는지가 남는다

## 005. npm 설치 시 경고 메시지

**증상**
```
25 high severity vulnerabilities
npm warn allow-scripts 4 packages have install scripts not yet covered by allowScripts
```

**판단**
- `high severity vulnerabilities`: NestJS 프레임워크 자체 의존성 트리에서 발생. `npm audit fix --force` 실행 시 NestJS 버전이 깨질 수 있으므로 실행하지 않음.
- `allow-scripts`: `bcrypt`, `fsevents` 등 네이티브 모듈의 빌드 스크립트. 신뢰 가능한 패키지이므로 무시.

**조치**
없음. 실제 배포 전 `npm audit` 재점검 예정.
