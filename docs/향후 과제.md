## Phase 1 완료 후

### 환경변수 스키마 검증

`.env` 값의 **형식**을 앱 시작 시점에 검증한다.
현재 `getOrThrow`는 "값이 존재하는지"만 보장하고 형식은 보지 않는다.

```
JWT_ACCESS_EXPIRES_IN=바나나  →  컴파일·기동 통과, 토큰 발급 시점에 실패
```

`ConfigModule`의 `validationSchema`(Joi)를 사용한다.
Spring의 `@ConfigurationProperties` + `@Validated`에 해당한다.

함께 검증할 것: `DB_PORT`가 숫자인지, JWT 시크릿이 비어있지 않은지, `NODE_ENV`가 허용값인지.

> 출처: 학습 노트 2-7 (템플릿 리터럴 타입 / 단언의 한계)

### 테스트 / CI-CD / 배포  ← **현재 진행**

```
lint (ESLint) → build (tsc) → test (Jest) → docker build → PR 머지 가능
```

PR마다 자동 검증되는 파이프라인을 구성한다.
AI 코드 리뷰 도구(CodeRabbit 등) 도입은 이 위에 얹는 보조 수단으로 판단한다.

> Gemini Code Assist 컨슈머 버전은 2026-07-17 종료되어 사용 불가.

### TypeORM 마이그레이션 도입

**트리거: 운영 배포 결정 시. 필수.**

현재 개발 환경은 `synchronize: true`로 Entity에서 스키마를 자동 생성한다.
운영에서는 컬럼 삭제·타입 변경 시 데이터가 소실될 수 있어 절대 켜지 않는다.

```bash
npm run typeorm migration:generate
npm run typeorm migration:run
```

Spring의 Flyway/Liquibase에 해당한다. → [[아키텍처#5. 데이터베이스]]

### 애플리케이션 컨테이너화

**트리거: 지금.** 현재 DB만 Docker이고 앱은 로컬 Node로 실행되어
개발 환경과 운영 환경의 런타임이 다르다.

`Dockerfile` + `.nvmrc`를 추가하고 CI에서 `docker build`를 검증한다.
로컬 개발은 watch 모드 유지(속도), 이미지 빌드 가능 여부만 CI가 보장. → [[아키텍처#4. 환경 구성]]

| 항목 | 트리거 | 출처 |
|------|--------|------|
| **출석 테이블 파티셔닝 + 보관 정책** | **`attendance` 행이 1천만을 넘거나 이력 조회가 느려지면.** 헬스장 100곳 기준 연 730만 행(인덱스 포함 약 1.5GB)이라 당장은 삭제할 필요가 없다. 필요해지면 **월 단위 declarative partitioning** 후 오래된 파티션을 `DROP`한다. 수백만 행 `DELETE`는 락이 걸리고 테이블이 부풀지만 파티션 드롭은 파일 삭제라 즉시 끝난다. **보관 기간은 개인정보처리방침 작성 시 법적 확인 필요** — 개인정보보호법은 보유기간 고지와 목적 달성 후 파기를 요구하나 출입기록의 구체적 연한은 정하지 않는다 | ADR-013 |

| 재실 현황 / 혼잡도 | 퇴실 기록 도입 이후. "지금 몇 명 있나"는 회원 앱의 핵심 기능이 될 수 있다 | ADR-013 |
| 출석 기반 이탈 예측 | 데이터가 6개월 이상 쌓인 뒤. 출석 빈도가 떨어지는 회원을 미리 잡아 재등록을 유도 | 도메인 지식 8장 |

### 통계

| 항목 | 트리거 | 출처 |
|------|--------|------|
| **헬스장 휴무일 설정** | **이용 일수를 퍼센트로 보여달라는 요구가 생기면.** 정기휴무·명절·임시휴관을 `Gym`에 설정해야 이용 가능 일수에서 뺄 수 있다. 지금은 반영하지 않으므로 100%가 애초에 불가능하고, 그래서 **퍼센트 대신 `4일 / 10일` 두 숫자를 그대로 보여준다** | 기능 명세 8장 |
| 매출 이연 인식 | 세무·회계 보고가 필요해지면. 현재는 결제일에 전액 인식한다. 12개월권 55만원을 월 4.5만원씩 나누는 것이 회계상 맞지만 데스크가 보는 숫자는 아니다 | 기능 명세 8장 |
| 회원 목록에 이용 일수 표시 | 목록에서도 이탈 위험을 훑고 싶어지면. **N+1이 되므로 집계 쿼리를 따로 만들어야 한다.** 현재는 회원 상세에만 있다 | ADR-015 |
| **`Payment.paidAt` 분리** | **월말·월초 소급 입력이 실제로 문제가 되면.** 현재 매출은 `createdAt`(입력 시각)으로 집계한다. 이는 *결제일*이 아니라 *입력일*이라, 8/31에 받은 돈을 9/1에 등록하면 9월 매출이 된다. 헬스장은 현장에서 즉시 등록하므로 대부분 일치하지만 월 경계에서 어긋난다. **지금 `paidAt`을 받으면 데스크가 매번 날짜를 입력해야 해 오히려 오류가 는다** | API 명세 10장 |
| 출석 카테고리 구분 | **PT·GX처럼 종목별 출석을 따로 세야 할 때.** 현재 `attendances`에는 어느 회원권 때문에 왔는지가 없어 이용 일수를 회원 단위로만 낼 수 있다. 필요해지면 QR 스캔 시 종목을 선택하거나, 종목별 단말을 두어야 한다 | API 명세 3장 |

#### PR 필수화를 미룬 이유

`dev`에 "Require a pull request before merging"을 켜면 문서 한 줄 수정에도 브랜치와 PR이 필요하다.
현재는 문서를 `dev`에 직접 커밋하는 규칙이므로, 켜면 워크플로우 전체를 바꿔야 한다.

또한 켜는 순간 **CI 경로 필터의 함정**을 함께 다뤄야 한다.

```yaml
on:
  pull_request:
    paths-ignore: ['**.md']    # md만 바뀌면 워크플로우가 실행되지 않음
```

실행되지 않은 체크는 통과도 실패도 아니어서 **필수 체크로 걸려 있으면 PR이 영원히 머지 불가** 상태가 된다.
우회하려면 잡을 셋으로 나눠야 한다.

```
changes (경로 감지) → verify / docker (조건부 실행) → ci-success (결과 취합)
                                                        └ 이것만 필수 체크로 지정
```

`dorny/paths-filter` 같은 서드파티 액션도 필요하다.

**혼자 개발하는 동안에는 얻는 것보다 복잡도가 크다.**
브랜치 확인은 CLAUDE.md 규칙과 Claude의 사전 확인으로 대응한다.
상태 체크만으로도 코드는 반드시 PR을 거치므로 품질은 지켜진다.

## 명시적 제외 (하지 않기로 결정)

되돌릴 이유가 생기기 전까지는 검토하지 않는다.

| 항목 | 제외 이유 |
|------|----------|
| 소셜 로그인 (OAuth2 / 카카오) | 앱이 없어 간편 로그인 이점이 반감됨. JWT 자체 인증 + Rotation + Reuse Detection에 집중하는 편이 깊이 있음. OWNER 공용 계정과도 맞지 않음 |
| Redis (Refresh Token 저장) | 로그인 빈도가 낮아 이점이 없고 컨테이너 비용만 발생. DB + CircuitBreaker 구조는 명백한 오버엔지니어링 → ADR-006 |
| MSA | 초기 B2B SaaS 단계에서 과도한 복잡성 |
| `@CurrentGym()` 데코레이터 | `@CurrentUser('gymId')`로 동일한 목적 달성. ADR-004 문구는 참고용 |
| **알림 기능 전체 (SSE·`Notification` 테이블)** | 수신자에게 클라이언트가 없고, 앱이 생겨도 SSE는 백그라운드에서 동작하지 않는다. 필요했던 것은 실시간 통지가 아니라 **대상을 뽑는 조회**였다 → ADR-015 |
