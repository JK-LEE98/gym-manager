## 1. 애플리케이션 구조

### 모놀리식

초기 B2B SaaS 단계에서 MSA는 과도한 복잡성이다.
트래픽이 늘어 특정 모듈이 병목이 되면 그때 분리한다.

다만 **분리가 가능하도록 도메인 경계를 지켜서** 모듈을 나눈다.
모듈 간 참조는 Service를 통하고, 다른 모듈의 Repository를 직접 주입하지 않는다.

### 레이어

```
Controller  →  Service  →  Repository(TypeORM)  →  PostgreSQL
    ↑             ↑
   얇게        비즈니스 로직 전부
```

- Controller는 요청/응답 변환만. 로직을 두지 않는다
- Service가 트랜잭션 경계를 잡는다
- Entity를 그대로 반환하지 않고 Response DTO로 변환한다

### 모듈 (Phase 4-2 완료 기준)

## 2. 요청 처리 흐름

```
HTTP 요청
   │
   ├─ ThrottlerGuard      유량 제한 (인증 무관하게 먼저)
   ├─ JwtAuthGuard        토큰 검증 → request.user = { sub, role, gymId }
   │                      @Public 라우트는 통과
   ├─ RolesGuard          @Roles 대조
   │
   ├─ TransformInterceptor (전)
   ├─ ValidationPipe      DTO 검증 + whitelist로 미정의 필드 제거
   │
   ├─ Controller → Service → Repository → DB
   │
   ├─ TransformInterceptor (후)  → { success, data, message }
   │
   └─ AllExceptionsFilter (예외 시) → { success, data, message, errorCode }
```

**Guard가 Pipe보다 먼저인 것**이 중요하다. 인증되지 않은 요청은 DTO 검증까지 갈 필요가 없다.
**전역 Guard 등록 순서가 곧 실행 순서**이므로 `app.module.ts`의 배열 순서를 바꾸면 안 된다.

## 3. 멀티테넌시

행 단위 분리. 주요 테이블에 `gymId` FK. → ADR-004

### 격리 보장 방식

**애플리케이션 레이어가 책임진다.** DB가 강제하지 않으므로 규칙을 코드 구조로 만든다.

```
1. JwtStrategy가 토큰에서 gymId를 추출해 request.user에 담는다
2. @CurrentUser('gymId')로 Controller가 꺼낸다
3. Service 메서드가 gymId를 필수 인자로 받는다  ← 컴파일 타임에 누락이 잡힘
4. Repository 조회의 WHERE에 gymId를 넣는다     ← 조건 누락 시 데이터가 새는 대신 조회가 안 됨
```

**클라이언트가 보낸 `gymId`는 절대 신뢰하지 않는다.** DTO에 `gymId` 필드를 두지 않으면
`whitelist: true`가 자동으로 제거하므로, 애초에 받을 수 없는 구조가 된다.

### 역할별 접근 범위

| 역할 | gymId | 접근 |
|------|-------|------|
| SUPER_ADMIN | **null** | 전체. `gymId === null`이 곧 "전체 접근" 조건 |
| OWNER | 필수 | 본인 헬스장만 |
| TRAINER | 필수 | 본인 헬스장 + 본인 관련 리소스 |
| MEMBER | 필수 | 본인 리소스만 |

## 4. 환경 구성

> **핵심 원칙**: 개발·CI·운영에서 **런타임과 DB 메이저 버전이 달라지면 안 된다.**
> "내 컴퓨터에선 됐는데"의 대부분이 여기서 나온다.

| 애플리케이션 코드·의존성 | ✅ | |

| 데이터 내용 | | ✅ |

| 인스턴스 수·사양 | | ✅ |
| 로그 레벨 | | ✅ |

### 현재 (Phase 1 완료)

```
┌─ macOS ─────────────────────────────┐
│  npm run start:dev  (Node 20, watch) │  ← ⚠️ 컨테이너 밖
│         │                            │
│         ↓ localhost:5432             │
│  ┌─ Docker ──────────────┐           │
│  │  postgres:16          │           │
│  └───────────────────────┘           │
└──────────────────────────────────────┘
```

**알려진 갭**: 애플리케이션이 컨테이너화되어 있지 않다.
로컬은 macOS ARM의 Node, 운영은 리눅스 컨테이너가 될 것이므로 런타임 환경이 다르다.
→ `Dockerfile` + `.nvmrc` 추가로 해소한다. (다음 작업)

### 목표 구성

```
[로컬 개발]                 [CI]                      [운영]
npm run start:dev          GitHub Actions            컨테이너 실행
  Node 20 (.nvmrc)           Node 20                   Dockerfile 이미지
  watch 모드                 lint·build·test
       │                     docker build 검증              │
       ↓                          │                         ↓
  postgres:16 (Docker)      postgres:16 (service)     PostgreSQL (관리형)
```

**로컬 개발은 컨테이너 밖에 둔다.** watch 모드의 즉시 반영이 개발 속도에 훨씬 중요하고,
`.nvmrc`로 Node 버전을 고정하면 실질적인 차이가 사라지기 때문이다.

**대신 CI에서 매번 `docker build`를 검증**해 운영 이미지가 항상 빌드 가능한 상태를 유지한다.
운영에서만 깨지는 상황을 PR 단계에서 잡는다.

### CI 파이프라인

```
PR 생성 (→ dev / main)
   │
   ├─ verify   npm ci → lint:ci → build → test
   └─ docker   운영 이미지 빌드 검증
        (두 잡 병렬 실행)
```

**브랜치 보호**: `dev`·`main`에 상태 체크 통과를 필수로 지정.
"PR 필수"는 켜지 않는다 — 문서를 `dev`에 직접 커밋하는 규칙과 충돌하고,
CI 경로 필터의 함정을 함께 다뤄야 한다. → [[향후 과제]]

**원칙**: CI가 실행하는 명령은 전부 로컬에서 그대로 칠 수 있어야 한다.
워크플로우 안에 로직을 넣지 않는다. CI에서만 통하는 동작이 있으면 실패 원인을 재현할 수 없다.

**`lint`와 `lint:ci` 분리**: 전자는 `--fix`가 붙어 있어 CI에서 쓰면
에러를 고쳐놓고 통과시킨다. 검증이 아니라 수정이 되므로 CI용은 `--fix` 없이 `--max-warnings 0`.

## 5. 데이터베이스

- PostgreSQL 16 → ADR-001
- 스키마 관리: **개발·테스트는 `synchronize: true`, 운영은 마이그레이션**

```typescript
synchronize: ['development', 'test'].includes(config.get('NODE_ENV') ?? '')
```

> ⚠️ **운영 전 필수 작업**: TypeORM 마이그레이션 도입.
> `synchronize`는 컬럼 삭제·타입 변경 시 데이터 손실 위험이 있어 운영에서 절대 켜지 않는다.
> → [[향후 과제]]

### 스키마는 마이그레이션이 만든다 (ADR-016)

`synchronize`는 **모든 환경에서 꺼져 있다.** 개발·테스트도 예외가 아니다.
켜두면 Entity를 고칠 때 자동으로 맞춰줘 **마이그레이션을 만들지 않아도 테스트가 통과하고**,
그러면 운영을 지키려고 만든 장치가 한 번도 검증되지 않는다.

```
앱 기동 → migrationsRun → 미적용 마이그레이션 실행 → 스키마 완성
```

| 명령 | 용도 |
|------|------|
| `npm run migration:generate` | Entity와 현재 DB의 차이로 새 파일 생성 |
| `npm run migration:run` | 미적용 마이그레이션 실행 |
| `npm run migration:revert` | 마지막 하나 되돌리기 |
| `npm run migration:show` | 적용 현황 |
| `npm run migration:check` | 차이가 남아 있으면 종료 코드 1 (**CI가 사용**) |

> `generate`는 **빈 DB에 붙어서** 돌려야 한다. 이미 테이블이 있는 DB에 붙으면
> 차이가 없어 빈 파일이 나온다. → ADR-016

### 초기화 순서 — 확장이 스키마보다 먼저다

```
① CREATE EXTENSION uuid-ossp, btree_gist   ← 마이그레이션 첫 두 줄
② CREATE TABLE ...                          ← 같은 마이그레이션, 같은 트랜잭션
```

`PTSchedule`의 시간 겹침 제약은 `trainer_id`(UUID **등호**)와
시간 범위(`&&`)를 **한 GiST 인덱스에 섞는다.**
GiST는 원래 범위·기하 타입용이라 UUID 등호를 모르는데, `btree_gist`가 그것을 가르쳐준다.

확장 없이 `synchronize`가 돌면 이렇게 실패한다.

```
data type uuid has no default operator class for access method "gist"
```

`uuid-ossp`도 함께 필요하다. **모든 테이블의 PK 기본값이 `uuid_generate_v4()`** 인데
그 함수가 이 확장에 들어있다. 없으면 첫 `CREATE TABLE`에서 바로 실패한다.

**`migration:generate`는 확장을 뽑아내지 못한다.** Entity 메타데이터에 없기 때문이다.
초기 마이그레이션에 손으로 넣었고, 그래서 순서가 보장된다.

> **`docker-entrypoint-initdb.d`를 쓰지 않는 이유**:
> 컨테이너를 **처음 만들 때만** 실행된다.
> 이미 만들어진 개발 DB나 CI 서비스 컨테이너에는 적용되지 않아
> 환경마다 다르게 동작하게 된다. 아래 "무엇이 같아야 하나"의 원칙에 어긋난다.
> 마이그레이션에 두면 **어느 DB에서든 같은 순서로 실행된다.**

### 인덱스 전략

멀티테넌시 구조이므로 **모든 복합 인덱스의 선두 컬럼은 `gymId`**.
대부분의 쿼리가 `WHERE gym_id = ?`로 시작한다. → [[DB 모델링#인덱스 전략]]

## 6. 인증

```
로그인 → Access Token (1시간) + Refresh Token (30일)
          │                       │
          │ stateless             │ DB 저장 (SHA-256 해시)
          │ 무효화 불가            │ 갱신마다 교체 (Rotation)
          │                       │ 폐기 후 재제출 시 전체 세션 종료
```

→ ADR-006, ADR-008, ADR-009

**Access Token이 stateless인 대가**: 로그아웃·계정 정지 후에도 최대 1시간 유효하다.
즉시 무효화가 필요해지면 블랙리스트가 필요하나, 현 단계에서는 짧은 수명으로 감수한다.

## 7. 배포

### 브랜치 전략 — `main`이 운영 배포 시점이다 (2026-08-19 확정)

```
feat/xxx  →  dev  →  main
   PR         PR       ↑
                    운영 배포 = 이 머지
```

`dev`는 통합 브랜치, **`main`은 "지금 운영에 떠 있는 것"** 이다.
배포마다 `dev → main` PR이 생기므로 태그·릴리스 노트를 붙일 자리가 자연스럽게 나온다.

> **정하지 않고 두면 어느 쪽도 아닌 상태가 굳는다.**
> 실제로 `main`은 초기 커밋에서 멈춰 `dev`보다 83커밋 뒤처져 있었다.
> 배포를 안 해서 문제가 안 됐을 뿐이다.

### 버전 태그

`main` 병합마다 `vMAJOR.MINOR.PATCH`를 붙인다.

| | 올리는 때 |
|---|---|
| MAJOR | API 하위 호환이 깨질 때 |
| MINOR | 기능 추가 |
| PATCH | 버그 수정만 |

**`v0.x`인 동안은 하위 호환을 약속하지 않는다.** 클라이언트가 아직 없어
API를 바꾸는 비용이 낮고, 억지로 호환을 지키면 잘못된 설계가 굳는다.
첫 외부 사용자가 붙으면 `v1.0.0`으로 올리고 그때부터 규칙을 지킨다.

```bash
git switch main && git pull
git tag -a v0.1.0 -m "..." && git push origin v0.1.0
```

### `synchronize`는 브랜치가 아니라 환경변수가 끈다

배포 전 사람이 확인해야 하는 항목으로 두지 **않는다.**

```ts
// app.module.ts
synchronize: ['development', 'test'].includes(config.get('NODE_ENV') ?? '')
```
```dockerfile
# Dockerfile
ENV NODE_ENV=production
```

운영 이미지는 `production`이라 자동으로 꺼지고, `NODE_ENV`가 아예 없어도
`?? ''`가 빈 문자열이라 여전히 꺼진다. **안전한 쪽이 기본값이다.**

> **방어는 코드에 두고 문서에는 근거만 남긴다.**
> 체크리스트로 만들면 "체크리스트가 방어선"이라는 착각이 생겨,
> 나중에 코드를 고쳐도 아무도 막지 못한다.

**진짜 위험은 반대편에 있다.** `synchronize`를 끄면 스키마가 아예 만들어지지 않아,
첫 배포에서 앱은 뜨는데 모든 요청이 `42P01 relation does not exist`로 죽는다.
지금까지 테이블은 전부 `synchronize`가 Entity를 보고 만들어준 것이다.
그래서 **마이그레이션은 배포의 선행 조건**이다. → [[향후 과제]]

### 인프라 (미결정)

실제 운영 여부가 아직 미정이다. 다만 **선택지에 따라 앱 코드가 달라지지 않도록** 컨테이너 이미지 단위로 준비한다.

| 방식 | 비용 | 난이도 | 비고 |
|------|------|--------|------|
| 단일 EC2 + Docker Compose | 낮음 | 낮음 | 초기 MVP에 충분 |
| ECS Fargate + RDS | 중간 | 중간 | 서버 관리 불필요 |
| EKS | 높음 | 높음 | 현 규모에 과함 |

**초기에는 단일 인스턴스로 충분하다.** 헬스장 100곳이 붙어도 동시 접속자는 수백 명 수준이다.

```
초기                        확장 시
Nginx                       ALB
  ↓                          ↓
Spring/Nest 1개            Nest 여러 개
  ↓                          ↓
PostgreSQL                 Redis (세션·캐시)
                             ↓
                           PostgreSQL (RDS)
```

## 8. 확장 시 분리 후보

병목이 발생하면 이 순서로 검토한다.

| 대상 | 트리거 | 방법 |
|------|--------|------|
| 통계 쿼리 | 집계가 느려짐 | 읽기 전용 복제본 분리 |
| 출석 이력 | 행이 1천만을 넘음 | 월 단위 파티셔닝 → ADR-013 |
| 출석 체크 | 피크 시간 집중 | 큐 도입 후 비동기 처리 |
| 특정 테넌트 | 대형 고객 발생 | 테넌트 단위 DB 분리 |

> 어느 것도 지금 필요하지 않다. **실제 병목이 측정된 뒤에 한다.**
