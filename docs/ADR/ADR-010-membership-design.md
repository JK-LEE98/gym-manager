# ADR-010: 회원권 도메인 설계

## 배경

실제 헬스장 운영 방식을 조사한 결과([[도메인 지식]]), 초기 설계로는 표현할 수 없는 요구가 드러났다.

- 한 회원이 회원권을 **여러 개 동시 보유**한다 (헬스 + 락커)
- 만료 임박 시 추가 결제하면 **뒤에 이어붙는다**
- 홀딩(휴회) 정책이 **헬스장마다 다르다**
- 양도가 실제로 발생한다
- 기입 형식이 제각각이라 **자유 텍스트**가 필요하다

---

## 결정 1: 회원권 복수 보유 (1:N)

`UserMembership`은 회원당 여러 건이 활성 상태로 존재할 수 있다.

```
헬스권 12개월  +  락커 12개월       ← 성격이 다른 것을 동시 보유
헬스권(잔여 3일) + 헬스권 12개월     ← 같은 성격을 이어붙임
```

**대가**: "잔여일이 며칠인가"에 단일 답이 없다.
→ **카테고리별로 응답**한다. (헬스 잔여 300일, 락커 잔여 300일)

---

## 결정 2: `MembershipType.category` 도입

### 문제

만료 임박 시 이어붙이기를 구현하려는데, **무엇에 이어붙일지 판단할 기준이 없다.**

```
헬스 12개월  +  락커 12개월        → 이어붙이면 안 된다 (동시 진행)
헬스 3개월(만료임박) + 헬스 12개월  → 이어붙여야 한다
```

`MembershipType`만으로는 판단할 수 없다.
"3개월 헬스권"과 "12개월 헬스권"은 **서로 다른 MembershipType**이지만 이어붙어야 하기 때문이다.

### 결정

`MembershipType`에 `category`(자유 문자열)를 둔다.
헬스장이 회원권 종류를 등록할 때 `"헬스"`, `"락커"`, `"PT"` 등을 지정한다.

**enum이 아닌 이유**: 헬스장마다 취급하는 종류가 다르다.
사우나만 파는 곳, 골프 레슨을 함께 하는 곳, 필라테스를 겸업하는 곳이 있다.
미리 열거할 수 없다.

**"운동복과 수건을 나눌지 합칠지"도 우리가 정하지 않는다.**

```
A 헬스장   "헬스" / "락커" / "운동복"          ← 운·수 통합
B 헬스장   "헬스" / "락커" / "운동복" / "수건"   ← 분리
```

헬스장이 회원권 종류를 등록할 때 `category`를 직접 입력하면 그것이 곧 카테고리가 된다.
코드에 카테고리 목록이 존재하지 않는다.

**대가**: 오타로 `"헬스"`와 `"헬스권"`이 갈리면 이어붙기가 동작하지 않는다.
프론트엔드에서 기존 카테고리를 자동완성으로 제공해 완화한다.

## 결정 3: 자동 이어붙이기

`startDate`를 지정하지 않으면 서버가 계산한다.

```
같은 gymId · 같은 userId · 같은 category · 아직 만료되지 않은 회원권
  → 그중 가장 늦은 endDate + 1일
  → 없으면 오늘
```

**명시적으로 `startDate`를 보내면 그 값을 그대로 쓴다.**
"오늘 결제했지만 다음 주부터 이용" 같은 요구가 실제로 있다.

`endDate`는 항상 서버가 계산한다. (`startDate + durationDays - 1`)
클라이언트가 보낸 종료일은 신뢰하지 않는다.

> **왜 -1인가**: 1일권을 오늘 시작하면 오늘 하루만 유효해야 한다.
> `startDate + 1`이면 이틀이 된다.

## 결정 4: 만료는 저장하지 않고 계산한다

`status`는 **사람이 개입한 상태만** 담는다.

```
status      ACTIVE | CANCELLED | TRANSFERRED   ← 사람이 바꾼 것
만료 여부    endDate < today 로 판단            ← 날짜에서 파생
홀딩 여부    MembershipHold + 날짜로 판단       ← 날짜에서 파생
```

> **이 원칙이 이후 두 번 더 적용됐다.**
> ADR-011의 홀딩 `phase`(예정/진행중/완료)를 저장하지 않은 것,
> #22에서 쓰이지 않던 `SUSPENDED`를 제거한 것이 같은 판단이다.
> 처음 작성 시점의 enum에는 `SUSPENDED`가 있었으나
> 홀딩을 테이블로 분리하면서 존재 이유가 사라졌다.

### 선택하지 않은 안

스케줄러가 매일 자정에 `status`를 `EXPIRED`로 갱신하는 방식.

- 조회가 단순해지고 인덱스를 잘 타는 장점이 있으나,
- **같은 사실이 두 곳(`endDate`, `status`)에 저장되어 어긋날 수 있다**
- 스케줄러가 멈추면 데이터가 실제와 달라진다
- 자정 직후 잠깐 불일치가 생긴다

ADR-007에서 정리한 **단일 출처 원칙**과 같은 판단이다.

> 스케줄러는 만료 임박 알림(D-7/D-3/D-1)을 만들 때 어차피 필요해진다.
> 그때 도입하되, `status` 갱신 용도로는 쓰지 않는다.

## 결정 5: 잔여일은 D-day 표기로 노출한다

데스크에서 회원을 응대할 때 가장 먼저 보는 정보다.
**성능보다 정확성과 노출 우선순위가 높다.**

### "N일 남음"을 쓰지 않는 이유

당일 포함 여부가 애매하다. 만료일이 오늘일 때 "0일 남음"인지 "1일 남음"인지
사람마다 다르게 읽고, **회원과 분쟁이 날 여지가 있다.**

**절대 날짜를 함께 주면 해석의 여지가 사라진다.**

```json
{
  "category": "헬스",
  "endDate": "2026-09-04",
  "daysUntilExpiry": 4
}
```

```
daysUntilExpiry = endDate - today
```

| 상황 | 값 | 표기 |
|------|-----|------|
| 만료일이 오늘 | `0` | D-day (오늘까지 이용 가능) |
| 만료일이 내일 | `1` | D-1 |
| 이미 만료 | `-1` 이하 | 만료됨 |

한국식 D-day 관용과 일치한다.
화면 표현은 클라이언트가 `endDate`와 `daysUntilExpiry`를 받아 결정한다.

> **API 이름에서부터 애매함을 뺀다.** `remainingDays`는 해석이 갈리므로 쓰지 않는다.

### 타임존 — "오늘"은 KST 기준이어야 한다

컨테이너는 기본적으로 UTC로 동작한다.

```
한국 시간  2026-08-06 08:00
UTC       2026-08-05 23:00    ← 서버가 UTC면 "어제"로 계산
```

**아침 9시 이전 조회에서 잔여일이 하루 더 많게 나온다.**
오픈 시간에 회원을 응대하는 헬스장이라면 매일 아침 틀린 값을 보게 된다.

**결정: 컨테이너 타임존을 KST로 고정한다.**

```dockerfile
ENV TZ=Asia/Seoul
```

선택하지 않은 안: 날짜 계산 시마다 KST로 명시적 변환.
정확하지만 코드가 늘고, 현재는 국내 전용 서비스라 이득이 없다.

> **해외 지점이 생기면** `Gym`에 타임존 컬럼을 두고 헬스장 기준으로 계산한다.
> → [[향후 과제]]

### N+1 방지

회원 목록에서도 잔여일을 함께 반환하므로,
`QueryBuilder`로 조인해 한 번에 가져온다.

## 결정 6: 메모를 두 곳에 둔다

성격이 다른 정보이므로 분리한다.

| 위치 | 용도 | 예시 |
|------|------|------|
| `User.memo` | 회원 전반의 특이사항 | 무릎 부상 이력, 응대 시 참고사항 |
| `UserMembership.memo` | 결제 건별 기록 | `*26.08.06 H12 + 락커12 [카 55만]` |

**형식을 강제하지 않는다.** 헬스장마다 기입 방식이 다르다.
구조화하려 시도하면 오히려 현장에서 쓰이지 않는다.

## 결정 7: 홀딩 정책은 MembershipType에 둔다

실제 정책 사례는 **회원권 기간에 따라 갈린다.**

| 회원권 기간 | 홀딩 가능 횟수 |
|------------|--------------|
| 6개월 미만 | 불가 |
| 6~12개월 미만 | 3회 |
| 12개월 이상 | 5회 |

`MembershipType`이 이미 `durationDays`를 갖고 있으므로,
**종류마다 홀딩 정책 필드를 두면 그대로 표현된다.**

```
"3개월권"   holdingLimit: 0
"6개월권"   holdingLimit: 3
"12개월권"  holdingLimit: 5
```

별도 정책 테이블이 필요 없다.

> 필드 추가는 홀딩 기능을 구현하는 Phase 2-2에서 한다.
> 쓰지 않을 컬럼을 미리 만들지 않는다. (CLAUDE.md 1-2)
