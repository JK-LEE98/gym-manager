# ADR-004: 멀티테넌시 구조 채택

## 배경

초기 설계는 헬스장 1곳을 전제로 했으나, 역할 체계를 논의하는 과정에서
"서비스 운영자가 헬스장 대표 계정을 발급한다"는 요구가 나왔다.
이는 곧 **하나의 서비스가 여러 헬스장을 동시에 관리**한다는 의미이며,
B2B SaaS의 멀티테넌시(Multi-tenancy) 구조가 필요하다.

## 선택지

### 테넌시 격리 수준

| | 설명 | 비용 | 격리 수준 |
|---|------|------|----------|
| DB 분리 | 헬스장마다 별도 DB | 매우 높음 | 최상 |
| 스키마 분리 | 헬스장마다 별도 스키마 | 높음 | 상 |
| **행 단위 분리** | 단일 스키마 + `gym_id` 컬럼 | 낮음 | 중 (앱 레이어에서 보장) |

### gym_id 배치 범위

**A안 — User에만 배치 (정규화 우선)**
- 다른 테이블은 `userId` → `User.gymId` JOIN으로 도달
- 장점: 데이터 중복 없음
- 단점: 모든 통계 쿼리가 JOIN 필요, 필터 누락 시 테넌트 간 데이터 유출 위험

**B안 — 주요 테이블에 전부 배치 (방어적 비정규화)**
- 장점: 단순 `WHERE gym_id = ?` 로 조회, 인덱스 효율, 필터 누락이 눈에 띔
- 단점: 데이터 중복 (단, gym_id는 불변값이므로 갱신 이상 없음)

## 결정

- **행 단위 분리 (단일 DB + `gym_id` 컬럼)** 채택
- **B안 — 주요 테이블에 `gym_id` 배치** 채택

### gym_id 배치 대상

| 테이블 | gym_id | 비고 |
|--------|--------|------|
| Gym | - | 테넌트 자체 |
| User | O | SUPER_ADMIN만 null |
| MembershipType | O | 헬스장마다 회원권 종류 상이 |
| Payment | O | 매출 통계 |
| UserMembership | O | 회원권 현황 |
| Attendance | O | 출석률 통계 |
| PTContract | O | PT 현황 |
| PTSchedule | O | 트레이너 슬롯 조회 |
| TrainerProfile | X | User와 1:1, 항상 User 경유 |

## 이유

- 초기 서비스 규모에서 DB/스키마 분리는 운영 비용이 과도함
- 통계 API(매출, 출석률)가 전부 JOIN을 타는 것을 방지
- `gym_id`는 생성 후 변경되지 않는 불변값이라 비정규화의 전형적 단점(갱신 이상)이 없음
- 헬스장 단위 데이터 분리/샤딩이 필요해질 때 이관이 용이

## 데이터 격리 보장 방식

행 단위 분리는 **애플리케이션 레이어가 격리를 책임진다.**
필터를 수동으로 붙이면 반드시 누락이 발생하므로 아래 구조로 강제한다.

1. `JwtStrategy`가 토큰 payload에서 `gymId`를 추출해 `request.user`에 주입
2. `@CurrentGym()` 커스텀 데코레이터로 Controller에서 꺼냄
3. Service 메서드 시그니처가 `gymId`를 필수 인자로 받도록 설계
   → 컴파일 타임에 누락이 잡힘
4. SUPER_ADMIN만 `gymId` 없이 전체 조회 가능 (별도 Guard로 분기)

## 결과

- `Gym` 테이블 신설
- 기존 7개 테이블 중 6개에 `gym_id` FK 추가
- 모든 조회 쿼리에 테넌트 필터 적용
- **면접 포인트**: "B2B SaaS 멀티테넌시에서 테넌트 간 데이터 격리를 타입 시스템으로 강제했습니다"

## 알려진 한계

- 앱 레이어 버그 시 데이터 유출 가능 (DB 레벨 강제가 아님)
  → 향후 PostgreSQL Row Level Security(RLS) 도입 검토 가능
- 테넌트 수가 크게 늘면 단일 테이블 크기가 병목이 될 수 있음
  → 파티셔닝 또는 샤딩으로 대응
