# ADR-005: OWNER 계정을 개인 계정과 분리 (운영 계정 모델)

## 배경

"대표이면서 트레이너인 사람"을 어떻게 처리할지 결정해야 했다.
초기에는 인스타그램식 계정 전환, 또는 한 계정에 여러 역할을 부여하는 방식을 검토했다.

그러나 실제 헬스장 운영 실태를 보면:
- **대표 계정은 헬스장 프론트 데스크 컴퓨터에 상주**한다
- 트레이너, 인포데스크 직원, 매니저가 **같은 계정을 공유**해서 신규 회원 등록 등의 업무를 처리한다
- 즉 대표 계정은 "개인의 정체성"이 아니라 **"헬스장의 운영 계정"** 이다

## 선택지

**A안 — OWNER 권한이 TRAINER를 포함**
- role 1개. OWNER도 TrainerProfile을 갖고 PT 계약의 담당자가 될 수 있음
- 대표 계정이 개인 계정이라는 전제 → 실제 운영 방식과 불일치

**B안 — 계정 1개 + 역할 여러 개 (UserGymRole 조인 테이블)**
- 슬랙 워크스페이스 방식. 로그인 후 역할 전환
- 가장 정석이나 권한 체크 로직이 복잡해짐. 공용 계정 개념을 표현하지 못함

**C안 — 계정 분리 (운영 계정 모델)**
- OWNER = 헬스장 공용 운영 계정 (개인 정체성 아님)
- TRAINER = 개인 계정 (PT 계약, 일정이 귀속됨)
- 대표이자 트레이너인 사람은 두 계정을 상황에 따라 사용

## 결정

**C안 채택 — OWNER는 헬스장 운영 계정으로 정의**

## 이유

- 실제 헬스장 운영 방식과 일치 (프론트 데스크 공용 사용)
- OWNER와 TRAINER는 같은 사람의 다른 역할이 아니라 **성격이 다른 별개 계정**이므로,
  계정 전환 UI 자체가 불필요해짐
- 권한 모델이 단순해짐: role 1개 = 권한 1세트
- PT 계약의 `trainerId`는 항상 개인 TRAINER 계정을 가리키므로,
  "누가 수업했는지"가 명확하게 추적됨

## 역할 체계 최종

| 역할 | 성격 | gymId | 설명 |
|------|------|-------|------|
| SUPER_ADMIN | 개인 | null | 서비스 운영자. 헬스장 등록, OWNER 계정 발급 |
| OWNER | **공용 운영 계정** | 필수 | 헬스장 운영 전반. 프론트 데스크에서 직원들이 공유 |
| TRAINER | 개인 | 필수 | PT 일정/계약이 귀속되는 개인 계정 |
| MEMBER | 개인 | 필수 | 일반 회원 |

## 계정 생성 흐름

```
SUPER_ADMIN → Gym 등록 + OWNER 계정 발급
MEMBER      → 공개 회원가입 API로 스스로 가입 (gymId 지정)
TRAINER     → MEMBER로 가입 후, OWNER가 역할을 TRAINER로 변경
              → 승격 시 TrainerProfile 자동 생성
```

## 결과

- `User.role` 단일 컬럼으로 권한 표현 (조인 테이블 불필요)
- 계정 전환 기능 미구현
- `TrainerProfile`은 role=TRAINER인 User만 보유
- `PTContract.trainerId`, `PTSchedule.trainerId`는 role=TRAINER인 User만 허용

## 알려진 한계 — 감사 추적(Audit Trail) 부재

공용 계정 구조의 대가로 **"누가 이 회원을 등록했는지" 추적이 불가능**하다.
OWNER 계정으로 발생한 모든 행위는 개인을 특정할 수 없다.

실제 B2B SaaS에서도 흔한 트레이드오프이며, 현재 MVP 범위에서는 수용한다.

**향후 개선 방향**: `STAFF` 역할을 추가하고 직원마다 개인 계정을 발급하면
행위자 추적이 가능해진다. 이때 OWNER는 순수 관리 권한만 갖게 된다.
