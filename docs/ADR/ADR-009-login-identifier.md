# ADR-009: 로그인 식별자 — 이메일이 아닌 아이디

## 배경

초기 설계는 `email + password` 로그인이었다.
그런데 **이메일 인증 절차를 넣지 않기로 한 상태**에서 이메일을 받는 것은 모순이라는 지적이 나왔다.

검증되지 않은 이메일은 단순한 문자열일 뿐이며, 다음 문제를 만든다.

- 오타나 타인의 주소를 입력해도 걸러지지 않는다
- "이메일이 있으니 비밀번호 찾기가 되겠지"라는 잘못된 기대를 준다
- 실제로는 아무 데도 쓰이지 않는 필드가 스키마에 남는다

즉 **이메일을 쓰려면 인증까지 해야 하고, 인증을 안 할 거면 이메일을 받지 말아야 한다.**

## 선택지

**A. 이메일 + 이메일 인증**
- 메일 발송 인프라 필요 (SES / SendGrid / Nodemailer), 로컬 개발엔 Mailhog 등
- 인증 토큰 저장소, 2단계 가입 플로우
- 부가 이득: 셀프 비밀번호 찾기 가능, [[ADR-008-user-enumeration|ADR-008]]의 C안(항상 성공 응답)으로 열거 문제 해결

**B. 아이디 + 비밀번호**
- 추가 인프라 없음
- 비밀번호 분실 시 셀프 복구 수단이 없음 → 별도 해결 필요

## 결정

**B — `loginId` + `password`. `email` 컬럼 제거.**

## 이유

### 1. 도메인과 맞는다

헬스장 회원관리에서 실질적인 식별·연락 수단은 **전화번호**다. 이메일을 받는 헬스장은 드물다.
`User.phone`이 이미 있으므로 연락 수단은 충족된다.

### 2. 비밀번호 분실이 문제가 되지 않는다

B의 유일한 약점인데, **상위 역할이 초기화**하는 방식으로 해결된다.

```
MEMBER / TRAINER  분실 → OWNER가 초기화        (데스크에서 즉시)
OWNER             분실 → SUPER_ADMIN이 초기화   (서비스 운영자에게 문의)
SUPER_ADMIN       분실 → DB 직접 수정 / 스크립트
```

회원이 데스크에 가서 "비밀번호를 잊었다"고 하면 직원이 초기화해주는 흐름이며,
**실제 헬스장 운영 방식과 정확히 일치한다.**
OWNER를 프론트 데스크 공용 계정으로 정의한 [[ADR-005-owner-account-separation|ADR-005]]와도 자연스럽게 이어진다.

### 3. OWNER 계정에 이메일이 어울리지 않는다

OWNER는 개인이 아니라 헬스장 운영 계정이다.
`gangnam@gym.com` 같은 주소를 억지로 만드는 것보다 `gangnam_gym` 같은 아이디가 자연스럽다.
SUPER_ADMIN도 마찬가지다.

### 4. 보안이 나빠지지 않는다

열거 대상이 이메일에서 아이디로 바뀌지만 **아이디는 표적 가치가 훨씬 낮다.**

| | 이메일 유출 시 | 아이디 유출 시 |
|---|---|---|
| 크리덴셜 스터핑 | 외부 유출 목록과 대조 가능 | 대조 불가 |
| 피싱 | 직접 발송 가능 | 발송 경로 없음 |
| 프라이버시 | 개인 식별 가능 | 서비스 내부 식별자에 그침 |

→ [[ADR-008-user-enumeration|ADR-008]]을 이에 맞게 개정한다.

## 스키마 변경

```
- email      VARCHAR(100) UNIQUE NOT NULL
+ loginId    VARCHAR(50)  UNIQUE NOT NULL
```

`email` 컬럼은 **제거**한다. 쓰지 않을 필드를 남겨두지 않는다.

**검증 규칙**
- 길이 4~20자
- 영문 소문자, 숫자, 언더스코어(`_`)만 허용
- 전역 유니크 (한 계정 = 한 헬스장)

## 추가되는 API

```
PATCH /users/:id/reset-password

OWNER        자기 헬스장의 MEMBER / TRAINER만 대상
SUPER_ADMIN  제한 없음 (OWNER 포함)
```

**임시 비밀번호는 서버가 생성해 응답에 1회만 반환한다.**
관리자가 직접 입력하게 하면 `1234` 같은 값을 넣게 되므로 서버가 랜덤 생성한다.

## 알려진 한계

### OWNER 분실 시 헬스장 전체가 잠긴다

OWNER는 공용 계정이므로 비밀번호를 분실하면 직원 전체가 접근 불가 상태가 된다.
회원 등록·출석 확인이 모두 멈추고, 서비스 운영자의 초기화를 기다려야 한다.

B2B SaaS에서 벤더가 고객사 계정을 초기화해주는 것은 일반적인 운영 방식이지만,
**대응 속도가 곧 서비스 품질**이 된다. 창업 단계에서는 대응 시간 기준(SLA)이 필요하다.

향후 완화책: 헬스장당 OWNER 계정 복수 발급, 또는 OWNER에 한해 복구용 연락처 등록.

### 초기화한 관리자가 비밀번호를 알게 된다

`mustChangePassword` 플래그로 첫 로그인 시 변경을 강제하는 것이 정석이나,
로그인 응답에 분기가 생기고 비밀번호 변경 전용 플로우가 따라와 Phase 1 범위를 넘는다.
헬스장 데스크 맥락에서는 감수 가능한 수준으로 판단해 향후 과제로 남긴다.

## 향후 확장

B2C로 확장해 회원이 셀프 서비스로 가입·복구해야 할 때 `email` 컬럼을 추가하고
이메일 인증을 붙인다. `loginId`를 유지한 채 `email`을 더하는 것은 마이그레이션으로 처리 가능하다.
