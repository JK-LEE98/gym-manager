# ADR-011: 회원권 홀딩(휴회) 설계

## 배경

회원권을 일시 정지하고 그만큼 종료일을 미루는 기능.
정책이 헬스장마다 다르며([[도메인 지식#4. 홀딩 (휴회)]]), 잘못 처리하면 **회원이 실제로 손해를 본다.**

실제 운영 사례(개발자 근무처):

```
1회 최대       14일. 원하는 일수로 지정 가능
횟수 제한      회원권 기간에 따라 다름 (12개월권 5회 → 최대 70일)
미래 날짜      가능
일정 변경      가능해야 함 (회원 사정이 바뀐다)
```

---

## 결정 1: 정책은 MembershipType에 둔다

실제 정책이 **회원권 기간에 따라 갈리므로**, 종류마다 필드를 두면 그대로 표현된다.

```
MembershipType
  + holdingLimit    INT  DEFAULT 0   홀딩 가능 횟수
  + holdingMaxDays  INT  DEFAULT 14  1회당 최대 일수
```

```
"3개월권"   holdingLimit: 0   → 홀딩 불가
"6개월권"   holdingLimit: 3
"12개월권"  holdingLimit: 5   → 최대 14×5 = 70일
```

별도 정책 테이블이 필요 없다.

---

## 결정 2: 종료일은 **항상 전체 재계산**한다

### 문제 — 증분 조정이 사고를 만든다

```
홀딩 10일 등록  →  endDate + 10
5일로 수정      →  endDate - 5     ← 여기서 어긋난다
```

수정을 여러 번 하거나 중간에 다른 변경이 끼면 숫자가 틀어지고, 되돌리기도 어렵다.

### 결정

```
endDate = startDate + durationDays - 1 + (홀딩 이력의 총 일수)
```

홀딩을 **생성·수정·취소할 때마다 처음부터 다시 계산**한다.
몇 번을 수정해도 결과가 항상 정확하며, `-5`를 정확히 되돌려야 하는 부담이 사라진다.

> ADR-010에서 만료를 `status`에 저장하지 않기로 한 것과 같은 원리다.
> **파생값을 증분으로 관리하지 않는다.**

`endDate`는 조회 성능을 위해 저장하되, 파생값이므로 항상 전체 재계산으로 갱신한다.

## 결정 3: 소급 수정을 허용한다

### 검토한 우려

"오늘이 7일인데 홀딩 종료일을 6일로 당기는 것"을 막아야 하는가?

### 결정: 허용한다

**막으면 우회한다.** 소급 수정을 금지하면 직원은 기간 연장으로 우회하고,
그러면 왜 연장했는지 추적이 더 어려워진다.

```
막았을 때     연장 기록만 남음 → 이유를 알 수 없음
허용했을 때   홀딩 8/1~8/5로 수정됨 → 무슨 일이 있었는지 명확
```

**현실의 요구를 막으면 사라지는 것이 아니라 추적 불가능한 형태로 새어나간다.**

실제 위험은 소급 자체가 아니라 **종료일 재계산의 부정확함**이었고,
그것은 결정 2로 해결된다.

### 제약

- 홀딩 종료일 < 시작일 불가
- 모든 홀딩과 수정 이력을 별도 테이블에 남긴다

## 결정 4: 회원 셀프 홀딩과 데스크 대행을 모두 제공한다

목적과 사용자가 다르다.

```
회원 (앱)       젊은 층이 직접 신청
데스크 (OWNER)  전화 요청을 대신 처리 (어르신 등)
```

### 권한 차이

| | 회원 | OWNER |
|---|:---:|:---:|
| 미래 날짜 홀딩 | ✅ | ✅ |
| **과거 소급** | ❌ | ✅ |
| 시작 전 취소 | ✅ (본인 것) | ✅ |
| 진행 중 홀딩 종료일 수정 | ❌ | ✅ |

**회원의 소급을 막는 이유**: 지난주에 나오지 않은 것을
나중에 "그때 홀딩이었다"로 돌려받는 악용이 가능하다.

반면 데스크는 "회원이 전화했는데 처리를 깜빡했다" 같은 정당한 소급이 필요하다.

### 즉시 반영

승인 절차를 두지 않는다. 횟수·일수 정책이 시스템에서 강제되므로
정책 범위 안이면 헬스장이 거부할 이유가 없고, 승인은 마찰만 만든다.

**누가 등록했는지는 기록한다.** 분쟁 시 "회원이 직접 걸었다"와
"데스크가 걸어줬다"는 다른 사실이다.

```
MembershipHold
  + createdByUserId  UUID   실제 등록한 계정
  + createdByRole    ENUM   MEMBER | OWNER
```

## 결정 5: 기간 연장(extend)은 사유를 필수로 한다

### 배경

Phase 2-1에서 `PATCH /memberships/:id/extend`를 구현했으나,
실제 헬스장 시스템에는 ±일수 기능이 없다는 지적이 나왔다.

### 판단

**제거하지 않는다.** 시설 공사로 휴관해 전 회원에게 보상하는 경우처럼
홀딩으로 표현할 수 없는 정당한 용도가 있다.

**다만 사유를 필수로 바꾼다.** 홀딩이 제대로 동작하면 `extend`는
"귀찮으니 며칠 더 주자"의 우회 경로가 되기 쉽다.
사유가 남으면 "이 회원권은 왜 이렇게 길지?"를 추적할 수 있다.

```
ExtendMembershipDto
  days   INT     필수
  reason STRING  필수 (기존 memo → reason 으로 명확화)
```

## 스키마

```
MembershipType
  + holdingLimit    INT DEFAULT 0
  + holdingMaxDays  INT DEFAULT 14

MembershipHold (신설)
  id                UUID  PK
  gymId             UUID  FK
  userMembershipId  UUID  FK
  startDate         DATE
  endDate           DATE
  status            ENUM  SCHEDULED | ACTIVE | COMPLETED | CANCELLED
  createdByUserId   UUID  FK
  createdByRole     ENUM  MEMBER | OWNER
  reason            TEXT  nullable
  createdAt/updatedAt
```

> `status`에 만료 개념을 두지 않는 것은 회원권과 같다.
> 진행 여부는 날짜로 판단하고, `CANCELLED`만 사람이 개입한 상태다.
