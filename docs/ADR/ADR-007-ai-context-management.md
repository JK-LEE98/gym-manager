# ADR-007: AI 컨텍스트 관리 전략 (CLAUDE.md 계층화)

## 배경

이 프로젝트는 Claude를 멘토/동업자/도구로 활용하는 것이 목적 중 하나다.
협업 규칙을 `CLAUDE.md`에 축적해왔는데, 프로젝트가 진행되며 파일이 계속 커졌다.

```
초기: 약 150줄  →  Phase 1 진입 시점: 388줄 (13KB)
```

`CLAUDE.md`는 **모든 요청마다 로드되는 파일**이다.
구체적으로 쓸수록 의도한 방향으로 협업이 되지만, 무한정 키울 수는 없다.

## 발견한 문제

### 1. 정합성 붕괴 (실제 발생)

토큰 유효기간 정책을 변경할 때(ADR-006 개정) `.env`와 `.env.example`은 갱신했으나
`CLAUDE.md`의 환경변수 섹션은 누락했다.

```
CLAUDE.md    JWT_ACCESS_EXPIRES_IN=15m   JWT_REFRESH_EXPIRES_IN=7d   ← 낡음
.env         JWT_ACCESS_EXPIRES_IN=1h    JWT_REFRESH_EXPIRES_IN=30d  ← 실제
```

**매 요청마다 로드되는 파일이 거짓 정보를 담고 있는 상태**가 되었다.
같은 사실이 두 곳에 기록되면 반드시 어긋나며, 어긋난 문서는 없는 문서보다 해롭다.
잘못된 정보를 확신을 갖고 따르게 되기 때문이다.

### 2. 주의 분산 (Attention Dilution)

토큰 비용 자체는 크지 않다. 388줄 ≈ 4,000토큰으로 컨텍스트 창의 약 2% 수준이다.

더 실질적인 비용은 **규칙 개수가 늘수록 개별 규칙의 준수율이 떨어진다**는 점이다.
100줄일 때 잘 지켜지던 규칙이 400줄이 되면 놓치기 시작한다.
문제는 파일 크기(토큰)가 아니라 **규칙의 밀도**다.

## 결정

정보를 **3계층으로 분리**하고 각 계층에 단일 출처 원칙(SSOT)을 적용한다.

| 계층 | 위치 | 담는 것 | 로드 시점 |
|------|------|--------|----------|
| ① 항상 로드 | `CLAUDE.md` | 항상 참이고, 어기면 손해가 크고, 다른 곳에 없는 규칙 | 매 요청 |
| ② 필요시 읽기 | Obsidian Vault | 상세 맥락, 설계 근거, 이력, ADR | 관련 작업 시 |
| ③ 사실의 출처 | 실제 파일 | `.env.example`, `package.json`, 코드 | 필요 시 직접 조회 |

### 핵심 규칙

> **③에 있는 것을 ①에 복사하지 않는다.**
> 실행 가능한 형태로 이미 존재하는 정보를 문서에 옮겨 적는 순간 정합성 부채가 된다.

> **②에 있는 것을 ①에 요약하지 않는다.**
> 진행 상태·이력처럼 자주 바뀌는 정보는 한 곳에서만 관리한다.

## 적용 결과

| 섹션 | 기존 | 조치 | 근거 |
|------|-----|------|------|
| 환경변수 | 22줄 | **삭제** | `.env.example`이 단일 출처. 이미 불일치 발생 |
| 현재 진행 상태 | 17줄 | **삭제** | Obsidian `개발 로그.md`가 단일 출처 |
| Claude의 역할 3가지 | 21줄 | 압축 | 행동 원칙과 내용 중복 |
| 개발 워크플로우 5단계 | 82줄 | 압축 | 예시 명령어 축약 |
| Git 컨벤션 | 41줄 | 압축 | 커밋 예시 축약 |
| Git 컨벤션 + 개발 워크플로우 | 123줄 | 통합·압축 | 같은 주제가 두 섹션으로 나뉘어 있었음 |
| 행동 원칙 / 코딩 컨벤션 / 컨텍스트 유지 규칙 | 88줄 | **유지** | 핵심 규칙 |

### 실측 결과

```
줄 수    388줄    →  206줄     (47% 감소)
바이트   13,225B  →  9,062B    (31% 감소)
```

> 줄 수와 바이트의 감소폭이 다른 이유는, 순수 삭제뿐 아니라
> 표·인라인 목록으로 **압축**한 부분이 많기 때문이다.
> 토큰 수는 바이트에 가깝게 움직이므로 **실제 절감은 31%로 보는 것이 정확하다.**

삭제가 아니라 **있어야 할 계층으로 이동**시킨 것이다. 정보는 사라지지 않는다.

### 추가로 얻은 것

압축 과정에서 **Git 컨벤션과 개발 워크플로우가 별개 섹션으로 중복**되어 있던 것을 발견해 통합했다.
컨텍스트 정리는 단순한 다이어트가 아니라 **문서 구조의 결함을 드러내는 과정**이기도 하다.

## 유지보수 규칙

앞으로 `CLAUDE.md`에 무언가를 추가하려 할 때 아래를 자문한다.

1. 이 정보가 다른 파일에 이미 실행 가능한 형태로 존재하는가? → 있으면 추가하지 않는다
2. 자주 바뀌는 정보인가? → Obsidian으로
3. 어겼을 때 실제로 손해가 발생하는 규칙인가? → 아니면 추가하지 않는다
4. 특정 작업에서만 필요한 규칙인가? → 해당 문서로

**주기적 점검**: Phase가 끝날 때마다 `CLAUDE.md`를 검토하고,
③계층과 중복된 내용이 생겼는지 확인한다.

## 결과

- `CLAUDE.md` 388줄 → 206줄 (바이트 기준 31% 감소)
- 환경변수 불일치 해소 — `.env.example`을 단일 출처로
- 진행 상태 관리 지점 일원화 — Obsidian `개발 로그.md`
- 중복 섹션(Git 컨벤션 / 개발 워크플로우) 통합
- 파일 상단에 **"이 파일의 원칙"** 섹션을 추가해 재비대화를 방지

## 포트폴리오 관점

AI 협업이 보편화되면서 "AI에게 무엇을 항상 알려줄 것인가"는 새로운 설계 문제가 되었다.
아직 확립된 베스트 프랙티스가 없는 영역이므로, 직접 문제를 발견하고 기준을 세운 과정 자체가 차별점이다.

**면접 서술 예시**

> "AI 협업 규칙 파일이 커지면서 두 가지 문제를 발견했습니다.
> 하나는 같은 정보가 여러 곳에 중복되면서 실제로 값이 어긋난 사례가 나왔고,
> 다른 하나는 규칙이 많아질수록 개별 규칙의 준수율이 떨어진다는 점이었습니다.
> 그래서 항상 로드되는 규칙, 필요할 때 읽는 문서, 사실의 출처가 되는 실제 파일을
> 3계층으로 분리하고 단일 출처 원칙을 적용해 38% 축소했습니다."

## 향후 검토

- 프로젝트가 더 커지면 디렉토리별 `CLAUDE.md` 분리 검토
  (예: `src/auth/CLAUDE.md`에 인증 모듈 고유 규칙)
- 자주 쓰지 않는 규칙은 별도 문서로 빼고 `CLAUDE.md`에는 포인터만 두는 방식
