# ADR-015: 알림(SSE) 제거와 회원 상태 필터 조회

## 배경

설계 초기에 Phase 5를 **SSE 실시간 알림**으로 잡았다. 트리거는 셋이었다.

```
① PT 슬롯 예약됨    → 트레이너에게  "홍길동님이 8/1 10:00 수업을 예약했습니다"
② PT 예약 취소됨    → 상대방에게    "8/1 10:00 수업이 취소되었습니다"
③ 회원권 만료 임박  → 회원에게      "회원권이 3일 후 만료됩니다" (D-7/D-3/D-1)
```

**구현 직전에 각 트리거를 다시 검사했더니 대부분 근거가 사라져 있었다.**

---

## 결정 1: 알림 기능을 제거한다

### 트리거별 검사

| | 상태 | 이유 |
|---|------|------|
| ① PT 예약됨 | ❌ 폐기 | **회원이 예약하지 않는다.** 트레이너가 직접 등록한다(ADR-014). 자기가 방금 입력한 것을 자기에게 알릴 이유가 없다 |
| ② PT 취소됨 | △ | 회원이 취소할 수 있으니 트레이너가 알아야 한다. 다만 현장에서는 카톡으로 먼저 말한다 |
| ③ 만료 임박 | ❌ 대상 오류 | **회원에게 보내려면 그 순간 브라우저가 열려 있어야 한다.** 그리고 이것은 원래 데스크가 하는 일이다 |

### 문서 간 모순도 있었다

```
기능 명세    "알림 목록 조회 (읽음/안읽음 상태)"
API 명세     그런 엔드포인트 없음. "DB 저장 없음"
```

**저장하지 않는데 목록을 조회할 수 없다.** 두 문서가 서로 다른 설계를 적고 있었다.

### 근본 이유 — Pull은 클라이언트 부재를 견디고 Push는 못 견딘다

이 프로젝트에는 **MEMBER용 클라이언트가 없다.** 앱을 만들지 않기로 했기 때문이다.

그런데 다른 MEMBER API들은 그 상태에서도 멀쩡하다.

```
GET /memberships/me        내 회원권
GET /attendance/me         내 출석 이력
GET /pt/schedules/me       내 PT 일정
GET /attendance/qr-token   QR 발급
```

**설계가 클라이언트를 기다리고 있을 뿐 망가진 상태가 아니다.** 앱이 붙으면 그대로 동작한다.

SSE만 다르다. **"지금 연결되어 있는가"에 기능의 존재 자체가 걸려 있다.**

그리고 앱이 생겨도 SSE는 답이 아니다.

> FCM 푸시 알림 — 앱 추가 시. **SSE는 앱 백그라운드에서 동작하지 않으므로 대체 필요** → [[향후 과제]]

**지금도 안 맞고 나중에도 안 맞는다.** 중간에 잠깐 쓸 자리가 없다.

### 이미 같은 결론에 세 번 도달했다

| 문제 | 해법 |
|------|------|
| 데스크가 홀딩 해제를 깜빡한다 | `GET /holds/ending-today` |
| 수업 확인을 놓친다 | `GET /pt/schedules/unconfirmed` |
| 만료를 놓쳐 매출을 잃는다 | 회원 조회 화면의 잔여일 상시 노출 |

셋 다 **"놓치지 않게 보여주되, 누르는 것은 사람이다"** 였고 셋 다 SSE가 필요 없었다.
알림도 같은 성질의 문제다. 우연이 아니라 **이 도메인의 성질**이다.

> **기능을 뺀 것도 결정이다.** "SSE를 구현했다"보다
> "검토 끝에 제거했고 그 이유를 설명할 수 있다"가 더 정확한 설계다.

## 결정 2: 필요한 것은 "대상 목록" 조회다

현장에서 실제로 하는 일은 이렇다. → [[도메인 지식#10. 만료 관리]]

```
만료 임박   →  알림 문자   "곧 만료됩니다"     →  재등록 유도
이미 만료   →  홍보 문자   "다시 오세요"       →  복귀 유도
```

**대상도 문구도 목적도 다른 두 목록이다.**

### 정확값과 범위를 구분한다

```
GET /users?category=헬스&expiringInDays=3       정확히 3일 남음
GET /users?category=헬스&expiredWithinDays=30   30일 이내에 만료됨
GET /users?startedWithinDays=7                  운동 시작 7일차
```

**`expiringInDays`가 범위가 아니라 정확값인 것이 핵심이다.**

```
❌ 7일 이내      → D-7, D-5, D-3이 모두 섞인다
                   매일 돌리면 한 사람에게 문자가 여러 번 간다

✅ 정확히 3일    → 오늘 D-3인 사람만
                   매일 돌려도 한 사람당 한 번
```

**중복 발송 방지가 이 기능의 존재 이유다.** 범위로 만들면 쓸 수 없다.

반대로 복귀 홍보는 "지난 30일 안에 만료된 사람 전부"가 자연스럽다.
한 명씩 정확히 뽑을 이유가 없다. **용도가 다르므로 파라미터를 나눈다.**

### 별도 엔드포인트를 만들지 않는다

기존 `GET /users`에 필터로 얹는다.

- 새 엔드포인트를 만들면 페이지네이션·검색·정렬을 다시 구현해야 한다
- 문자를 보내려면 이름·전화번호가 필요한데 **이미 이 응답에 있다**

## 결정 3: 카테고리로 구분한다

회원이 여러 회원권을 동시에 보유하므로 "만료 임박 회원"이 애매해진다.

```
홍길동
  헬스 12개월   D-3    ← 임박
  락커 6개월    D-95
```

`category`를 지정해 조회한다. **가장 늦은 종료일 기준으로 뭉치면 락커 때문에 헬스 임박이 가려진다.**

같은 카테고리를 여러 건 보유(이어붙이기)한 경우 **그 카테고리에서 가장 늦은 `endDate`** 를 기준으로 한다.

### 락커는 문자를 보내지 않는다

현장에서 헬스 만료는 문자를 보내지만 **락커는 대부분 구두로 전한다.**
대신 QR을 찍을 때 화면에 띄운다. → 결정 4

---

## 결정 4: 출입구 화면을 카테고리별로 분리한다

기존 `check-in` 응답의 `daysUntilExpiry`는 **가장 늦게 끝나는 회원권 기준**이라
락커가 3일 남아도 87로 표시된다.

```json
{
  "maskedName": "이*규",
  "memberships": [
    { "category": "헬스", "daysUntilExpiry": 87 },
    { "category": "락커", "daysUntilExpiry": 3 }
  ]
}
```

```
이*규 회원님 반갑습니다
헬스 87일 · 락커 3일 남았습니다
```

**회원이 직접 보게 되므로 데스크가 따로 말할 필요가 없어진다.**
마스킹된 이름이라 문 앞 화면에 떠도 지나가는 사람은 누구인지 알 수 없다.(ADR-013 결정 6)

## 결정 5: 문자 발송은 범위 밖이다

```
우리가 하는 것      "누구에게 보낼지" 목록을 뽑는다
우리가 안 하는 것    실제 발송
```

문자 발송은 외부 서비스(알리고·NHN 등) 연동이고 **비용·발신번호 사전등록·수신거부 처리**가 따라온다.
별개 문제이므로 [[향후 과제]]로 미룬다.

---

## 결과

**얻는 것**

- 클라이언트가 없어도 성립하는 설계만 남는다
- 문자 중복 발송이 구조적으로 막힌다 (정확값 필터)
- 락커 만료를 문자 없이 전달할 경로가 생긴다

**감수하는 것**

- 실시간 통지가 없다. PT 취소를 트레이너가 즉시 알 수 없다
  (현재도 카톡으로 먼저 말하므로 실질 손실은 작다)
- `Notification` 테이블이 없어 "지난 알림 보기"가 불가능하다

**미룬 것** → [[향후 과제]]

- 문자·알림톡 발송 연동
- FCM 푸시 (앱 추가 시)
- PT 예약 변경 통지

## Phase 재정의

```
Phase 5   ~~SSE 알림~~   →  회원 상태 조회·필터 + 통계
Phase 6   ~~통계~~       →  (5로 흡수)
Phase 7   배포           →  Phase 6으로 앞당김
```

알림을 빼면 남는 작업이 이슈 하나 규모라 별도 Phase로 두기 어렵다.
**배포가 프로젝트 목적 중 유일하게 경험하지 않은 영역**이므로 앞당긴다.
