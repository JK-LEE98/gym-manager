# ADR-012: 회원권 양도 설계

## 배경

**양도인**의 잔여 기간을 **양수인**에게 넘긴다.
이사·부상 등으로 실제 헬스장에서 흔히 발생한다. → [[도메인 지식#5. 양도]]

```
양도인 검색 → [회원권 양도] → 양수인 선택 → 잔여 일수 이전
```

> **용어**: 주는 쪽이 양도인, 받는 쪽이 양수인이다.
> 코드에서는 `fromUser` / `toUser` 로 표기한다.

---

## 결정 1: 원본을 종료하고 새 회원권을 만든다

### 선택지

**A. 기존 회원권의 `userId`를 양수인으로 변경**
- 레코드 하나만 수정하면 되어 간단하다
- **양도인의 이력에서 회원권이 통째로 사라진다.** 나중에 "12개월 끊었었다"고 해도 추적할 수 없다
- 결제 기록만 남아 소유자와 어긋난다

**B. 원본을 종료하고 양수인에게 새로 생성**
- 레코드가 늘어난다
- **양쪽 이력이 모두 보존된다**

### 결정: B

```
양도인   UserMembership.status = TRANSFERRED   (새 상태값)
양수인   UserMembership 신규 생성
         MembershipTransfer 이력으로 두 건을 연결
```

회원권 취소·회원권 종류 판매중지에서 일관되게 택해온
**"삭제하지 않고 상태로 남긴다"** 와 같은 맥락이다.

## 결정 2: 잔여 "일수"를 넘긴다. 날짜가 아니다

양도인의 기간(9/1~12/31)을 그대로 복사하면,
**양수인이 이미 같은 카테고리 회원권을 갖고 있을 때 기간이 겹친다.**
두 건이 동시에 활성이 되어 잔여일 계산이 무너진다.

```
잔여 일수 = 양도인 회원권의 endDate - 오늘 + 1
→ 양수인에게 새 회원권으로 부여
→ 시작일은 양수인의 이어붙이기 규칙을 그대로 적용 (ADR-010)
```

양수인이 같은 카테고리 회원권을 갖고 있으면 그 뒤에 이어지고, 없으면 오늘부터 시작한다.
**기존 규칙을 재사용하므로 예외 로직이 없다.**

## 결정 3: 홀딩은 "취소"가 아니라 "조기 종료"한다

**가장 주의가 필요한 부분이다.**

양도는 회원권 전체를 넘기는 것이므로 홀딩 상태를 유지한 채 넘길 수 없다.
그런데 **단순히 취소하면 이미 지나간 홀딩 일수가 사라져 양도인이 손해를 본다.**

### 문제

```
30일권  8/1 ~ 8/30
8/5~8/9 홀딩(5일)  →  endDate 9/4로 밀림
8/7에 양도
```

홀딩을 **취소**하면 `endDate`가 8/30으로 되돌아간다.
잔여는 8/7~8/30 = **24일**.

그러나 8/5·8/6 이틀은 실제로 홀딩이었으므로 이용하지 못한 날이다.
정확한 잔여는 **26일**이어야 한다.

### 결정

```
8/5~8/9 홀딩  →  8/5~8/6 으로 종료일 단축 (오늘 전날까지)
endDate = 8/30 + 2 = 9/1
잔여 = 8/7 ~ 9/1 = 26일 ✅
```

**이미 지나간 홀딩은 인정하고, 남은 홀딩만 걷어낸다.**

| 홀딩 상태 | 처리 |
|-----------|------|
| 예정 (아직 시작 안 함) | 취소 |
| 진행 중 | **어제까지로 종료일 단축**. 오늘 시작한 홀딩이면 취소 |
| 완료 | 그대로 둔다 (이미 반영됨) |

기존의 홀딩 수정·취소 기능을 그대로 사용하므로 종료일 전체 재계산이 자동으로 따라온다.

### 처리 순서가 중요하다

```
① 홀딩 정리 (단축 / 취소)
② endDate 재계산 → 정확한 잔여 확정
③ 잔여 일수를 양수인에게 이전
④ 원본을 TRANSFERRED로 변경
```

②를 ①보다 먼저 하면 **남은 홀딩 일수까지 넘어가 양수인이 이득을 본다.**

## 결정 4: 양도권은 홀딩할 수 없다

양도로 만들어진 회원권은 원본과 같은 `MembershipType`을 참조한다.
그대로 두면 **그 종류의 `holdingLimit`(예: 5회)이 양도권에도 적용된다.**

```
UserMembership
  + isTransferred  BOOLEAN DEFAULT false
```

홀딩 등록 시 이 값이 `true`면 거부한다.
**회원권 종류의 정책보다 우선하는 개별 제약**이다.

---

## 결정 5: 수수료는 금액을 입력받는다

헬스장마다 다르다. 가족 양도는 무료, 지인 양도는 5만원 정도 받는 곳이 있다.

```
POST /memberships/:id/transfer
{
  "toUserId": "uuid",
  "fee": 50000,        // 선택. 생략하거나 0이면 결제 기록을 만들지 않는다
  "memo": "가족 양도"
}
```

**`fee`가 0보다 클 때만 `Payment`를 생성한다.**
무료 양도에 0원짜리 결제 기록이 쌓이면 매출 통계가 지저분해진다.

> 금액을 고정하지 않는 것은 양도만의 특성이 아니다.
> 회원권 결제 전반이 그렇다. → [[도메인 지식#6. 가격은 "정가"가 아니라 "기본값 제안"이다]]

### 원본 결제는 건드리지 않는다

양도는 새로운 매출이 아니다. 양수인의 회원권에는 `paymentId`를 `null`로 두고,
원본 결제는 양도인에게 남긴다. **여기서 결제를 복제하면 같은 돈이 두 번 계상된다.**

수수료 결제가 있다면 그것만 별도 `Payment`로 기록한다.

---

## 결정 6: OWNER만 실행한다

양도는 되돌릴 수 없는 조작이고 양쪽 합의가 필요하다.
데스크에서 직원이 확인 후 처리하는 것이 자연스럽다.

회원이 앱에서 신청하고 상대가 수락하는 흐름은 상태와 알림이 늘어나
현 단계에서 얻는 것보다 복잡도가 크다.

---

## 스키마

```
UserMembership
  + isTransferred  BOOLEAN DEFAULT false      양도로 생성됨. 홀딩 불가
  status 에 TRANSFERRED 추가                   양도해서 종료된 원본

MembershipTransfer (신설)
  id                  UUID PK
  gymId               UUID FK
  fromMembershipId    UUID FK   원본 (양도인)
  toMembershipId      UUID FK   신규 (양수인)
  fromUserId          UUID FK
  toUserId            UUID FK
  transferredDays     INT       넘긴 일수
  feePaymentId        UUID FK nullable   수수료 결제. 무료면 null
  memo                TEXT nullable
  createdByUserId     UUID FK
  createdAt
```

---

## 검증

- 원본이 `ACTIVE` 상태여야 한다 (취소·이미 양도된 것은 불가)
- 잔여 일수가 1일 이상이어야 한다 (만료된 회원권은 양도 불가)
- 양도인과 양수인이 같은 헬스장 소속이어야 한다
- 양도인과 양수인이 서로 달라야 한다
- 양도권(`isTransferred = true`)의 재양도 허용 여부는 **허용한다** —
  받은 사람이 사정이 생겨 다시 넘기는 일은 충분히 발생한다
