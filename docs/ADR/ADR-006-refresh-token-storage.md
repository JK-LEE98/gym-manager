# ADR-006: Refresh Token 저장 전략

> **개정 이력**
> - 2026-07-27 최초 작성: User 테이블 컬럼에 저장
> - 2026-07-28 **개정**: RefreshToken 테이블로 분리. 다중 기기 지원 + Rotation + Reuse Detection

---

## 배경

JWT Access/Refresh Token 방식을 사용하기로 했으며, Refresh Token을 어디에 저장할지 결정해야 했다.
개발자는 이전 프로젝트에서 **DB + Redis 이중 저장 + CircuitBreaker 폴백** 구조를 사용한 경험이 있다.
배포 환경으로 AWS 프리티어 수준을 고려하고 있어 메모리 사용량도 판단 기준에 포함됐다.

최초에는 `User.refreshToken` 컬럼 방식으로 결정했으나,
**"한 기기에서만 로그인이 유지되는 문제"** 가 제기되어 재검토했다.

## 선택지

| 방식 | 앱 메모리 | 인프라 | 무효화 | 다중 기기 | 전체 로그아웃 |
|------|----------|--------|--------|----------|--------------|
| 저장 안 함 (stateless) | 0 | 불필요 | **불가** | 가능 | 불가 |
| User 테이블 컬럼 | 0 | 불필요 | 가능 | **불가** | **표현 불가** |
| **별도 RefreshToken 테이블** | 0 | 불필요 | 가능 | 가능 | 가능 |
| Redis | 컨테이너 50~100MB+ | Redis 필요 | 가능 | 가능 | 가능 |

### User 컬럼 방식이 탈락한 이유

토큰을 담을 자리가 하나뿐이라 아래 두 동작이 구분되지 않는다.

- "이 기기만 로그아웃" → 컬럼을 null로
- "모든 기기 로그아웃" → 컬럼을 null로 (동일)

비밀번호 변경 시 다른 기기 세션을 강제 종료하는 것은 인증의 기본 동작인데,
이를 표현할 수 없다. 또한 Reuse Detection에 필요한 "폐기 이력"을 기억할 자리가 없다.

### Redis가 탈락한 이유

Redis의 이점은 초당 수천 건 이상의 세션 조회에서 발생한다.
본 서비스의 로그인 빈도는 헬스장당 하루 수십~수백 건 수준이므로 이점이 없고,
별도 컨테이너로 인한 메모리/비용 부담만 발생한다.
DB + Redis + CircuitBreaker 구조는 현 단계에서 명백한 오버엔지니어링이다.

## 결정

**별도 `RefreshToken` 테이블 + Rotation + Reuse Detection**

### 토큰 유효기간

| 토큰 | 유효기간 | 근거 |
|------|---------|------|
| Access Token | **1시간** | 갱신 요청 빈도와 탈취 시 노출 시간의 균형. Firebase ID Token과 동일한 값 |
| Refresh Token | **30일** | 월 1회 재로그인. Rotation으로 실제 개별 토큰 수명은 1시간 수준 |

> Access Token은 stateless라 발급 후 만료까지 **무효화가 불가능**하다.
> 로그아웃, 계정 정지, 비밀번호 변경 모두 이미 발급된 Access Token을 막지 못한다.
> 따라서 "재로그인 빈도를 줄이고 싶다"는 요구는 Access가 아니라 **Refresh 기간을 늘려** 해결한다.

### 토큰 해싱 — SHA-256 (bcrypt 아님)

| | bcrypt | SHA-256 |
|---|--------|---------|
| 조회 | 인덱스 불가. userId로 후보를 모두 가져와 순회 비교 | **해시값으로 단일 조회** |
| 속도 | 의도적으로 느림 | 빠름 |
| 적합 대상 | 저엔트로피 비밀번호 | **고엔트로피 랜덤 토큰** |

bcrypt의 느린 해싱은 **사람이 만든 비밀번호가 무차별 대입에 취약**하기 때문에 필요한 것이다.
Refresh Token은 서버가 생성한 고엔트로피 문자열이라 무차별 대입 자체가 불가능하므로
느린 해싱이 이점을 주지 않는다.

SHA-256은 결정적(deterministic)이라 **컬럼에 인덱스를 걸어 단일 쿼리로 조회**할 수 있다.
코드도 더 단순해진다.

> 단, **비밀번호는 반드시 bcrypt를 유지**한다. 용도가 다르다.

## Rotation

갱신 요청마다 기존 토큰을 폐기하고 새 토큰 쌍을 발급한다.

```
POST /auth/refresh
  1. 제출된 토큰의 해시로 RefreshToken 조회
  2. revokedAt이 null이고 만료되지 않았는지 확인
  3. 기존 row의 revokedAt = now  (삭제하지 않고 폐기 표시)
  4. 새 RefreshToken row 생성 + 새 Access Token 발급
```

30일짜리 토큰이 30일 내내 같은 값으로 존재하는 것이 아니라,
갱신할 때마다 값이 바뀐다. 개별 토큰의 실제 수명은 갱신 주기(약 1시간) 수준이다.

## Reuse Detection

폐기된(`revokedAt != null`) 토큰이 다시 제출되면 **탈취로 간주**한다.

```
공격자가 토큰 탈취 → 갱신 성공 → 새 토큰 획득 (기존 토큰은 revoked)
정상 사용자가 갱신 시도 → revoked된 토큰 제출 → 이상 감지
  → 해당 userId의 모든 RefreshToken을 revoke → 양쪽 모두 로그아웃
  → 정상 사용자는 재로그인, 공격자는 접근 차단
```

이 동작을 위해 폐기된 row를 **즉시 삭제하지 않고 `revokedAt`으로 표시만** 한다.
삭제해버리면 "정상 만료된 토큰"과 "재사용 공격"을 구분할 수 없다.

## 결과

- `User.refreshToken` 컬럼 제거, `RefreshToken` 테이블 신설
- 로그인 시 해당 유저의 **만료된 row를 함께 정리** (별도 배치 불필요)
- `.env` 변경: `JWT_ACCESS_EXPIRES_IN=1h`, `JWT_REFRESH_EXPIRES_IN=30d`
- **면접 포인트**: "Refresh Token 30일이라는 긴 만료 기간의 위험을 Rotation과 Reuse Detection으로 상쇄했습니다"

## 알려진 한계

- row가 누적된다. 로그인 시 만료분을 정리하지만, 로그인이 없는 유저의 row는 남는다.
  → 규모가 커지면 주기적 정리 배치 추가 검토
- Access Token 1시간은 로그아웃 후에도 최대 1시간 유효하다.
  즉시 무효화가 필요해지면 토큰 블랙리스트가 필요하나, 현 단계에서는 과도하다.
