# ADR-008: 사용자 열거(User Enumeration) 대응 범위

> **개정 이력**
> - 2026-07-29 최초 작성: 이메일 기준
> - 2026-07-29 **개정**: 로그인 식별자가 `loginId`로 변경됨에 따라 위협 평가 수정 → ADR-009

---

## 배경

인증 관련 에러 메시지가 계정 존재 여부를 노출할 수 있다는 문제를 검토했다.

- **로그인**: "존재하지 않는 아이디" / "비밀번호 불일치"를 구분하면 가입 여부가 드러난다
- **회원가입**: "이미 사용 중인 아이디입니다"도 동일한 정보를 노출한다

## 위협 모델

| 항목 | 내용 |
|------|------|
| 공격자 | 외부 익명 사용자 |
| 목적 | 서비스에 가입된 계정 식별자 목록 확보 |
| 활용 | 크리덴셜 스터핑, 표적 공격, 특정 인물의 가입 여부 확인 |
| 비용 | 낮음. 후보 문자열 대입만 하면 됨 |

### 식별자가 아이디로 바뀌면서 위협이 낮아졌다

[[ADR-009-login-identifier|ADR-009]]에서 로그인 식별자를 `email`에서 `loginId`로 변경했다.
이는 열거 위험 자체를 상당히 완화한다.

| | 이메일 노출 시 | 아이디 노출 시 |
|---|---|---|
| 크리덴셜 스터핑 | 외부 유출 목록과 **대조 가능** | 대조 불가 |
| 피싱 | 직접 발송 **가능** | 발송 경로 없음 |
| 프라이버시 | 개인 식별 가능 | 서비스 내부 식별자에 그침 |

이메일은 서비스 간 공통 식별자라 한 곳에서 새면 다른 서비스 공격에 재활용된다.
아이디는 이 서비스 안에서만 의미를 가지므로 **유출 시 파급이 닫혀 있다.**

### 그럼에도 남는 위험

- `loginId`가 **전역 유니크**이고 `GET /gyms/public`이 공개이므로,
  유효한 `gymId` 하나만 얻으면 전체 아이디 공간을 탐색할 수 있다
- 사람들이 아이디를 다른 서비스와 동일하게 쓰는 경향이 있어 완전히 무해하지는 않다

## 완화 수단 평가

효과 순으로 정렬했다.

| 수단 | 효과 | 비용 | 채택 |
|------|:---:|:---:|:---:|
| ① Rate Limiting | **큼** — 대량 시도 자체를 차단 | 낮음 | ✅ |
| ② 식별자를 이메일 → 아이디로 | **큼** — 유출 시 파급을 닫음 | 없음 | ✅ (ADR-009) |
| ③ 메시지 뭉개기 | 작음 — 문구만 가림 | UX 손실 | 로그인만 |

**③이 단독으로는 효과가 약한 이유**

메시지를 통일해도 아래로 여전히 추론 가능하다.

- HTTP 상태 코드 차이 (409 vs 201)
- 응답 시간 차이 (DB 조회·해싱 유무)
- 후속 플로우 차이

①을 적용하지 않고 ③만 하면 UX만 잃고 보안은 확보하지 못한다.

## 결정

### 로그인 — 메시지 통일 + 타이밍 보정

```
❌ "존재하지 않는 아이디입니다" / "비밀번호가 올바르지 않습니다"
✅ "아이디 또는 비밀번호가 올바르지 않습니다"   errorCode: INVALID_CREDENTIALS
```

메시지 통일의 UX 비용이 사실상 0이며 업계 표준 문구가 정착되어 있다.

**타이밍 공격 대응**: 유저를 찾지 못한 경우에도 **더미 해시와 bcrypt 비교를 수행**해
응답 시간을 맞춘다. 즉시 반환하면 해싱 소요 시간(수십~수백 ms) 차이로 존재 여부가 드러난다.

```typescript
const user = await this.userRepo.findOne(...);
// 유저가 없어도 해싱 비용을 발생시켜 응답 시간을 맞춘다
const hash = user?.password ?? DUMMY_HASH;
const isValid = await bcrypt.compare(password, hash);
if (!user || !isValid) throw new BusinessException(ErrorCode.INVALID_CREDENTIALS);
```

### 회원가입 — 명확한 메시지 유지 (의도적 선택)

```
"이미 사용 중인 아이디입니다"   errorCode: DUPLICATE_LOGIN_ID
```

**이유**

- 아이디 중복을 감추면 사용자가 가입 실패 원인을 알 수 없어 UX 손실이 즉각적이다
- **아이디는 이메일과 달리 노출 시 파급이 닫혀 있다** (위 표 참고)
- Rate Limiting을 함께 적용하므로 대량 열거는 차단된다
- 메시지 문구는 되돌리기 비용이 매우 낮은 결정이다 (한 줄 수정)

### 아이디 중복확인 API — 두지 않는다

`GET /auth/check-id?loginId=xxx` 같은 별도 엔드포인트는 만들지 않는다.
**열거를 기능으로 제공하는 셈**이 되고, 가입 시 검사만으로도 목적은 달성되기 때문이다.

국내 서비스 다수가 제공하는 UX이긴 하나, 엔드포인트를 줄이는 편이 공격 표면 관리에 유리하다.
프론트엔드가 필요로 하면 그때 Rate Limiting을 강하게 걸어 추가한다.

### Rate Limiting — feat/auth에 포함

`@nestjs/throttler`로 인증 엔드포인트에 적용한다. Spring의 Bucket4j에 해당한다.

## 결과

- 로그인 실패는 원인과 무관하게 `INVALID_CREDENTIALS` 단일 코드
- 로그인 시 유저 미존재에도 더미 해시 비교 수행
- 회원가입 중복은 `DUPLICATE_LOGIN_ID`로 명확히 안내
- 중복확인 전용 엔드포인트 없음
- 인증 엔드포인트에 Rate Limiting 적용

## 면접 서술

> "인증 에러 메시지의 사용자 열거 위험을 검토했습니다.
> 완화 수단을 효과 순으로 평가한 결과 메시지 뭉개기는 상태 코드와 응답 시간으로
> 우회 가능해 단독 효과가 약하다고 판단했습니다.
> 대신 로그인 식별자를 이메일에서 아이디로 바꿔 유출 시 파급 범위를 서비스 내부로 닫고,
> Rate Limiting을 적용했습니다.
> 로그인은 비용이 없으므로 메시지를 통일하고 더미 해시 비교로 타이밍까지 보정했으며,
> 회원가입은 UX 손실이 커서 명확한 안내를 유지했습니다."
