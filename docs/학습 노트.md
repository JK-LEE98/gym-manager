## 1. 개발 도구

### jq — 커맨드라인 JSON 뷰어

TypeScript도 Node도 아니고, **JSON을 다루는 독립 CLI 도구**다. 다른 언어 환경에서도 똑같이 쓴다.

`curl`은 응답을 한 줄로 뱉는다. 사람이 읽기 힘들다.

```bash
$ curl -s http://localhost:3000
{"success":true,"data":"Hello World!","message":"요청이 처리되었습니다"}
```

`jq`에 파이프로 넘기면 들여쓰기 + 색상으로 정리해준다.

```bash
$ curl -s http://localhost:3000 | jq
{
  "success": true,
  "data": "Hello World!",
  "message": "요청이 처리되었습니다"
}
```

**설치**
```bash
brew install jq
```

**자주 쓰는 형태**

```bash
# 전체 예쁘게 출력 (.는 "전체"를 뜻함)
curl -s localhost:3000 | jq

# 특정 필드만 꺼내기
curl -s localhost:3000/users/me | jq '.data.loginId'

# 배열에서 필드만 뽑기
curl -s localhost:3000/users | jq '.data.items[].name'

# 조건 필터
curl -s localhost:3000/users | jq '.data.items[] | select(.role == "TRAINER")'
```

> `curl -s`의 `-s`는 silent. 진행률 표시를 끄는 옵션이다. 이게 없으면 진행률 텍스트가
> JSON에 섞여서 jq가 파싱에 실패한다.

API를 직접 호출하며 테스트할 일이 많아지므로 익혀두면 Postman 없이도 대부분 해결된다.

**토큰을 변수로 받으면 복붙 실수가 없다**

```bash
R1=$(curl -s -X POST localhost:3000/auth/login -H "Content-Type: application/json" \
  -d '{"loginId":"hong_gd","password":"password1234"}' | jq -r '.data.refreshToken')

curl -s -X POST localhost:3000/auth/refresh -H "Content-Type: application/json" \
  -d "{\"refreshToken\":\"$R1\"}" | jq -r '.errorCode'
```

`jq -r`의 `-r`은 raw output. 따옴표 없이 값만 뽑아 변수에 담을 수 있다.

### 검증 루프 — 기능 개발 후 매번 돌리는 것

```bash
npm run lint          # 자동 수정 (포맷 정리)
npm run lint:ci       # 검증만 (0 problems 여야 함)
npm run build         # 타입 검사 + 컴파일
npm test              # 단위 테스트
npm run test:e2e      # E2E 테스트 (테스트 DB 필요)
```

**CI가 PR마다 실행하는 것과 같은 명령이다.** 로컬에서 통과하면 CI도 통과한다.

#### lint가 뭔가

**코드를 실행하지 않고 정적으로 분석해 문제를 찾는 도구**다.
Java의 Checkstyle·SpotBugs·SonarLint에 해당한다.

우리 설정에는 성격이 다른 두 가지가 섞여 있다.

| | 도구 | 잡는 것 |
|---|------|--------|
| **코드 품질** | ESLint (typescript-eslint) | 위험하거나 실수하기 쉬운 패턴 |
| **포맷** | Prettier | 들여쓰기, 줄바꿈, 따옴표 |

`eslint-plugin-prettier`로 둘을 합쳐 한 명령으로 실행한다.

#### 컴파일과 뭐가 다른가

**컴파일은 "돌아가는가"를 보고, lint는 "안전한가·읽기 좋은가"를 본다.**

실제로 우리가 lint로 잡은 것들이다.

```typescript
// 컴파일은 통과하지만 위험한 코드

bootstrap();                    // no-floating-promises
// Promise를 아무도 기다리지 않는다. 실패해도 조용히 넘어간다

gyms.map(GymResponseDto.from);  // unbound-method
// 정적 메서드를 참조로 넘기면 this 바인딩이 끊길 수 있다

status >= HttpStatus.OK         // no-unsafe-enum-comparison
// number와 enum을 섞어 비교한다
```

셋 다 타입 오류가 아니라 **컴파일러는 통과시키는 코드**다.

#### `lint`와 `lint:ci`가 왜 둘인가

```json
"lint":    "eslint ... --fix",              // 자동 수정
"lint:ci": "eslint ... --max-warnings 0",   // 검증만
```

CI에서 `--fix`를 쓰면 **에러를 고쳐놓고 통과**시킨다. 검증이 아니라 수정이 되어버린다.
CI용은 고치지 않고 하나라도 있으면 실패한다.

`--max-warnings 0`은 경고도 실패로 취급한다. **경고를 허용하면 쌓이기만 하기 때문이다.**

> `--fix`는 규칙 단위로 판단하지 전체 맥락을 보지 않는다.
> 실제로 `--fix`가 필요한 타입 단언을 "불필요하다"며 지워 옆 줄이 깨진 적이 있다.
> **`--fix` 후에는 반드시 `lint:ci`로 다시 검사한다.**

#### 각 명령이 잡는 것

| 명령 | 잡는 것 | 못 잡는 것 |
|------|--------|-----------|
| `lint:ci` | 위험한 패턴, 포맷 | 동작 오류 |
| `build` | 타입 오류 | 런타임 동작 |
| `test` | 순수 로직 | DB·HTTP가 얽힌 흐름 |
| `test:e2e` | 실제 요청→응답 전체 | 실제 부하·동시성 |

**층층이 쌓아 서로가 못 잡는 것을 메운다.**
실제로 `lint`가 잡은 것, `build`가 잡은 것, `test:e2e`가 잡은 것이 모두 달랐다.

### 디버깅 체크리스트 — "서버가 도는데 왜 안 되지"

여러 번 겪은 패턴이다. **서버가 살아있다는 것과 최신 코드가 돈다는 것은 다르다.**

| 증상 | 먼저 볼 것 | 실제 원인 사례 |
|------|-----------|--------------|
| `404 Cannot POST /...` | 컴파일 로그 | 패키지 미설치로 빌드 실패 → watch가 옛 빌드를 계속 서빙 |
| `EADDRINUSE :::3000` | `lsof -i :3000` | 터미널 두 개에서 서버를 중복 실행 |
| DB 연결 실패 | `lsof -i :5432` | 로컬 PostgreSQL이 포트를 선점 → Docker가 아닌 로컬에 접속 |
| 스키마가 그대로 | `\d 테이블명` | `synchronize`가 컬럼 삭제를 건너뜀 |

**공통 교훈**: 프로세스가 떠 있다는 사실만으로 판단하지 않는다.
포트를 누가 잡고 있는지, 마지막 빌드가 성공했는지를 먼저 확인한다.

NestJS는 부팅 시 등록된 라우트를 전부 출력하므로, 이게 가장 빠른 확인 수단이다.

```
[RouterExplorer] Mapped {/auth/signup, POST} route
[RouterExplorer] Mapped {/auth/login, POST} route
```

## 2. TypeScript 타입 시스템

> Java에 없는 개념이 많다. 이 절의 내용은 대부분 **"값 자체가 타입이 될 수 있다"** 는
> TypeScript의 특징에서 파생된다.

### 2-1. 유니온 타입 (Union Type)

`A | B` — "A이거나 B다". Java에는 대응하는 문법이 없다.

```typescript
let phone: string | null;   // 문자열이거나 null
let id: string | number;    // 문자열이거나 숫자
```

Java라면 `Object`로 받고 `instanceof`로 분기하거나, 아예 오버로딩으로 나눠야 한다.
TypeScript는 타입 자체로 "둘 중 하나"를 표현한다.

우리 프로젝트에서는 Entity의 nullable 컬럼에 쓰고 있다.

```typescript
@Column({ type: 'varchar', length: 20, nullable: true })
phone: string | null;
```

> 이 선언이 [[트러블슈팅#003|트러블슈팅 003]]의 원인이었다.
> 유니온 타입은 런타임 메타데이터에 `Object`로 기록되어 TypeORM이 컬럼 타입을 추론하지 못한다.
> 그래서 `type: 'varchar'`를 명시해야 했다.

### 2-2. 리터럴 타입 (Literal Type)

**특정 값 하나만 허용하는 타입.** 값이 곧 타입이 된다.

```typescript
let a: true = true;      // true만 가능. a = false 는 컴파일 에러
let s: 'ACTIVE' = 'ACTIVE';  // 'ACTIVE'라는 문자열만 가능
```

리터럴 타입을 유니온으로 묶으면 Java의 enum과 비슷한 역할을 한다.

```typescript
type Status = 'ACTIVE' | 'EXPIRED' | 'SUSPENDED';

let s: Status = 'ACTIVE';   // OK
let t: Status = 'DELETED';  // 컴파일 에러
```

```java
// Java라면
enum Status { ACTIVE, EXPIRED, SUSPENDED }
```

차이점은 TypeScript 쪽은 **런타임에 그냥 문자열**이라는 것이다.
enum 객체가 따로 생기지 않아 JSON 직렬화나 DB 저장이 자연스럽다.

> 다만 우리 프로젝트는 Role, Status 등에 TypeScript의 `enum` 키워드를 쓰고 있다.
> TypeORM의 `@Column({ type: 'enum', enum: Role })`이 enum 객체를 요구하기 때문이다.

### 2-3. 타입 넓히기 (Widening)

TypeScript는 값에서 타입을 추론할 때 **리터럴을 일반 타입으로 넓힌다.**
이게 `as const`가 필요한 이유의 핵심이다.

```typescript
const a = true;   // 타입: true      (const는 재할당 불가라 안 넓힘)
let  b = true;    // 타입: boolean   (재할당 가능하니 넓힘)
```

문제는 **객체 프로퍼티는 const여도 넓혀진다**는 점이다.

```typescript
const obj = { success: true };
//    타입: { success: boolean }   ← true가 아니라 boolean!
```

`obj.success = false`가 가능하기 때문에 TypeScript가 안전하게 넓혀버린 것이다.

### 2-4. `as const`

**"넓히지 말고 리터럴 그대로 둬라"** 는 지시다.

```typescript
const obj1 = { success: true };
//    { success: boolean }

const obj2 = { success: true as const };
//    { success: true }              ← 해당 프로퍼티만 고정

const obj3 = { success: true } as const;
//    { readonly success: true }     ← 전체를 readonly + 리터럴로 고정
```

### 2-5. 판별 유니온 (Discriminated Union)

여기까지가 모여 실제로 쓰이는 지점이다.

**공통 필드의 리터럴 값으로 어느 쪽인지 구분하는 유니온**을 판별 유니온이라 한다.
우리 프로젝트의 API 응답 타입이 정확히 이 구조다.

```typescript
// src/common/interfaces/api-response.interface.ts
export interface ApiSuccessResponse<T> {
  success: true;      // ← 리터럴 타입. boolean이 아님
  data: T;
  message: string;
}

export interface ApiErrorResponse {
  success: false;     // ← 리터럴 타입
  data: null;
  message: string;
  errorCode: ErrorCode;
}

export type ApiResponse<T> = ApiSuccessResponse<T> | ApiErrorResponse;
```

**무엇이 좋은가**: `if` 하나로 타입이 자동으로 좁혀진다(narrowing).

```typescript
function handle(res: ApiResponse<User>) {
  if (res.success) {
    res.data.loginId;    // TS가 ApiSuccessResponse로 확정. data 접근 OK
    res.errorCode;     // 컴파일 에러 — 성공 응답엔 없는 필드
  } else {
    res.errorCode;     // TS가 ApiErrorResponse로 확정. OK
    res.data.loginId;    // 컴파일 에러 — data가 null이므로
  }
}
```

`success`가 `boolean`이면 이 좁히기가 동작하지 않는다.
`true`와 `false`라는 **리터럴**이어야 TypeScript가 두 인터페이스를 구별할 수 있다.

### 2-6. 그래서 `as const`가 왜 필요했나

Interceptor에서 성공 응답을 만드는 코드다.

```typescript
// src/common/interceptors/transform.interceptor.ts
return next.handle().pipe(
  map((data) => ({
    success: true as const,   // ← 이것
    data,
    message,
  })),
);
```

`as const`가 없으면 이렇게 된다.

```typescript
{ success: true, data, message }
// 추론된 타입: { success: boolean; data: T; message: string }
```

그런데 이 함수의 반환 타입은 `Observable<ApiSuccessResponse<T>>`로 선언되어 있고,
`ApiSuccessResponse`의 `success`는 `true` 리터럴이다.

```
할당하려는 것:  { success: boolean }
받아야 하는 것: { success: true }
```

`boolean`은 `true`보다 넓으므로 **할당할 수 없다.** 컴파일 에러가 난다.
`as const`로 리터럴을 유지해야 타입이 맞는다.

> **한 줄 요약**: 판별 유니온을 쓰려면 판별 필드가 리터럴 타입이어야 하고,
> 객체 리터럴은 기본적으로 넓혀지므로 `as const`로 막아야 한다.

### 2-7. 템플릿 리터럴 타입 (Template Literal Type)

**문자열의 "형태"를 타입으로 표현한다.** Java에는 없는 개념이다.

```typescript
type Duration = `${number}h` | `${number}d` | `${number}m`;

let a: Duration = '1h';    // OK
let b: Duration = '30d';   // OK
let c: Duration = '바나나'; // 컴파일 에러
```

[[#2-2. 리터럴 타입 (Literal Type)|리터럴 타입]]이 값 하나를 고정한다면,
템플릿 리터럴 타입은 **패턴을 고정한다.** 조합 가능한 값이 무한해도 형태로 제약할 수 있다.

#### 실제로 겪은 사례 — JwtModule의 expiresIn

```typescript
signOptions: {
  expiresIn: config.getOrThrow<string>('JWT_ACCESS_EXPIRES_IN'),
}
```

```
Type 'string' is not assignable to type 'number | StringValue | undefined'.
```

`ms` 패키지가 `expiresIn`을 `"1h"`, `"30d"` 형태만 받도록 템플릿 리터럴 타입으로 좁혀놓았기 때문이다.
`ConfigService`는 `.env`에서 읽은 임의의 `string`을 반환하므로 할당되지 않는다.
TypeScript 입장에서는 `"바나나"`가 들어올 수도 있는 값이다.

**해결** — 라이브러리 내부 타입을 몰라도 되도록 기대 타입을 인덱스로 가져온다.

```typescript
const toExpiresIn = (value: string): JwtSignOptions['expiresIn'] =>
  value as JwtSignOptions['expiresIn'];
```

`JwtSignOptions['expiresIn']`은 **인덱스 접근 타입**으로,
해당 프로퍼티의 타입을 그대로 꺼내온다. 라이브러리가 타입을 바꿔도 자동으로 따라간다.

#### 단언(assertion)의 한계

`as`는 **"내가 보증한다"는 선언일 뿐 검증이 아니다.**

```
.env에 JWT_ACCESS_EXPIRES_IN=바나나  →  컴파일 통과, 런타임에 실패
```

`getOrThrow`는 "값이 존재하는지"만 보장하고 "형식이 맞는지"는 보지 않는다.

제대로 하려면 앱 시작 시 환경변수를 스키마로 검증해야 한다.
`ConfigModule`의 `validationSchema`(Joi)를 쓰며,
Spring의 `@ConfigurationProperties` + `@Validated`에 해당한다. → 향후 과제

> **교훈**: `as`가 나오면 "여기서 타입 시스템이 보장을 포기했다"는 신호다.
> 정말 안전한지, 아니면 런타임 검증이 필요한지 한 번 생각해볼 지점이다.

### 2-8. 데코레이터와 런타임 메타데이터

`@Injectable()`, `@Column()`처럼 `@`로 시작하는 문법이다. Java 어노테이션과 겉모습이 같다.

**결정적인 차이**: Java 어노테이션은 순수한 메타데이터 표식이고 스스로 아무것도 하지 않는다.
TypeScript 데코레이터는 **실제로 실행되는 함수**다. 클래스나 프로퍼티를 직접 수정할 수도 있다.

```typescript
// 데코레이터는 결국 함수다
function Log(target: any, key: string) {
  console.log(`${key} 프로퍼티가 선언됨`);   // 클래스 로딩 시점에 실행
}

class User {
  @Log
  name: string;
}
```

`tsconfig.json`에서 두 옵션으로 활성화된다.

```json
"experimentalDecorators": true,    // 데코레이터 문법 허용
"emitDecoratorMetadata": true      // 타입 정보를 런타임에 남김
```

#### emitDecoratorMetadata — 왜 중요한가

TypeScript의 타입은 **컴파일되면 대부분 사라진다.** JavaScript에는 타입이 없기 때문이다.

```typescript
// 컴파일 전
name: string;

// 컴파일 후 — 타입이 흔적도 없다
name;
```

그런데 TypeORM이나 NestJS는 **런타임에** 타입을 알아야 한다.
"이 프로퍼티가 string이니 varchar 컬럼으로 만들자" 같은 판단을 실행 시점에 해야 하니까.

`emitDecoratorMetadata`는 데코레이터가 붙은 곳에 한해 타입 정보를 `design:type` 메타데이터로 남겨준다.

```typescript
@Column()
name: string;
// → design:type = String 이 런타임에 조회 가능
```

**여기에 한계가 있다.** 이 메타데이터는 생성자 함수 하나만 담을 수 있어서
유니온 타입처럼 복잡한 타입은 표현하지 못한다.

```typescript
name: string;          // design:type = String   ✅
name: string | null;   // design:type = Object   ❌ 정보 손실
```

이것이 [[트러블슈팅#003|트러블슈팅 003]]의 근본 원인이었다.
그래서 nullable 컬럼에는 `type`을 명시해 추론에 의존하지 않게 한 것이다.

> **정리**: TypeScript 타입은 컴파일 후 사라진다.
> 런타임 리플렉션에 의존하는 라이브러리(TypeORM, class-validator, NestJS DI)를 쓸 때는
> "이 정보가 런타임까지 살아남는가"를 항상 의식해야 한다.

#### `isolatedModules` — 타입인지 값인지 알려줘야 할 때

데코레이터가 붙은 시그니처에 인터페이스를 쓰면 이런 에러가 난다.

```
TS1272: A type referenced in a decorated signature must be imported with
'import type' or a namespace import when 'isolatedModules' and
'emitDecoratorMetadata' are enabled.
```

```typescript
import { JwtPayload } from './interfaces/jwt-payload.interface';

@Get('me')
me(@CurrentUser() user: JwtPayload) { ... }   // ❌
```

**원인**: `isolatedModules`는 파일을 **하나씩 독립적으로** 컴파일한다.
다른 파일을 들여다보지 않으므로 `JwtPayload`가 인터페이스(타입)인지 클래스(값)인지 알 수 없다.

그런데 `emitDecoratorMetadata`는 데코레이터가 붙은 자리에 **런타임 참조를 남기려 한다.**
`JwtPayload`가 인터페이스라면 런타임에 존재하지 않으므로 참조가 깨진다.
컴파일러는 판단할 수 없으니 개발자에게 명시하라고 요구한다.

**해결 두 가지**

```typescript
// 1. import type — "이건 타입이니 런타임에 참조하지 마라"
import type { JwtPayload } from './interfaces/jwt-payload.interface';

// 2. 애초에 데코레이터 시그니처에서 빼기 (더 나은 설계였다)
me(@CurrentUser('sub') userId: string) { ... }
```

우리는 2번을 택했다. `/auth/me`는 토큰에 없는 `name`·`loginId`까지 반환해야 해서
어차피 DB 조회가 필요했고, 그러면 `sub`(userId)만 받으면 충분했다.

> **교훈**: 타입 에러가 설계 문제를 드러내는 경우가 있다.
> 우회하기 전에 "애초에 이 타입이 여기 필요한가"를 한 번 묻는다.

## 3. NestJS 구조

### 3-1. DTO와 검증

**DTO(Data Transfer Object)** 는 요청·응답의 데이터 형태를 정의하는 객체다. Spring에서 쓰던 것과 같은 개념이다.

#### interface가 아니라 class여야 한다

TypeScript에는 `interface`가 있는데, DTO에는 쓸 수 없다.

```typescript
// ❌ 동작하지 않는다
export interface SignupDto {
  email: string;
}

// ✅
export class SignupDto {
  @IsEmail()
  email: string;
}
```

이유는 [[#2-8. 데코레이터와 런타임 메타데이터|2-8]]과 같다.
**`interface`는 컴파일되면 사라지고 `class`는 남는다.**

```typescript
// interface → 컴파일 후 아무것도 남지 않음
// class     → 컴파일 후 JavaScript 클래스로 남음
```

`ValidationPipe`는 런타임에 "이 요청 본문을 어떤 규칙으로 검증할지" 알아내야 하는데,
`interface`는 그 시점에 존재하지 않으므로 검증할 대상이 없다.

Java는 인터페이스도 클래스처럼 런타임에 존재하므로 겪지 않는 문제다.

#### class-validator 데코레이터

검증 규칙을 프로퍼티에 선언한다. Spring의 Bean Validation(`@NotNull`, `@Email`)과 같은 역할이다.

```typescript
export class SignupDto {
  /** 로그인에 사용할 이메일 */
  @IsEmail()
  email: string;

  /** 최소 8자 */
  @IsString()
  @MinLength(8)
  password: string;

  @IsOptional()
  @IsString()
  phone?: string;
}
```

| Spring | class-validator |
|---|---|
| `@NotNull` / `@NotBlank` | `@IsNotEmpty()` |
| `@Email` | `@IsEmail()` |
| `@Size(min=8)` | `@MinLength(8)` |
| `@Min` / `@Max` | `@Min()` / `@Max()` |
| (필수 아님) | `@IsOptional()` |

#### ValidationPipe 전역 설정

`main.ts`에서 한 번 등록하면 모든 컨트롤러에 적용된다. Spring의 `@Valid`를 매번 붙이지 않아도 되는 셈이다.

```typescript
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,
    forbidNonWhitelisted: true,
    transform: true,
  }),
);
```

| 옵션 | 동작 | 왜 켜는가 |
|------|------|----------|
| `whitelist` | DTO에 없는 필드를 **제거** | 클라이언트가 `{ role: 'OWNER' }`를 몰래 끼워넣어도 무시된다 |
| `forbidNonWhitelisted` | DTO에 없는 필드가 오면 **400 에러** | 조용히 지우는 대신 명시적으로 거부. 오타도 잡힌다 |
| `transform` | 요청 데이터를 DTO 타입으로 **변환** | 쿼리스트링의 `"1"`을 `number 1`로 바꿔준다 |

`whitelist`가 특히 중요하다. 이게 없으면 **권한 상승 공격**이 가능하다.
회원가입 요청에 `role: 'OWNER'`를 끼워 넣었을 때 그대로 저장되면 끝이다.

> 우리 프로젝트는 여기에 더해 **`gymId`·`userId`를 클라이언트에서 받지 않고
> 토큰에서만 추출**하는 규칙을 둔다. → CLAUDE.md 보안 컨벤션

### 3-2. Interceptor — 응답 가공

Spring의 `ResponseBodyAdvice`에 해당한다.
Controller가 순수 데이터를 반환하면 Interceptor가 공통 포맷으로 감싼다.

```typescript
// Controller는 이것만 반환
return user;

// 클라이언트가 받는 것
{ "success": true, "data": { ... }, "message": "요청이 처리되었습니다" }
```

컨트롤러마다 손으로 감싸면 반드시 빠뜨리는 곳이 생기므로 한 곳에서 일괄 처리한다.

### 3-3. Reflector와 커스텀 데코레이터

Interceptor는 어느 컨트롤러가 호출됐는지는 알아도 **그 컨트롤러가 무슨 일을 하는지는 모른다.**
그래서 응답 메시지를 다르게 주려면 핸들러에 메타데이터를 남겨야 한다.

```typescript
// 1. 데코레이터로 메타데이터를 심는다
export const ResponseMessage = (message: string) =>
  SetMetadata(RESPONSE_MESSAGE_KEY, message);

// 2. 컨트롤러에 붙인다
@Post('signup')
@ResponseMessage('회원가입이 완료되었습니다')
async signup() { ... }

// 3. Interceptor가 Reflector로 꺼낸다
const message = this.reflector.get<string>(RESPONSE_MESSAGE_KEY, context.getHandler());
```

Spring에서 `HandlerMethod`로부터 커스텀 어노테이션을 꺼내 쓰는 것과 같은 원리다.

### 3-4. Exception Filter — 전역 예외 처리

Spring의 `@RestControllerAdvice`에 해당한다.

```typescript
@Catch()   // 인자 없이 쓰면 모든 예외를 잡는다
export class AllExceptionsFilter implements ExceptionFilter { ... }
```

우리 필터는 예외를 3종류로 나눠 처리한다.

| 종류 | 처리 |
|------|------|
| `BusinessException` (직접 정의) | errorCode·status·message를 그대로 사용 |
| `HttpException` (NestJS 내장) | 상태 코드로 errorCode 추론 |
| 그 외 모든 것 | 500 + 고정 문구. 원본은 로그에만 |

세 번째가 보안상 중요하다. → [[#5-4. 내부 구현 노출 방지]]

### 3-5. Swagger 자동 문서화

Spring의 Springdoc에 해당한다. `main.ts`에서 설정하면 `/api-docs`에 문서가 뜬다.

```typescript
const config = new DocumentBuilder()
  .setTitle('Gym Manager API')
  .addBearerAuth()          // JWT 입력란 추가
  .build();
SwaggerModule.setup('api-docs', app, SwaggerModule.createDocument(app, config));
```

#### CLI 플러그인 — 보일러플레이트 제거

기본 상태에서는 DTO의 모든 필드에 `@ApiProperty`를 손으로 붙여야 한다.

```typescript
// 플러그인 없이
export class SignupDto {
  @ApiProperty({ type: String, description: '이메일', required: true })
  @IsEmail()
  email: string;

  @ApiProperty({ type: String, minLength: 8, required: true })
  @MinLength(8)
  password: string;
}
```

`nest-cli.json`에 플러그인을 등록하면 컴파일 시점에 자동 생성된다.

```json
"compilerOptions": {
  "plugins": [
    { "name": "@nestjs/swagger", "options": { "introspectComments": true } }
  ]
}
```

```typescript
// 플러그인 활성화 후 — 같은 문서가 생성된다
export class SignupDto {
  /** 로그인에 사용할 이메일 */
  @IsEmail()
  email: string;

  /** 최소 8자 */
  @MinLength(8)
  password: string;
}
```

플러그인이 읽는 것

| 소스 | Swagger 스키마 |
|------|---------------|
| TypeScript 타입 `string` | `type: 'string'` |
| `?` 또는 `@IsOptional()` | `required: false` |
| `@MinLength(8)` | `minLength: 8` |
| JSDoc 주석 (`introspectComments`) | `description` |

#### introspectComments를 켠 이유

JSDoc 주석 하나가 **Swagger 설명**과 **에디터 자동완성 툴팁** 양쪽에 쓰인다.
`@ApiProperty({ description })`를 따로 쓰면 같은 문장을 두 곳에 적게 되고,
결국 한쪽만 고쳐져 어긋난다. → ADR-007에서 정리한 중복 문제와 같은 구조다.

#### 왜 DTO를 쓰기 전에 켰나

나중에 켜면 이미 손으로 작성한 `@ApiProperty`를 전부 걷어내야 한다.
빌드 설정이므로 **`nest-cli.json` 변경 후에는 watch 모드를 껐다 켜야** 반영된다.

#### 아직 해결되지 않은 것

우리는 [[#3-2. Interceptor — 응답 가공|Interceptor]]로 응답을 `{ success, data, message }`로 감싸는데,
**Swagger는 이 사실을 모른다.** 그래서 문서에는 래핑되지 않은 raw DTO만 표시된다.

이를 맞추려면 `getSchemaPath`를 사용하는 커스텀 응답 데코레이터가 필요하다.
실제 엔드포인트가 있어야 검증할 수 있으므로 Auth API 구현 시 함께 만든다.

### 3-6. Guard — 요청을 통과시킬지 결정

**`canActivate()`가 `true`를 반환하면 컨트롤러로 넘어가고, `false`면 거기서 차단된다.**

```typescript
@Injectable()
export class JwtAuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    // 토큰 검증 후 통과 여부 반환
    return isValid;
  }
}
```

`false`를 반환하면 NestJS가 자동으로 `ForbiddenException`을 던진다.

#### Interceptor와의 차이

| | Guard | Interceptor |
|---|---|---|
| 하는 일 | 통과/차단 **결정** | 요청·응답 **가공** |
| 반환 | `boolean` | 변형된 데이터 |
| 시점 | 컨트롤러 진입 **전** | 진입 **전과 후** |

#### 요청 처리 순서

```
요청 → Middleware → Guard → Interceptor(전) → Pipe → Controller
                                                          ↓
응답 ←──────────── Interceptor(후) ←───────────────────────┘
        예외 발생 시 → Exception Filter
```

**Guard가 Pipe보다 먼저인 것이 중요하다.**
인증되지 않은 요청은 DTO 검증까지 갈 필요 없이 즉시 차단된다. 불필요한 연산을 하지 않는다.

#### 이 프로젝트의 Guard 3개

```
1) ThrottlerGuard   유량 제한 (인증 여부와 무관하게 가장 먼저)
2) JwtAuthGuard     토큰 검증 → request.user에 { sub, role, gymId } 주입
3) RolesGuard       request.user.role이 @Roles()에 명시된 역할인지 확인
```

**등록 순서가 곧 실행 순서다.**

```typescript
// app.module.ts
providers: [
  { provide: APP_GUARD, useClass: ThrottlerGuard },
  { provide: APP_GUARD, useClass: JwtAuthGuard },
  { provide: APP_GUARD, useClass: RolesGuard },
]
```

순서가 중요한 이유가 각각 다르다.

- `ThrottlerGuard`가 맨 앞인 이유: 뒤에 두면 무차별 대입 요청이 매번 토큰 검증까지 연산을 태운다
- `RolesGuard`가 맨 뒤인 이유: `JwtAuthGuard`가 `request.user`를 채워야 role을 읽을 수 있다.
  순서가 바뀌면 항상 401이 난다

> Spring의 `@Order`처럼 별도 어노테이션으로 순서를 주는 것이 아니라
> **배열에 쓴 순서가 그대로 실행 순서**라는 점이 다르다.

#### 엔드포인트별로 한도를 다르게

전역 기본값을 두고 필요한 곳만 `@Throttle`로 덮어쓴다.

```typescript
// 전역: 1분 100회
ThrottlerModule.forRoot([{ ttl: 60_000, limit: 100 }])

// 인증 엔드포인트: 1분 5회
@Throttle({ default: { limit: 5, ttl: 60_000 } })
@Post('login')
```

Spring의 Bucket4j에 해당한다. 사용자 열거와 무차별 대입을 함께 막는 수단이다. → ADR-008

#### 전역 Guard + `@Public` 예외 방식

Guard를 거는 방법은 두 가지다.

```typescript
// A. 필요한 곳에만 붙이기
@UseGuards(JwtAuthGuard)
@Get('me')

// B. 전역으로 걸고 공개 라우트만 예외 표시  ← 채택
@Public()
@Post('login')
```

**B를 선택했다.** A는 Guard를 깜빡 빠뜨리면 **엔드포인트가 조용히 열린다.**
테스트해보기 전까지 알아채기 어렵다. B는 반대로 깜빡하면 접근이 막히므로 즉시 발견된다.

**실패하는 방향이 안전한 쪽(fail-safe)** 을 택한 것이다.
Spring Security에서 `anyRequest().authenticated()`를 기본으로 깔고
`permitAll()`을 예외로 두는 것과 같은 접근이다.

### 3-7. Pipe — 변환과 검증

요청 데이터가 핸들러에 도달하기 **직전**에 가공하거나 검증한다.
Spring의 `Converter` + `@Valid`를 합친 자리다.

```
Guard → Interceptor(전) → Pipe → Controller
```

Guard보다 뒤인 이유는, 인증되지 않은 요청은 검증까지 갈 필요가 없기 때문이다.

#### 전역 Pipe — ValidationPipe

`main.ts`에 한 번 등록하면 모든 DTO에 적용된다. → [[#3-1. DTO와 검증|3-1]]

#### 파라미터 단위 Pipe

특정 파라미터에만 붙일 수도 있다.

```typescript
@Get(':id')
findOne(@Param('id', ParseUUIDPipe) id: string) { ... }
```

**실제로 겪은 문제**: `ParseUUIDPipe`가 없으면 UUID가 아닌 값이 그대로 DB까지 내려간다.

```
GET /gyms/GYM_ID
  → findOne({ where: { id: 'GYM_ID' } })
  → PostgreSQL: invalid input syntax for type uuid (22P02)
  → QueryFailedError → 전역 필터가 "정의되지 않은 오류"로 판단
  → 500 Internal Server Error
```

**형식 오류는 400이어야 한다.** 클라이언트 잘못인데 서버 오류로 응답하면
모니터링에서 실제 장애와 구분되지 않는다.

내장 Pipe는 이 외에도 `ParseIntPipe`, `ParseBoolPipe`, `ParseArrayPipe`,
`DefaultValuePipe` 등이 있다.

> **규칙**: 경로 파라미터로 UUID를 받으면 항상 `ParseUUIDPipe`를 붙인다.

### 3-7-1. 쿼리스트링의 boolean 함정

```
GET /membership-types?includeInactive=true
```

```typescript
@IsOptional()
@IsBoolean()
includeInactive?: boolean;   // ❌ 400 VALIDATION_FAILED
```

**쿼리스트링은 항상 문자열이다.** `"true"`가 들어오므로 `@IsBoolean()`이 거부한다.

`@Type(() => Boolean)`으로도 해결되지 않는다.

```javascript
Boolean('true')   // true
Boolean('false')  // true   ← 빈 문자열이 아니면 전부 참
Boolean('')       // false
```

**`false`를 보내도 참이 되어 조용히 틀린다.** 에러가 나지 않아 더 위험하다.

**해결** — 명시적으로 변환한다.

```typescript
@IsOptional()
@Transform(({ value }) => value === 'true' || value === true)
@IsBoolean()
includeInactive?: boolean;
```

> 숫자는 `@Type(() => Number)`가 정상 동작한다. `Number('1')`은 `1`이기 때문이다.
> **boolean만 예외**라는 점을 기억해야 한다.

### 3-8. NestJS 인증 구조 vs Spring Security

#### JWT 자체는 동일하다

JWT는 **RFC 7519 표준**이다. 프레임워크와 무관하게 구조가 같다.

```
헤더.페이로드.서명
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMifQ.SflKxwRJ...
```

Spring에서 만든 토큰을 NestJS에서 검증할 수도 있다. 같은 시크릿과 알고리즘이면 호환된다.
**다른 것은 토큰이 아니라 프레임워크가 제공하는 추상화 수준이다.**

#### 구조 대응

| Spring Security | NestJS | 비고 |
|---|---|---|
| `SecurityFilterChain` 설정 | 전역 Guard + `@Public()` | NestJS는 중앙 설정 클래스가 없음 |
| `JwtAuthenticationFilter` (직접 구현) | `JwtStrategy` (Passport) | |
| `UserDetailsService.loadUserByUsername` | `JwtStrategy.validate()` | 반환값이 `request.user`가 됨 |
| `SecurityContextHolder.getContext()` | `request.user` | ⚠️ 아래 설명 |
| `@PreAuthorize("hasRole('OWNER')")` | `@Roles(Role.OWNER)` + `RolesGuard` | |
| `AuthenticationManager` | 없음. Service에서 직접 처리 | |
| `PasswordEncoder` 빈 | `bcrypt` 직접 호출 | |
| `@AuthenticationPrincipal` | `@CurrentUser()` (직접 만듦) | |

#### 가장 큰 차이 — 제공 수준

**Spring Security는 완성된 프레임워크다.** 로그인 처리, 세션 관리, CSRF, 권한 평가가 이미 들어있고
개발자는 설정으로 조립한다. 대신 내부 동작이 보이지 않아 "왜 이게 막히지"를 디버깅하기 어렵다.

**NestJS는 재료만 준다.** Guard, Passport Strategy, 데코레이터가 전부다.
로그인 로직, 토큰 발급, 비밀번호 비교를 전부 직접 작성한다.
코드는 늘어나지만 **동작이 전부 눈에 보인다.**

이 프로젝트에서 Refresh Token Rotation이나 Reuse Detection을 직접 구현할 수 있는 것도
그 흐름이 우리 코드 안에 있기 때문이다. Spring Security였다면 필터를 커스터마이징해야 했을 것이다.

#### SecurityContextHolder가 없는 이유

Spring의 `SecurityContextHolder`는 기본적으로 **ThreadLocal**에 인증 정보를 담는다.
요청 하나가 스레드 하나를 점유하므로 성립하는 구조다.

Node.js는 **싱글 스레드 이벤트 루프**다. 요청마다 스레드가 배정되지 않으므로 ThreadLocal이 성립하지 않는다.
그래서 인증 정보를 **request 객체에 직접 붙인다.**

```typescript
// JwtStrategy.validate()의 반환값이 request.user에 담긴다
async validate(payload: JwtPayload) {
  return { userId: payload.sub, role: payload.role, gymId: payload.gymId };
}
```

이 값을 컨트롤러에서 꺼내려면 커스텀 데코레이터가 필요하다.

```typescript
export const CurrentUser = createParamDecorator(
  (data: unknown, ctx: ExecutionContext) =>
    ctx.switchToHttp().getRequest().user,
);

// 사용
@Get('me')
getMe(@CurrentUser() user: JwtPayload) { ... }
```

Spring의 `@AuthenticationPrincipal`과 같은 역할이며, 역시 직접 만든다.

#### 스크립트 실행 — CommandLineRunner 대응

시드처럼 HTTP 없이 DI 컨테이너만 필요할 때가 있다.

```typescript
// HTTP 서버까지 띄운다 (포트 점유)
const app = await NestFactory.create(AppModule);

// DI 컨테이너만 부팅한다 (포트 점유 없음, 빠름)
const app = await NestFactory.createApplicationContext(AppModule, {
  logger: ['error', 'warn'],
});
```

`createApplicationContext`를 쓰면 서비스·Repository를 그대로 주입받아 쓸 수 있으면서
3000번 포트를 잡지 않는다. 서버가 떠 있는 상태에서도 시드를 돌릴 수 있다.

```json
// package.json — ts-node는 NestJS 프로젝트에 기본 포함되어 있다
"seed": "ts-node -r tsconfig-paths/register src/seed.ts"
```

**멱등성은 존재 확인으로 구현했다.**
`INSERT ... ON CONFLICT DO NOTHING`도 가능하지만,
시드는 사람이 직접 돌리고 결과를 눈으로 확인하는 스크립트라
"생성했는지 건너뛰었는지"가 로그에 보이는 편이 낫다.

**고정 UUID를 쓴 이유**도 하나 있다.
이름으로 존재를 판단하면 이름이 바뀌었을 때 중복 생성된다.
PK로 판단하면 안전하고, 테스트 스크립트에 gymId를 하드코딩할 수 있어 매번 조회할 필요가 없다.

```typescript
const DEV_GYM = { id: '00000000-0000-4000-8000-000000000001', ... };
```

> 세 번째 그룹이 `4`, 네 번째가 `8`로 시작하면 유효한 UUID v4 형식이라
> `@IsUUID()` 검증을 통과한다. 나머지를 0으로 채우면 **딱 봐도 시드 데이터**로 구분된다.

#### 실행 위치의 차이

Spring Security 필터는 **서블릿 필터**라 `DispatcherServlet`보다 앞에서 동작한다.
따라서 URL 패턴으로 인가를 판단한다(`.antMatchers("/admin/**")`).

NestJS Guard는 **라우팅이 끝난 뒤** 실행되므로 어느 핸들러가 호출될지 이미 안다.
그래서 `Reflector`로 핸들러의 메타데이터(`@Roles`, `@Public`)를 쉽게 읽을 수 있다.

Spring의 메서드 시큐리티(`@PreAuthorize`)가 이쪽에 더 가깝다.

## 4. TypeORM 실전

> JPA와 개념은 거의 같지만, 실제로 코드를 쓰다 보면 걸리는 지점들이 다르다.

### 4-1. `select: false` 와 `addSelect`

비밀번호처럼 **DB에서 아예 가져오면 안 되는 컬럼**에 쓴다.

```typescript
@Column({ length: 255, select: false })
password: string;
```

일반 조회에서는 이 컬럼이 SELECT 절에 포함되지 않는다.
API 응답에 해시가 실수로 나가는 경로를 원천 차단한다.

Java의 `@JsonIgnore`와는 성격이 다르다.
`@JsonIgnore`는 **조회는 하고 직렬화만** 막지만, `select: false`는 **조회 자체를 안 한다.**

로그인처럼 실제로 필요할 때만 QueryBuilder로 명시적으로 꺼낸다.

```typescript
const user = await this.userRepo
  .createQueryBuilder('user')
  .addSelect('user.password')          // ← 이때만 포함
  .where('user.loginId = :loginId', { loginId })
  .getOne();
```

> `findOne({ where: ... })`으로는 `addSelect`를 쓸 수 없어 QueryBuilder가 필요하다.

### 4-2. `IsNull()` vs `undefined` — 조용히 틀리는 조건

TypeORM은 조건 객체에서 **`undefined`인 프로퍼티를 무시한다.**

```typescript
// ❌ 의도: 폐기되지 않은 것만
// 실제: userId 조건만 적용되어 이미 폐기된 것까지 전부 갱신
repo.update({ userId, revokedAt: undefined }, { revokedAt: new Date() });

// ✅
repo.update({ userId, revokedAt: IsNull() }, { revokedAt: new Date() });
```

**에러가 나지 않는다는 점이 위험하다.** 쿼리는 성공하고 결과만 틀린다.
우리 경우 이미 폐기된 토큰의 폐기 시각과 사유까지 덮어써서
재사용 감지의 근거 데이터가 훼손될 뻔했다.

> **규칙**: NULL 비교는 반드시 `IsNull()` / `Not(IsNull())`을 쓴다.
> `undefined`는 "조건 없음"이지 "NULL"이 아니다.

### 4-3. DB 제약 위반을 의미 있는 응답으로 바꾸기

애플리케이션에서 중복을 먼저 확인해도 **동시 요청은 통과한다.**

```
요청 A: SELECT → 없음
요청 B: SELECT → 없음
요청 A: INSERT → 성공
요청 B: INSERT → unique 제약 위반 💥
```

최종 방어선은 항상 DB 제약이다. 그런데 그대로 두면 전역 예외 필터가 500으로 뭉갠다.

```typescript
try {
  return await this.userRepo.save(user);
} catch (error) {
  if (
    error instanceof QueryFailedError &&
    (error as QueryFailedError & { code?: string }).code === '23505'
  ) {
    throw new BusinessException(ErrorCode.DUPLICATE_LOGIN_ID);
  }
  throw error;
}
```

**PostgreSQL 주요 에러 코드**

| 코드 | 의미 |
|------|------|
| `23505` | unique_violation (중복) |
| `23503` | foreign_key_violation (참조 무결성) |
| `23502` | not_null_violation |
| `23514` | check_violation |

> Spring에서 `DataIntegrityViolationException`을 잡아 처리하던 것과 같은 맥락이다.
> 다만 TypeORM은 예외를 추상화하지 않아 **DB 벤더의 에러 코드를 직접 다뤄야 한다.**
> PostgreSQL에 종속되는 코드이므로, 상수로 분리해 의도를 드러냈다.

### 4-4. `synchronize`는 컬럼 삭제를 항상 반영하지 않는다

```typescript
synchronize: config.get('NODE_ENV') === 'development',
```

Spring의 `ddl-auto=update`에 해당한다. Entity를 읽어 테이블을 맞춰준다.

**컬럼 추가는 잘 되지만 삭제·타입 변경은 데이터 손실 위험 때문에 건너뛸 수 있다.**
`email` → `loginId` 처럼 컬럼이 사라지는 변경을 했다면 반드시 실제 스키마를 확인한다.

```bash
docker exec -it gym-manager-db psql -U gym -d gym_manager -c "\d users"
```

반영되지 않았으면 개발 환경에서는 그냥 테이블을 밀어버리는 편이 빠르다.

```bash
docker exec ... -c "DROP TABLE refresh_tokens, users, gyms CASCADE;"
```

> 운영 환경에서는 `synchronize`를 절대 켜지 않는다. 대신 마이그레이션을 쓴다.

### 4-5. 트랜잭션 두 가지 방식

Spring은 `@Transactional` 하나로 끝나지만, TypeORM은 **직접 경계를 잡아야 한다.**
NestJS에는 `@Transactional` 같은 선언적 트랜잭션이 기본 제공되지 않는다.

#### A. `dataSource.transaction()` — 콜백 방식

```typescript
await this.dataSource.transaction(async (manager) => {
  const gym = await manager.save(manager.create(Gym, { ... }));
  const owner = await manager.save(manager.create(User, { gymId: gym.id, ... }));
  return { gym, owner };
});
```

콜백이 정상 종료하면 commit, 예외를 던지면 rollback. **해제(release)도 자동이다.**

#### B. `QueryRunner` — 수동 방식

```typescript
const queryRunner = this.dataSource.createQueryRunner();
await queryRunner.connect();
await queryRunner.startTransaction();
try {
  await queryRunner.manager.update(...);
  await queryRunner.commitTransaction();
} catch (error) {
  await queryRunner.rollbackTransaction();
  throw error;
} finally {
  await queryRunner.release();   // 빠뜨리면 커넥션 누수
}
```

#### 언제 무엇을 쓰나

| | `transaction()` | `QueryRunner` |
|---|---|---|
| 코드량 | 적음 | 많음 |
| 해제 누락 위험 | 없음 | **있음** |
| 격리 수준 지정 | 인자로 가능 | 가능 |
| 세이브포인트 | 어려움 | 가능 |
| 비관적 락 | 가능하나 제한적 | 유연함 |

**기본은 A.** 커넥션 해제를 깜빡할 수 없다는 점이 크다.
락이나 세이브포인트가 필요한 복잡한 흐름에서만 B를 쓴다.

#### 중요한 함정 — 반드시 `manager`를 써야 한다

```typescript
await this.dataSource.transaction(async (manager) => {
  await manager.save(gym);        // ✅ 트랜잭션 안
  await this.gymRepo.save(gym);   // ❌ 트랜잭션 밖! 롤백되지 않는다
});
```

콜백 안에서 주입받은 Repository를 그대로 쓰면 **별도 커넥션을 사용해 트랜잭션에 참여하지 않는다.**
Spring의 `@Transactional`은 프록시가 알아서 커넥션을 전파해주지만, TypeORM은 명시적이다.

> 이것이 트랜잭션을 쓰는 서비스에서 `@InjectRepository` 대신
> `manager`를 넘겨받는 형태를 선호하는 이유다.

### 4-6. 조건부 UPDATE — 락 없이 동시성 잡기

**트랜잭션으로 감싸는 것만으로는 동시 요청이 막히지 않는다.**
PostgreSQL 기본 격리 수준이 `READ COMMITTED`라 두 트랜잭션이 같은 값을 읽을 수 있다.

#### 문제 — lost update

```typescript
const contract = await repo.findOne(...);              // ① 읽는다
if (contract.remainingSessions <= 0) throw ...;        // ② 판단한다
await repo.update(id, {                                // ③ 쓴다
  remainingSessions: contract.remainingSessions - 1,   //   읽은 값으로 계산
});
```

```
A: ① 읽음 remaining=1
B: ① 읽음 remaining=1     ← A가 아직 안 썼다
A: ② 통과 → ③ 0 저장
B: ② 통과 → ③ 0 저장      ← A의 갱신을 덮어쓴다
```

**잘못된 곳이 두 군데다.**

| | 문제 |
|---|------|
| 조건이 애플리케이션에 | ②와 ③ 사이에 다른 트랜잭션이 끼어든다 |
| 계산이 애플리케이션에 | 읽은 시점의 값으로 빼서 남의 갱신을 덮어쓴다 |

#### 해결 — 조건과 계산을 둘 다 SQL 안으로

```typescript
const result = await manager.update(
  PTContract,
  { id, remainingSessions: MoreThan(0) },                   // 조건 → WHERE
  { remainingSessions: () => '"remaining_sessions" - 1' },  // 계산 → SET
);

if (result.affected === 0) throw new BusinessException(...);
```

```sql
UPDATE pt_contracts
   SET remaining_sessions = remaining_sessions - 1
 WHERE id = $1 AND remaining_sessions > 0
```

#### 왜 락이 필요 없나

```
UPDATE는 실행되는 순간 그 행에 배타 락을 잡고,
락을 잡은 뒤에 WHERE 조건을 다시 평가한다.

A: UPDATE … WHERE remaining > 0  →  락 획득, 조건 참  → 1 row
B: UPDATE … WHERE remaining > 0  →  A 커밋 대기 → 재평가 → 거짓 → 0 row
```

**`SELECT ... FOR UPDATE`가 하는 일을 `UPDATE` 한 문장이 이미 하고 있다.**
읽고 잠그고 다시 쓰는 왕복이 한 번으로 줄어든다.

#### 상태 전이에도 같은 방식을 쓴다

```typescript
await manager.update(
  PTSchedule,
  { id, status: SCHEDULED },        // 조건
  { status: COMPLETED, ... },
);
// affected === 0 → 이미 처리됨 (중복 클릭)
```

**멱등성 확보에도 그대로 쓰인다.** 이전 프로젝트에서 Kafka 중복 소비를 막던
`UPDATE … SET restore_status = 1 WHERE restore_status = 0`도 같은 패턴이었다.

#### 다른 방식과 비교

| 방식 | 언제 쓰나 | 비용 |
|------|----------|------|
| **조건부 UPDATE** | 조건이 SQL로 표현될 때 | 없음. 쿼리 한 번 |
| 비관적 락 (`FOR UPDATE`) | 읽고 → 계산하고 → 쓰는 과정이 길 때 | 대기·데드락 |
| 낙관적 락 (`@Version`) | 충돌이 드물고 재시도가 쌀 때 | 재시도 로직 |
| Redis 분산 락 | 여러 **DB**를 다룰 때 | DB 락이 이미 분산 락이다 |

> **`affected`를 확인하지 않으면 조건을 건 의미가 없다.**
> 0 row도 예외 없이 성공으로 보인다. 이게 이 패턴의 유일한 함정이다.

→ 트러블슈팅 006, ADR-014 결정 5

## 5. 보안

### 5-1. 두 가지를 구분하기

에러 응답에서 정보를 감추는 데는 **성격이 다른 두 층위**가 있다.
Spring에서 "존재하지 않는 이메일입니다"를 뭉갰던 경험은 이 중 첫 번째에 해당한다.

| | 사용자 열거 방지 | 내부 구현 노출 방지 |
|---|---|---|
| 무엇을 감추나 | **비즈니스 사실** (이 이메일이 가입돼 있는지) | **구현 세부사항** (스택, 쿼리, 경로) |
| 왜 | 계정 존재 여부를 알아내는 정찰을 막으려고 | 시스템 구조 파악을 막으려고 |
| 어디서 | 비즈니스 로직 (Service) | 인프라 (Exception Filter) |
| 성격 | **의도적으로** 정보를 뭉갬 | **실수로 새는 것**을 차단 |

**둘 다 필요하고, 서로를 대체하지 않는다.**
지금 만든 Exception Filter는 두 번째만 해결한다. 첫 번째는 Auth 모듈에서 별도로 구현해야 한다.

#### 사용자 열거(User Enumeration)가 왜 위험한가

공격자는 비밀번호를 모르는 상태에서도 **"이 이메일이 가입돼 있다"** 는 사실만으로 다음을 할 수 있다.

- 확보한 유출 계정 목록 중 이 서비스에 유효한 것만 추려 크리덴셜 스터핑
- 실제 사용자에게 표적 피싱 메일 발송
- 특정 인물의 가입 여부 확인 (프라이버시 침해 자체가 피해)

**로그인**에서는 뭉개는 데 비용이 거의 없다. 이미 표준 문구가 정착되어 있다.

```
❌ "존재하지 않는 이메일입니다"  /  "비밀번호가 올바르지 않습니다"
✅ "이메일 또는 비밀번호가 올바르지 않습니다"
```

#### 타이밍 공격 — 메시지를 통일해도 새는 경로

메시지가 같아도 **응답 시간이 다르면** 계정 존재 여부가 드러난다.

```
아이디 없음   → 즉시 반환                    (1ms)
아이디 있음   → bcrypt.compare 수행 후 반환   (100ms)
```

수백 번 요청해 평균을 내면 통계적으로 구분된다.
유저를 찾지 못했을 때도 **더미 해시와 비교**해 연산 비용을 발생시킨다.

```typescript
// 프로세스 시작 시 1회 생성. 값 자체는 의미 없고 비용만 필요하다
private readonly dummyHash = bcrypt.hashSync(
  randomBytes(16).toString('hex'),
  BCRYPT_ROUNDS,
);

const user = await this.userRepo.createQueryBuilder('user')
  .addSelect('user.password')
  .where('user.loginId = :loginId', { loginId: dto.loginId })
  .getOne();

// 유저가 없어도 해싱 비용을 발생시킨다
const passwordMatches = await bcrypt.compare(
  dto.password,
  user?.password ?? this.dummyHash,
);

// 미존재 / 불일치 / 비활성을 구분하지 않는다
if (!user || !passwordMatches || !user.isActive) {
  throw new BusinessException(ErrorCode.INVALID_CREDENTIALS);
}
```

> **비활성 계정도 같은 응답으로 묶은 것**에 주목.
> "정지된 계정입니다"라고 알려주면 그것 역시 계정 존재의 증거가 된다.

**회원가입**은 사정이 다르다. → [[#5-2. 회원가입의 딜레마]]

### 5-2. 회원가입의 딜레마

회원가입에서 "이미 가입된 이메일입니다"를 보여주면 로그인과 똑같이 열거가 가능하다.
그런데 이 메시지를 감추면 **사용자가 왜 가입이 안 되는지 알 수 없다.** 정직한 트레이드오프다.

| 방식 | 열거 방지 | UX | 비용 |
|------|:---:|:---:|------|
| A. 명확히 안내 ("이미 가입된 이메일") | ✗ | 좋음 | 없음 |
| B. 뭉개기 ("가입할 수 없습니다") | △ | 나쁨 | 지원 문의 증가 |
| C. 항상 성공 응답 + 이메일 통지 | ✓ | 좋음 | 메일 인프라 필요 |

C가 정석이다. 가입 요청은 항상 성공처럼 응답하고,
이미 계정이 있으면 **"누군가 이 메일로 가입을 시도했습니다. 이미 계정이 있습니다"** 메일을 보낸다.
응답만 봐서는 존재 여부를 알 수 없고, 진짜 소유자만 사실을 알게 된다.

B가 애매한 이유는, 메시지를 뭉개도 **응답 시간·상태 코드·후속 흐름의 차이**로 여전히 추론이 가능하기 때문이다.
철저히 막으려면 결국 C가 필요하다.

> **이 프로젝트의 선택**: 로그인은 통합 메시지 + 타이밍 보정,
> 회원가입은 명확한 안내 유지 + Rate Limiting. → ADR-008
> 중요한 것은 "위험을 인지하고 의도적으로 선택했는가"이며,
> 인지하지 못한 채 노출하는 것과는 전혀 다르다.

#### 이런 트레이드오프를 판단하는 순서

정답이 하나로 정해지지 않는 문제를 만났을 때 쓰는 틀이다.

**1. 위협 모델을 구체화한다.** "보안상 안 좋다"는 추상적이다.
*누가 / 무엇을 얻으려고 / 얼마의 비용으로* 를 채워야 판단할 수 있다.

**2. 완화 수단을 효과 순으로 줄 세운다.**
가장 약한 수단만 적용하고 안심하는 것이 가장 흔한 실수다.
우리 경우 메시지 뭉개기(약함)만 하고 Rate Limiting(강함)을 빼면 아무것도 안 한 것과 같다.

**3. 되돌리기 비용을 본다.**
메시지 문구는 한 줄 수정이면 바뀐다. DB 스키마나 인증 구조는 되돌리기가 비싸다.
**되돌리기 싼 결정에는 오래 고민하지 않는다.** 지금 정하고 나중에 바꾸면 된다.

**4. 선택을 기록한다.**
모르고 노출한 것과 알고 선택한 것은 전혀 다르다. ADR이 그 차이를 증명한다.

#### 함께 필요한 방어

메시지를 어떻게 하든 **Rate Limiting 없이는 열거를 막을 수 없다.**
초당 수백 건의 가입 시도가 가능하면 어떤 문구를 쓰든 통계적으로 뚫린다.

NestJS는 `@nestjs/throttler`로 처리한다. Spring의 Bucket4j나 Spring Cloud Gateway 필터에 해당한다.

### 5-3. Refresh Token Rotation과 재사용 감지

긴 만료 기간(30일)의 위험을 상쇄하는 구조다. → ADR-006

#### Rotation

갱신할 때마다 기존 토큰을 폐기하고 새 쌍을 발급한다.
30일짜리 토큰이 30일 내내 같은 값으로 떠도는 것이 아니라,
**개별 토큰의 실제 수명은 갱신 주기(약 1시간) 수준**이 된다.

#### 재사용 감지

```
공격자가 토큰 탈취 → 갱신 성공 → 새 토큰 획득 (기존 토큰은 폐기됨)
정상 사용자가 갱신 시도 → 이미 폐기된 토큰 제출 → 이상 감지
  → 해당 계정의 모든 토큰 폐기 → 양쪽 모두 로그아웃
```

정상 사용자는 재로그인하면 되고, 공격자는 접근이 끊긴다.
**폐기된 토큰을 삭제하지 않고 `revokedAt`으로 표시만 하는 이유**가 여기 있다.
지워버리면 "정상 만료"와 "재사용 공격"을 구분할 수 없다.

#### 실제로 겪은 설계 결함 — 폐기 사유가 없으면 오판한다

처음에는 "폐기된 토큰이 오면 무조건 탈취"로 구현했다. 동작은 했지만 의미가 틀렸다.

```
회전으로 교체된 토큰이 다시 옴   → 진짜 탈취 정황
로그아웃으로 폐기된 토큰이 다시 옴 → 클라이언트의 단순 재시도일 수 있음
```

구분이 없으니 **로그아웃한 사용자에게 "보안상의 이유로 모든 세션이 종료되었습니다"** 가 나갔다.
더 나쁜 것은 진짜 공격 신호가 이런 노이즈에 묻힌다는 점이다.

`revokedReason` 컬럼을 추가해 `ROTATED` 상태의 재제출만 탈취로 판정하도록 고쳤다.

```typescript
if (stored.revokedAt) {
  if (stored.revokedReason === RevokeReason.ROTATED) {
    await this.revokeAllByUser(stored.userId, RevokeReason.REUSE_DETECTED);
    throw new BusinessException(ErrorCode.TOKEN_REUSE_DETECTED);
  }
  // 로그아웃·일괄 폐기된 토큰은 그냥 무효 처리
  throw new BusinessException(ErrorCode.INVALID_REFRESH_TOKEN);
}
```

> **교훈**: 테스트가 "동작하는데 의미가 틀린" 코드를 잡아냈다.
> 예상 결과와 실제 결과가 다를 때, 코드를 고치기 전에
> **내 예상이 틀린 것인지 코드가 틀린 것인지**를 먼저 가려야 한다.

#### 왜 Refresh Token은 SHA-256인가

| | bcrypt | SHA-256 |
|---|--------|---------|
| 조회 | 인덱스 불가. 후보를 모두 가져와 순회 비교 | **해시값으로 단일 조회** |
| 속도 | 의도적으로 느림 | 빠름 |
| 적합 대상 | 저엔트로피 **비밀번호** | 고엔트로피 **랜덤 토큰** |

bcrypt의 느린 해싱은 사람이 만든 비밀번호가 무차별 대입에 취약하기 때문에 필요하다.
Refresh Token은 서버가 생성한 고엔트로피 값이라 무차별 대입 자체가 불가능하므로
느린 해싱이 이점을 주지 않는다.

**비밀번호는 계속 bcrypt를 쓴다. 용도가 다르다.**

### 5-4. 내부 구현 노출 방지

우리가 필터에서 한 것이다.

```typescript
// 3. 정의되지 않은 오류 — 내부 정보를 숨긴다
return {
  status: HttpStatus.INTERNAL_SERVER_ERROR,
  errorCode: ErrorCode.INTERNAL_ERROR,
  message: '서버 오류가 발생했습니다',   // 고정 문구
};
```

이걸 안 하면 이런 게 그대로 나간다.

```
duplicate key value violates unique constraint "UQ_users_email"
```

한 줄에 **테이블명, 제약조건명, 컬럼 구조**가 다 들어있다.
공격자에게는 DB 스키마를 유추할 단서가 된다.

스택 트레이스는 더 나쁘다. 파일 경로, 프레임워크 버전, 내부 클래스 구조가 전부 드러난다.

### 5-5. Spring 대조 — `server.error.include-stacktrace`

Spring Boot는 처리되지 않은 예외를 `/error` 엔드포인트로 넘기고,
`DefaultErrorAttributes`가 기본 에러 응답을 만든다.

```json
{
  "timestamp": "2026-07-29T02:30:00.000+00:00",
  "status": 500,
  "error": "Internal Server Error",
  "trace": "java.lang.NullPointerException\n\tat com.gym.service.UserService...",
  "message": "...",
  "path": "/api/users"
}
```

`trace` 필드가 문제다. 이걸 제어하는 설정이다.

```properties
server.error.include-stacktrace=never   # trace 필드를 아예 빼기
server.error.include-message=never      # message도 감추기
```

값은 `always` / `on_param` / `never` 세 가지다.
`on_param`은 `?trace=true` 쿼리를 붙였을 때만 노출한다 — 개발 중 디버깅용.

> 최근 Spring Boot 버전은 두 설정 모두 기본값이 `never`다.
> 예전 버전은 `always`가 기본이라 운영 서버에서 스택이 그대로 노출되는 사고가 흔했다.

**NestJS와의 차이**: Spring은 프레임워크가 기본 에러 응답을 만들어주고 설정으로 조절한다.
NestJS는 그런 기본 동작이 약해서 **Exception Filter를 직접 만들어야 한다.**
대신 응답 형태를 완전히 통제할 수 있다.

### 5-6. 로그 레벨을 상태 코드로 나눈 이유

```typescript
if (status >= 500) {
  this.logger.error(..., exception.stack);   // 스택까지
} else {
  this.logger.warn(...);                     // 한 줄만
}
```

400대는 대부분 클라이언트의 잘못된 요청이라 스택이 의미 없다.
전부 `error`로 찍으면 진짜 봐야 할 500번대가 로그에 파묻힌다.

## 6. 테스트

### 6-1. 세 층위

| | 검증 범위 | Spring | NestJS |
|---|---|---|---|
| **단위** | 클래스 하나. 나머지는 mock | Mockito | Jest + mock |
| **통합** | 여러 계층 + 실제 DB | `@DataJpaTest` | Jest + TestingModule |
| **E2E** | HTTP 요청 → 응답 전체 | `@SpringBootTest` + `MockMvc` | `supertest` |

**Postman으로 API를 호출하며 DB를 확인하던 것이 바로 E2E다.** 손으로 하느냐 코드로 하느냐의 차이다.

| | 수동(Postman) | E2E 테스트 |
|---|---|---|
| 앱·DB | 실제 | 실제 (동일) |
| 응답 확인 | 눈으로 | `expect`로 단언 |
| DB 확인 | psql에서 SELECT | 테스트 안에서 Repository 조회 |
| 반복 | 매번 손으로 | `npm run test:e2e` |
| 회귀 감지 | 안 됨 | 예전 기능이 깨지면 즉시 실패 |

### 6-2. 왜 단위보다 E2E를 먼저 했나

우리 서비스 코드는 대부분 **DB를 거쳐야 의미가 생긴다.**
`UsersService.findAll`을 단위 테스트하려면 Repository와 QueryBuilder를 전부 mock해야 하는데,
그러면 **"내가 만든 mock이 맞는지"를 테스트하는 꼴**이 된다.
정작 중요한 "WHERE에 gymId가 들어갔나"는 검증되지 않는다.

E2E는 실제 DB를 쓰므로 테넌트 격리 같은 것이 진짜로 확인된다.

**단위 테스트가 유리한 곳도 있다.** 임시 비밀번호 생성처럼 입출력이 순수한 로직은
단위 쪽이 빠르고 명확하다. 그런 곳만 골라 쓴다.

### 6-3. 전역 설정을 공유해야 한다

```typescript
// src/app.setup.ts
export function configureApp(app: INestApplication): void {
  app.useGlobalPipes(new ValidationPipe({ ... }));
  app.useGlobalInterceptors(new TransformInterceptor(app.get(Reflector)));
  app.useGlobalFilters(new AllExceptionsFilter());
}
```

`main.ts`와 E2E가 **같은 함수**를 호출한다.

각자 설정하면 테스트가 실제와 다른 환경을 검증하게 된다.
예를 들어 테스트에 `ValidationPipe`를 빠뜨리면 "role을 보내도 무시되는지" 검증이
통과하는 것처럼 보이지만 실제로는 검증되지 않는다.

### 6-4. `overrideGuard`가 안 먹는 경우

Rate Limit(인증 1분 5회) 때문에 E2E가 429로 실패했다.
`overrideGuard(ThrottlerGuard)`로 막으려 했으나 동작하지 않았다.

```typescript
{ provide: APP_GUARD, useClass: ThrottlerGuard }
```

**`useClass`는 `ThrottlerGuard` 토큰을 조회하지 않고 그 클래스로 새 인스턴스를 만든다.**
따라서 테스트에서 `ThrottlerGuard` 토큰을 교체해도 APP_GUARD 쪽은 원본을 쓴다.
`APP_GUARD` 토큰을 덮어쓰려 해도 우리는 세 개를 등록해 어느 것인지 지정할 수 없다.

**해결**: 라이브러리가 제공하는 확장점을 쓴다.

```typescript
ThrottlerModule.forRoot({
  throttlers: [{ ttl: 60_000, limit: 100 }],
  skipIf: () => process.env.NODE_ENV === 'test',
})
```

> 테스트 쪽 꼼수보다 프레임워크가 의도한 지점을 찾는 편이 낫다.
> 대가로 유량 제한 자체는 테스트되지 않는다. → [[향후 과제]]

### 6-5. 테스트 DB 분리

테스트는 매번 테이블을 비우므로 **개발 DB와 반드시 분리**해야 한다.

```
개발  localhost:5432  gym_manager
테스트 localhost:5433  gym_manager_test   ← docker-compose에 별도 컨테이너
CI    localhost:5433  gym_manager_test   ← 서비스 컨테이너를 5433으로 매핑
```

CI의 포트를 로컬과 똑같이 맞춘 덕에 **`.env.test` 하나를 양쪽이 공유**한다.
CI 워크플로우에 환경변수를 나열할 필요가 없어졌다.

```typescript
// app.module.ts
envFilePath: process.env.NODE_ENV === 'test' ? '.env.test' : '.env',
```

`.env.test`는 실제 시크릿이 아니므로 **git에 커밋한다.**

**Jest 설정 두 가지**

```json
{ "maxWorkers": 1, "testTimeout": 30000 }
```

- `maxWorkers: 1` — 테스트가 DB 하나를 공유한다. 병렬로 돌면 서로 `TRUNCATE`를 날려 깨진다
- `testTimeout` — 앱 부팅 + DB 작업은 기본값(5초)을 넘길 수 있다

### 6-6. 수동 테스트가 못 잡는 버그가 있다

E2E 도입 첫날 실제 버그를 하나 잡았다. → [[트러블슈팅#004]]

Refresh Token의 payload가 `{ sub }`뿐이고 JWT의 `iat`는 **초 단위**라,
**같은 초에 두 번 발급하면 토큰 문자열이 완전히 동일**해진다.
`tokenHash`의 unique 제약을 위반해 500이 발생했다.

```
로그인   → sign({ sub: 'abc' })  iat=1785803124  → "eyJ...A"
즉시 갱신 → sign({ sub: 'abc' })  iat=1785803124  → "eyJ...A"   ← 동일
```

**손으로 curl을 칠 때는 한 번도 재현되지 않았다.** 명령 사이에 최소 1초가 지나기 때문이다.
E2E는 밀리초 단위로 연속 호출하므로 즉시 드러났다.

해결은 JWT 표준 클레임 `jti`(JWT ID)에 UUID를 넣는 것이다.

> **교훈**: 사람이 명령을 치는 속도가 자연스러운 지연을 만들어
> 타이밍 의존 버그를 통째로 가려버린다. Postman으로 아무리 꼼꼼히 눌러도 이런 건 안 나온다.

### 6-7. 테스트가 설계 결함을 드러내기도 한다

`revokedReason` 사례도 같은 맥락이다. → [[#5-3. Refresh Token Rotation과 재사용 감지]]

코드는 "동작"했지만 의미가 틀렸다. 로그아웃한 사용자의 단순 재시도를 탈취로 오판하고 있었다.

> 예상 결과와 실제 결과가 다를 때, 코드를 고치기 전에
> **내 예상이 틀린 것인지 코드가 틀린 것인지**를 먼저 가려야 한다. 그때는 둘 다였다.

## 7. Spring ↔ NestJS 대조표

| Spring Boot | NestJS | 비고 |
|---|---|---|
| `@RestController` | `@Controller` | |
| `@Service` | `@Injectable` | |
| `@Autowired` / 생성자 주입 | 생성자 주입 | NestJS는 생성자 주입만 |
| `@Configuration` | `@Module` | |
| `@RestControllerAdvice` | `ExceptionFilter` + `@Catch()` | 직접 만들어야 함 |
| `ResponseBodyAdvice` | `Interceptor` | |
| `HandlerInterceptor` | `Guard` (인증·인가) | |
| `@Valid` + `BindingResult` | `ValidationPipe` + `class-validator` | 전역 등록 |
| DTO를 record/class로 | DTO는 **반드시 class** | interface는 런타임에 사라짐 |
| 어노테이션 (순수 메타데이터) | 데코레이터 (**실행되는 함수**) | |
| `@Order`로 필터 순서 지정 | **배열 등록 순서**가 실행 순서 | APP_GUARD |
| Bucket4j | `@nestjs/throttler` | Rate Limiting |
| `DataIntegrityViolationException` | `QueryFailedError` + DB 에러 코드 | TypeORM은 예외를 추상화하지 않음 |
| `@JsonIgnore` (직렬화만 제외) | `select: false` (**조회 자체를 안 함**) | |
| `@SpringBootTest` + `MockMvc` | `Test.createTestingModule` + `supertest` | E2E |
| `@Transactional` 테스트 롤백 | `TRUNCATE ... CASCADE` 수동 정리 | 자동 롤백 없음 |
| `application-test.yml` | `.env.test` + `NODE_ENV=test` | |
| `application.yml` | `.env` + `ConfigModule` | |
| `DataSource` 설정 | `TypeOrmModule.forRootAsync` | |
| JPA `@Entity` | TypeORM `@Entity` | 거의 동일 |
| `@Id @GeneratedValue` | `@PrimaryGeneratedColumn('uuid')` | |
| `@ManyToOne` (기본 EAGER) | `@ManyToOne` (**기본 로딩 안 함**) | ⚠️ 정반대 |

| Springdoc | `@nestjs/swagger` | |

### 특히 주의할 차이

**관계 로딩 기본값이 정반대다.**

```java
// JPA — @ManyToOne은 기본 EAGER. 조회하면 딸려옴
@ManyToOne
private Gym gym;
```
```typescript
// TypeORM — 명시하지 않으면 아예 안 불러옴
@ManyToOne(() => Gym, ...)
gym: Gym;    // user.gym은 undefined
```

TypeORM에서 관계를 가져오려면 명시해야 한다.

```typescript
userRepo.find({ relations: ['gym'] })
// 또는
qb.leftJoinAndSelect('user.gym', 'gym')
```

JPA에서 넘어오면 "왜 null이지?"로 헤매는 지점이다.
대신 N+1이 모르는 사이에 터질 일은 줄어든다.

**`select: false`는 JPA에 대응물이 없다.**

```typescript
@Column({ length: 255, select: false })
password: string;
```

일반 조회에서 **DB에서 아예 가져오지 않는다.**
Java의 `@JsonIgnore`는 조회는 하고 직렬화만 막는 것이라 성격이 다르다.

필요할 때만 명시적으로 꺼낸다.

```typescript
qb.addSelect('user.password')
```
