## 확정된 프로젝트 방향

### 프로젝트 목적 (3가지)
1. AI(Claude)를 멘토/동업자/도구로 활용하는 협업 경험
2. NestJS를 활용한 백엔드 프로젝트 경험 (Spring Boot 경력 보유)
3. 초안 설계 → 기능 구현 → CI/CD → 배포까지 전 과정 경험

### 범위 결정
- **웹 백엔드 API만 구현.** 모바일 앱(Flutter)은 제외
- 단, **멀티유저 구조(ADMIN/TRAINER/MEMBER)로 설계** → 나중에 앱/웹 프론트 어느 쪽이든 붙일 수 있게
- 실제 헬스장은 계정 1개 공유 방식이 많지만, 포트폴리오 가치를 위해 역할 분리 구조 채택

### 역할별 기능 (2026-07-27 개정 — 멀티테넌시 반영)
| 역할 | 성격 | 기능 |
|------|------|------|
| SUPER_ADMIN | 개인 (gymId null) | 헬스장 등록/관리, OWNER 계정 발급, 전체 통계 |
| OWNER | **공용 운영 계정** | 회원 등록/관리/검색, 역할 변경(TRAINER 승격), 회원권 종류 설정 및 부여, 출석 현황 조회/수동 처리, PT 계약 등록, 통계(매출/출석률) |
| TRAINER | 개인 | 담당 회원 PT 예약 등록/이동/취소, 완료·노쇼 확정(잔여 횟수 차감), 담당 회원 목록 조회, 프로필 관리 |
| MEMBER | 개인 | 공개 회원가입, 본인 회원권 잔여일 조회, QR 토큰 발급, 본인 PT 일정 조회·취소, 본인 출석 이력 조회 |

### 제외 항목

- 채팅 기능
- 운동 일지
- Flutter 모바일 앱
- 락커 관리

## 설계 변경 이력

### 2026-07-27 — 단일 헬스장 → 멀티테넌시 전환

**계기**: 역할 체계를 논의하다가 "서비스 운영자가 헬스장 대표 계정을 발급한다"는 요구가 나옴.
이는 곧 서비스가 여러 헬스장을 관리한다는 의미였음.

**변경 내용**
- `Gym` 테이블 신설 (테넌트)
- `User`, `MembershipType`, `Payment`, `UserMembership`, `Attendance`, `PTContract`, `PTSchedule`에 `gymId` FK 추가
- `TrainerProfile`은 User와 1:1이므로 gymId 제외
- 역할 체계 3개(ADMIN/TRAINER/MEMBER) → **4개(SUPER_ADMIN/OWNER/TRAINER/MEMBER)**
- 모든 복합 인덱스의 선두 컬럼을 `gymId`로 재구성

**함께 결정된 것**
- OWNER는 개인 계정이 아니라 **헬스장 공용 운영 계정** (프론트 데스크 공유 사용 실태 반영) → ADR-005
- 계정 전환 기능 불필요 (OWNER와 TRAINER는 성격이 다른 별개 계정)
- MEMBER는 공개 회원가입, TRAINER는 MEMBER 가입 후 OWNER가 역할 승격
- Refresh Token은 Redis 없이 User 컬럼 저장 → ADR-006

**데이터 격리 방식**
JwtStrategy가 토큰에서 `gymId` 추출 → `@CurrentUser('gymId')` 데코레이터 → Service 시그니처가 `gymId`를 필수 인자로 요구.
컴파일 타임에 누락을 잡는 구조. (면접 어필 포인트)

> ADR-004에는 `@CurrentGym()`으로 적혀 있으나, `@CurrentUser('gymId')`로 동일한 목적을 달성하므로
> 데코레이터를 추가하지 않았다.

---

### 2026-07-29 — 로그인 식별자 변경 (email → loginId)

**계기**: 이메일 인증을 넣지 않기로 한 상태에서 이메일을 받는 것이 모순이라는 지적.
검증되지 않은 이메일은 단순 문자열일 뿐이고, "비밀번호 찾기가 되겠지"라는 잘못된 기대만 만든다.

**변경 내용**
- `User.email` **제거** → `User.loginId` 추가 (VARCHAR(50), 4~20자, 영소문자·숫자·`_`)
- 비밀번호 복구는 **상위 역할이 초기화**하는 방식
  (MEMBER/TRAINER ← OWNER ← SUPER_ADMIN ← DB 직접)
- `PATCH /users/:id/reset-password`, `PATCH /users/me/password` 추가
- `DUPLICATE_EMAIL` → `DUPLICATE_LOGIN_ID`, `INVALID_CREDENTIALS` 신설
- ADR-008을 아이디 기준으로 개정 (열거 위험이 이메일 대비 낮아짐)

**함께 확인된 것**
- **소셜 로그인(OAuth2)은 설계에 없었다.** 카카오 언급은 전부 결제(KAKAO_PAY)였으며 혼동이 있었다.
  JWT 자체 인증 + Rotation + Reuse Detection에 집중하기로 하고 도입하지 않는다.
- 아이디 중복확인 전용 엔드포인트는 두지 않는다 (열거를 기능으로 제공하는 셈)

|------|------|
| `synchronize: false`는 절반이다 | 끄면 데이터가 안전해지는 게 아니라 **테이블을 만들 주체가 사라진다.** 첫 배포에서 `42P01 relation does not exist`로 전부 죽는다. 마이그레이션이 선행 조건인 이유 |
| `generate`는 붙은 DB에 따라 결과가 바뀐다 | "Entity와 **지금 이 DB**의 차이"를 뽑는다. 테이블이 이미 있는 DB에 붙으면 빈 파일이 나온다. 초기 생성은 **빈 DB**에서 |
| `generate`가 못 뽑는 것 | **확장**은 Entity 메타데이터에 없어 빠진다. `uuid-ossp`(PK 기본값)와 `btree_gist`(EXCLUDE) 둘 다 손으로 넣어야 했다. `EXCLUDE` 제약 자체는 정확히 뽑혔다 |
| 검증 장치는 실패도 확인해야 한다 | `migration:check`가 0을 낸 것만 보면 **아무것도 검사하지 않는 단계**를 CI에 넣은 것일 수 있다. 일부러 컬럼을 지워 1이 나오는지 확인했다 |
| 테스트가 값을 하드코딩하면 방어선에 도달하지 못한다 | `.env.test`의 시크릿을 바꾸자 위조 QR이 **서명 검증에서 먼저 걸려** `type` 검증에 닿지 못했다. 상태 코드만 보는 단언도 같은 문제 |

**Phase 5에서 배운 것**

| 함정 | 내용 |
|------|------|
| `LEFT JOIN`의 기간 조건 위치 | `WHERE`에 두면 조인 결과가 NULL인 행이 탈락해 **사실상 `INNER JOIN`이 된다.** 실적 0건인 트레이너가 목록에서 사라진다. `ON` 절에 넣어야 한다 |
| `timestamp` vs `timestamptz` | 같은 "시각"인데 처리가 반대다. `@CreateDateColumn`의 TypeORM 기본 매핑은 **`timestamp`(타임존 없음)** 라 이미 벽시계 시각이고, 명시한 `timestamptz`(`checked_at`·`start_at`)는 **세션 타임존이 UTC**라 `AT TIME ZONE 'Asia/Seoul'`이 필요하다. 안 붙이면 오전 9시 이전 기록이 전날로 밀린다 |
| 겹칠 수 있는 기간의 합산 | 홀딩 겹침 검사는 **같은 회원권 안에서만** 한다. 헬스·락커를 같은 기간에 홀딩하면 단순 합산이 같은 날을 두 번 빼 분모가 음수가 될 수 있다. `generate_series` + `DISTINCT`로 센다 |
| `getRawMany<T>()`는 단언일 뿐이다 | 별칭 철자가 틀려도 컴파일은 통과하고 런타임에 `undefined`가 된다. 이 계층은 **E2E가 유일한 방어선**이다 |
| `addMonths`의 말일 오버플로 | `setMonth`는 없는 날짜(9월 31일)를 다음 달로 흘린다. **1일로 맞춘 뒤 월을 빼야** 31일에 실행할 때 한 달이 사라지지 않는다 |

**트리거를 걸어두고 놓친 사고 (#37)**

`향후 과제`에 "Phase 4-1 구현 직후 **바로**"라고 적어둔 항목을 **Phase 5까지 지나치도록 아무도 안 봤다.**
문서에 트리거를 적는 것만으로는 부족하고, **작업 단위가 끝날 때 발동한 트리거를 훑는 절차**가 있어야 한다.

조사해보니 구멍은 하나가 아니었다.

| 지점 | 증상 |
|------|------|
| `updateRole` 강등 | `TrainerProfile`이 지워지고 담당 관계가 끊긴다. 1:1 전속이라 대체 트레이너가 없다 |
| `remove` 트레이너 | soft delete된 계정의 계약이 조회에서 사라진다. 강등과 달리 되돌리기 어렵다 |
| `remove` 회원 | 잔여 횟수가 남은 회원을 지우면 **돈을 받은 수업이 증발한다** |

원인이 같다 — *계정 상태를 바꾸기 전에 그 계정에 걸린 미이행 의무를 확인하지 않는다.*
증상 하나만 고쳤으면 나머지 둘은 그대로 남았을 것이다.

**테스트가 검증하려던 것을 검증하지 않고 있었다 (#39)**

`.env.test`의 시크릿 길이를 늘리자 출석 E2E 2개가 깨졌다.
테스트가 `'test-qr-secret'`을 **문자열로 베껴 적고 있었기 때문**이다.

```
의도:  서명 통과 → type이 ACCESS다 → INVALID_TOKEN_TYPE
실제:  서명 실패 → QR_TOKEN_EXPIRED
```

위조 토큰이 서명 검증에서 먼저 걸려 **두 번째 방어선에 도달하지 못했다.**
`app.get(ConfigService).getOrThrow('JWT_QR_SECRET')`으로 바꿔 값 변경에 견디게 했다.

같이 발견한 것: `만료된 QR은 거부된다`는 **통과하고 있었지만 아무것도 보장하지 않았다.**

```ts
await checkIn(expired).expect(401);   // 상태 코드만 본다
```

401 하나에 서명 실패·만료·타입 오류가 모두 모여 있어, **만료 검증이 통째로 사라져도 초록불이다.**
`errorCode`까지 확인하도록 고쳤다.

> **여러 이유로 같은 상태 코드가 나오는 지점에서는 코드만 보는 단언이 무의미하다.**

> **Phase 1 완료.** Auth · Gym · User + 공통 레이어 + CI/컨테이너화 + E2E.
> `dev`에 상태 체크 필수 규칙 적용.

> **Phase 2 완료.** 회원권 · 홀딩 · 양도.
> 하나의 이슈로 묶지 않고 셋으로 쪼갠 것이 맞았다.
> 홀딩을 만들면서 "정지/해제 API로는 기간이 안 남는다"는 걸 알게 됐고,
> 양도를 만들면서 "홀딩 중 양도"라는 **홀딩 구현 없이는 보이지 않던 문제**를 만났다.
> 한 번에 설계했으면 둘 다 놓쳤다.

> **Phase 3 완료.** QR 출석.
> 설계 과정에서 **이전 결정 하나를 뒤집었다.** ADR-011에 "출석 시 홀딩 자동 종료"를
> 개선안으로 적어뒀는데, 홀딩은 회원이 신청한 것이라 시스템이 임의로 끝내면
> 회원 동의 없이 회원권 기간을 깎는 것이 된다.
> **도메인을 다시 물어보지 않았으면 그대로 구현했을 것이다.**

### E2E 도입 성과

`21개 (Phase 1) → 72개 (Phase 2)`

첫날 **운영에서도 발생 가능한 버그**를 하나 잡았다. → 트러블슈팅 004

Refresh Token payload가 `{ sub }`뿐이고 JWT의 `iat`가 초 단위라,
로그인 직후 즉시 갱신하면 토큰 문자열이 완전히 동일해져 500이 발생했다.
**수동 테스트는 명령 사이의 지연 때문에 재현되지 않던 버그다.**

Phase 2에서는 **날짜 계산의 오프바이원을 잡는 그물** 역할을 했다.
회원권 종료일(`-1`), 홀딩 일수(양끝 포함), 양도 잔여일은
전부 하루 차이로 정답과 오답이 갈린다. 눈으로는 검증이 안 된다.

> 기대값을 상수로 박지 않고 `addDays(start, 29 + 6)`처럼 계산식으로 둔다.
> 숫자만 있으면 **왜 그 값인지가 보이지 않아** 테스트가 깨졌을 때
> 코드가 틀렸는지 테스트가 틀렸는지 판단할 수 없다.
> (실제로 홀딩 E2E가 한 번 실패했는데, **틀린 건 테스트 쪽이었다.**)

### 워크플로우 트리거 (CLAUDE.md에 규칙 정의됨)

```
① 이슈 생성 → ② 브랜치 생성 → ③ 커밋(반복) → ④ PR → ⑤ 머지 후 정리
```

- 이슈: 코드 변경이 있는 모든 작업. 레포 내 문서(`docs`)만 예외 → dev 직접 커밋
- 커밋: 논리적 완결 단위마다. 한 PR에 여러 커밋 정상. 빌드 깨진 상태로 커밋 금지
- PR: 완료 조건 충족 시. `Closes #N` 필수
- 템플릿: `.github/pull_request_template.md`, `.github/ISSUE_TEMPLATE/task.md`

> 문서(Obsidian) 작업은 git 관리 밖이라 브랜치 대상이 아니다.
> `CLAUDE.md` 등 레포 내 문서는 `docs:` 타입으로 `dev`에 직접 커밋한다.

## 지난 작업 — Phase 4 (Trainer + PT)

**설계 완료 (2026-08-11)** → ADR-014

| 쟁점 | 결정 |
|------|------|
| 트레이너-회원 | **1:1 전속.** 계약 시 배정. 변경은 향후 과제 |
| 빈 슬롯 | **만들지 않는다.** 행 하나 = 예약 하나 |
| 예약 주체 | 트레이너가 등록. 회원은 조회·취소만 |
| 반복 예약 | 요일·시간 패턴으로 일괄 생성. 겹친 건 건너뛰고 알려준다 |
| 시간 겹침 | **PostgreSQL `EXCLUDE` 제약**이 DB에서 차단 |
| 차감 시점 | 완료 확인 버튼. **자정 일괄 처리 없음** |
| 미확인 방치 | 목록 조회로 대응 (`ending-today` 패턴) |
| 노쇼 | `status`와 `sessionDeducted` 분리 |
| 동시성 | **조건부 UPDATE + affected rows.** 락·재시도 없음 |

**이슈를 셋으로 쪼갠다.** Phase 2에서 쪼갠 것이 맞았던 것과 같은 이유다.

```
① feat/pt-contract   계약 + Payment + 트레이너 배정 + 잔여 횟수
② feat/pt-schedule   예약 등록·반복등록·이동·취소, EXCLUDE 제약
③ feat/pt-session    완료·노쇼 확정, 차감 정합성 (동시성이 여기 몰려 있다)
```

> **설계 중 초기 전제 하나가 무너졌다.**
> "네이버 예약처럼 여러 회원이 슬롯을 경쟁한다"고 가정했는데
> 실제로는 1:1 전속이라 **경합 자체가 발생하지 않았다.**
> 슬롯 개념만 그 프레임의 잔재로 남아 있었고, 사용자가 지적해 걷어냈다.

> **Kafka·Redis·Outbox를 검토했으나 전부 제외했다.**
> 이전 프로젝트(JabaClass, MSA)에서는 재고·예치금·주문이 서로 다른 DB에 있어
> 한 트랜잭션으로 묶을 수 없었고 그래서 Outbox + 보상 트랜잭션이 필요했다.
> **gym-manager는 모놀리식 단일 DB라 그 도구들이 푸는 문제 자체가 없다.**
> "안 쓴 이유를 설명할 수 있는 것"이 이 프로젝트의 어필 포인트다.

**E2E 계획**: `Promise.all`로 실제 동시 요청을 날려 정확히 하나만 성공하는지 확인한다.
`SELECT` 후 `UPDATE`로 먼저 짜서 **깨지는 것을 보고** 조건부 UPDATE로 고치는 순서로 진행하고,
그 과정을 `트러블슈팅.md`에 남긴다.

## 지난 작업 — Phase 3 (출석 · QR)

**설계 완료 (2026-08-10)** → ADR-013

| 쟁점 | 결정 |
|------|------|
| QR 토큰 | 30초 만료 + `type: 'ATTENDANCE'` 별도 단기 토큰 |
| 재출입 | `Gym.reentryGraceMinutes` 안의 재스캔은 같은 입장. `isReentry`로 기록 |
| 하루 입장 횟수 | `Gym.dailyEntryLimit`. `null`이면 무제한 |
| 퇴실 | 만들지 않는다. 입장 이벤트만 누적 |
| 홀딩 중 출석 | **입장 차단.** 자동 종료는 철회 |
| 이름 노출 | 서버가 마스킹. `check-in` 응답에 풀네임 없음 |
| 보관 주기 | 지금은 삭제 안 함. 파티셔닝으로 향후 과제 등록 |

> **설계 중 이전 결정 하나를 뒤집었다.**
> ADR-011에 "출석 시 홀딩 자동 종료"를 개선안으로 적어뒀는데,
> 홀딩은 회원이 신청한 것이라 시스템이 임의로 끝내면
> **회원 동의 없이 회원권 기간을 깎는 것**이 된다.
> `향후 과제`에서 철회하고 ADR-011에도 취소선을 남겼다.
