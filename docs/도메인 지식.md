# 도메인 지식 — 헬스장 회원권 운영

> 개발자가 실제 헬스장에서 근무하며 파악한 운영 방식.
> 추측이 아니라 현장에서 쓰이는 흐름이므로, 설계가 흔들릴 때 이 문서를 기준으로 삼는다.
>
> 기록일: 2026-08-06

---

## 1. 회원 조회 화면

이름이나 회원번호로 조회하면 **그 회원의 모든 정보가 한 화면에 뜬다.**

```
인적사항    이름, 주소, 생년월일, 연락처
회원권      현재 이용 중인 것 + 과거 이력 전부
잔여일      항상 표시된다
특이사항    자유 텍스트
```

> ⚠️ **현재 스키마에 주소·생년월일이 없다.** User Entity 확장이 필요하다.

**잔여일은 성능을 포기하더라도 항상 노출해야 한다.**
데스크에서 회원 응대할 때 가장 먼저 보는 정보다.

---

## 2. 회원권 부여

### 시작일 기본값과 변경

- 회원권 종류를 선택하면 **오늘 날짜부터 적용**되는 것이 기본값
- **시작일을 변경하면 종료일이 자동으로 재계산**된다
- 이유: "오늘 결제했지만 다음 주부터 이용하고 싶다"는 회원이 있다

### 만료 임박 시 추가 결제 — 자동 이어붙이기

**가장 중요한 규칙이다.**

```
현재: 헬스권이 8/6에 만료 (3일 남음)
행동: 12개월권 추가 결제
결과: 8/7부터 12개월이 시작되도록 자동 설정
```

기존 회원권을 덮어쓰거나 잔여일을 버리지 않는다. **뒤에 이어붙인다.**

### 회원권 복수 보유

한 회원이 여러 회원권을 동시에 가질 수 있다.

```
헬스권 12개월  +  락커 12개월     ← 성격이 다른 것을 동시 보유
헬스권(잔여 3일) + 헬스권 12개월   ← 같은 종류를 이어붙임
```

---

## 3. 특이사항 (자유 텍스트)

회원권 데이터와 **별개로** 텍스트를 기입한다. 헬스장마다 기입 방식이 다르다.

실제 예시:

```
*26.08.06 H12 + 락커12 [카 55만]
```

> 8월 6일에 헬스권 12개월과 락커 12개월을 카드로 55만원 결제

**형식을 강제하지 않고 자유 텍스트로 열어두는 것이 맞다.**
각 헬스장이 자기 방식대로 기입한다.

---

## 4. 홀딩 (휴회)

회원권을 일시 정지하고 그만큼 종료일을 미루는 기능.

**정책이 헬스장마다 다르다.** 실제 사례:

| 회원권 기간 | 홀딩 가능 횟수 |
|------------|--------------|
| 6개월 미만 | 불가 |
| 6개월 ~ 12개월 미만 | 3회 |
| 12개월 이상 | 5회 |

> 기간에 따라 정책이 갈리므로, **회원권 종류(MembershipType)마다 홀딩 정책을 두면**
> 자연스럽게 표현된다. "3개월권"은 0회, "12개월권"은 5회처럼.

---

## 5. 양도

A 회원의 잔여 기간을 B 회원에게 넘긴다.

```
A 회원 검색 → [회원권 양도] → 대상 회원(B) 선택
  → A의 남은 일수가 그대로 B에게 적용
```

실제 헬스장에서 흔히 발생하는 요구다. (이사, 부상 등)

**수수료는 헬스장마다 다르다.**

```
가족 양도  무료
지인 양도  5만원 정도 받는 곳이 있다
```

→ 금액을 고정하지 않고 입력받는다. 0원도 가능해야 한다.

**양도권은 홀딩할 수 없다.** 원본과 같은 회원권 종류를 참조하더라도
그 종류의 홀딩 정책이 적용되면 안 된다.

## 6. 가격은 "정가"가 아니라 "기본값 제안"이다

**가장 중요한 도메인 사실 중 하나.**

회원권 종류에 가격을 등록해두지만, **실제 결제 금액은 거의 매번 달라진다.**

- 카드냐 계좌이체냐에 따라 금액이 다르다
- 이벤트가 잦고 그에 따른 변동 폭이 크다
- 현장 협상이 있다

그래서 실제 업무 흐름은 이렇다.

```
① 회원권 기간만 선택   → 등록된 가격이 자동으로 뜬다
② 가격을 수정한다      ← 거의 매번 발생
③ 시작 날짜를 확인한다  ← "다음 주 월요일부터 할게요" 하는 회원이 있다
④ 확인 버튼
```

**설계 반영**

| 도메인 사실 | 설계 |
|------------|------|
| 가격이 매번 다르다 | `MembershipType.price`는 기본값. `Payment.amount`를 별도로 받아 저장 |
| 시작일이 오늘이 아닐 수 있다 | `startDate`를 선택 입력으로. 생략 시 서버가 계산 |
| 양도도 같은 흐름 | 대상 회원만 선택하고 금액은 데스크가 입력 |

> **"가격은 회원권 종류에서만 관리한다"는 설계는 현장에서 쓰이지 않는다.**
> 정가는 참고값이고, 확정 금액은 결제 시점에 정해진다.

## 7. 출석

### QR의 역할이 헬스장마다 다르다

**같은 기능처럼 보이지만 완전히 다른 두 가지다.**

```
형식적 스캔형   데스크에 사람이 있다. QR은 기록용이고 안 찍어도 들어간다
출입 통제형     QR을 찍어야 문이 열린다. 주로 24시 무인 헬스장
```

이 차이가 나머지를 전부 좌우한다.
출입 통제형에서 **막는다는 판단은 곧 회원을 문 앞에 세우는 일**이다.

### 하루 입장 횟수도 헬스장마다 다르다

```
제한 없음      오전에 오든 저녁에 오든 자유
하루 2회       오전·저녁 운동을 인정
하루 1회       하루 한 번만
```

**어느 하나가 표준이 아니다.** 헬스장이 정하게 해야 한다.

### 재입장이 문제를 만든다

출입 통제형 + 횟수 제한이 겹치면 실제로 이런 일이 생긴다.

```
19:00  입장
19:20  흡연하러 나감
19:25  재입장  ← 하루 1회 제한이면 여기서 막힌다
```

**잠깐 나갔다 오는 것은 새로운 입장이 아니다.**
유예 시간 안의 재스캔은 같은 입장으로 봐야 한다.

### 퇴실은 대부분 쓰지 않는다

퇴실 스캔 기능이 있는 곳도 있지만 **회원들이 그냥 나간다.**
그래서 재실 인원이 항상 실제보다 많게 표시된다.

> 있지만 신뢰할 수 없는 데이터는 없느니만 못하다.

### 홀딩 중 출석 시도

**입장을 막아야 한다.** 홀딩은 회원이 신청한 것이므로
시스템이 임의로 종료하면 회원 동의 없이 회원권 기간을 깎는 것이 된다.

> `현재 휴회중인 회원입니다. 휴회를 철회한 후 이용해주세요`

### 출입구 화면

```
이*규 회원님 반갑습니다
회원권이 87일 후에 만료됩니다
```

문 앞 화면은 **지나가는 사람에게도 보인다.** 이름은 가운데를 가린다.

**설계 반영** → ADR-013

| 도메인 사실 | 설계 |
|------------|------|
| QR 역할이 헬스장마다 다름 | `Gym.reentryGraceMinutes` (0이면 형식적 스캔형) |
| 입장 횟수 정책이 다름 | `Gym.dailyEntryLimit` (null이면 무제한) |
| 재입장은 새 입장이 아님 | 유예 시간 안이면 `isReentry=true`, 횟수 미차감 |
| 퇴실을 안 씀 | 퇴실 기록하지 않음. 입장 이벤트만 누적 |
| 홀딩 중 입장 불가 | 403 + 철회 안내 문구 |
| 문 앞 화면 노출 | 서버가 마스킹. `check-in` 응답에 풀네임 없음 |

## 8. 신규 회원 관리

**운동을 시작한 지 얼마 안 된 회원을 따로 관리한다.**

- 일주일 된 회원에게 쿠폰을 주는 곳이 있다
- 만족도 조사를 돌리기도 한다

초기 이탈이 가장 많은 구간이라 여기서 관리가 갈린다.

### "운동 시작일"의 함정

재등록 회원이 문제다.

```
경우 A   만료 후 한 달 뒤 재등록      → 계속 다니던 회원이다
경우 B   만료 후 1년 뒤 재등록        → 새로 시작하는 회원에 가깝다
경우 C   만료 전에 이어서 추가 결제   → 당연히 계속 다니던 회원
```

**공백이 1년 이상이면 새로 시작한 것으로 본다.** (2026-08-10 결정)

3개월은 너무 짧다. 계절을 타거나 몇 달 쉬었다 오는 회원이 흔한데
그들까지 "신규"로 잡으면 쿠폰과 만족도 조사가 엉뚱한 사람에게 간다.

**설계 반영**

| 도메인 사실 | 설계 |
|------------|------|
| 운동 시작일이 필요 | **컬럼으로 저장하지 않는다.** 회원권 이력에서 계산 |
| 재등록 시 리셋 기준 | 공백 365일. 계산이므로 나중에 바꿔도 과거 데이터가 함께 따라온다 |
| 신규 회원 목록이 필요 | 컬럼이 아니라 **조회 필터**가 필요한 것이다 → 향후 과제 |

> **저장하려니 애매했던 것이다.** 저장하면 리셋 기준을 지금 확정해야 하고,
> 나중에 기준을 바꿔도 **이미 저장된 값은 바뀌지 않는다.**
> `EXPIRED`·`SUSPENDED`를 두지 않은 것과 같은 판단이다. → ADR-010

```
최초 등록일   User.createdAt
운동 시작일   현재 등록 구간의 첫 UserMembership.startDate
운동 마감일   보유 중인 회원권 중 가장 늦은 endDate
```

## 9. PT

### 트레이너는 계약 시 배정되고 1:1로 고정된다

```
회원이 헬스장에 와서 PT 등록
  → 회원이 원하거나 헬스장이 임의로 트레이너를 배정
  → 그 이후 1:1 관계로 고정
```

정말 마음에 안 들면 바꾸는 경우가 있지만 **이례적이다.**

### 예약은 대화로 정하고 트레이너가 입력한다

```
실제 흐름   문자·전화·카카오톡으로 시간을 정한다
            → 트레이너가 시스템에 등록한다
```

**회원이 화면에서 빈 시간을 골라 잡는 구조가 아니다.**
PT는 "매주 화·목 19시"처럼 고정 스케줄이 되는 경우가 대부분이다.

> 선착순으로 열면 **특정 시간대만 가능한 회원이 계속 밀린다.**
> 담당 트레이너가 정해져 있어 놓쳐도 대안이 없기 때문이다.
> 트레이너가 담당 회원 전체를 보고 배분하는 편이 실제로 더 공정하다.

### 차감은 수업이 끝난 뒤 확인으로

```
5시 수업 → 6시 이후 "진행되었습니까?" → 확인 → 차감
```

**시스템은 수업이 실제로 진행됐는지 알 수 없다.** 출석과 달리 QR 같은 증거가 없다.
자정에 일괄 완료 처리하면 하지 않은 수업도 차감된다.

### 노쇼는 트레이너 재량이다

노쇼 처리 버튼은 두되, **차감할지 수업을 취소할지는 트레이너가 정한다.**
사유에 따라 달라지고 헬스장 정책도 제각각이다.

### 슬롯은 한 달치를 미리 잡는다

트레이너가 다음 달 일정을 미리 등록해두고, 급한 일이 생기면 개별로 옮기거나 취소한다.

**설계 반영** → ADR-014

| 도메인 사실 | 설계 |
|------------|------|
| 트레이너 1:1 전속 | `PTContract.trainerId`. 변경은 향후 과제 |
| 대화로 정하고 트레이너가 입력 | 회원 셀프 예약 없음. 회원은 조회·취소만 |
| 빈 시간을 고르는 화면이 없음 | **빈 슬롯 테이블을 만들지 않는다.** 행 하나 = 예약 하나 |
| 고정 스케줄이 대부분 | 요일·시간 패턴으로 **반복 예약 일괄 생성** |
| 급한 일정 변경 | 개별 이동·취소 |
| 진행 여부를 시스템이 모름 | 확인 버튼으로 차감. 배치 자동 완료 없음 |
| 확인을 놓칠 수 있음 | 미확인 목록 조회 (`ending-today` 패턴) |
| 노쇼 처리가 재량 | `status`와 `sessionDeducted` 분리 |

## 10. 만료 관리

**재등록을 놓치는 것이 곧 매출 손실이다.** 그래서 만료 전후로 연락을 돌린다.

```
만료 임박   →  알림 문자   "곧 만료됩니다"     →  재등록 유도
이미 만료   →  홍보 문자   "다시 오세요"       →  복귀 유도
```

**대상도 문구도 목적도 다르다.**

### 조회가 안 되는 게 제일 불편했다

> **한 번에 목록을 뽑아낼 수가 없었다.**
> 3을 검색하면 만료 3일 남은 회원, 5를 검색하면 5일 남은 회원이 나오면 좋겠다.

이게 **범위가 아니라 정확값이어야 하는 이유**다.

```
❌ 7일 이내      D-7, D-5, D-3이 섞인다 → 매일 돌리면 한 사람에게 문자가 여러 번
✅ 정확히 3일    오늘 D-3인 사람만      → 매일 돌려도 한 사람당 한 번
```

반대로 **복귀 홍보는 범위가 맞다.** "지난 30일 안에 만료된 사람 전부"를 한 번에 보낸다.

### 헬스와 락커는 다르게 다룬다

```
헬스 만료   →  문자를 보낸다
락커 만료   →  대부분 구두로 전한다. 출석했을 때 말해준다
```

락커까지 문자를 보내는 곳도 있지만 **안 보내는 경우가 더 많다.**
대신 **QR을 찍을 때 화면에 띄우면** 회원이 직접 보게 되어 데스크가 말할 필요가 없어진다.

**설계 반영** → ADR-015

| 도메인 사실 | 설계 |
|------------|------|
| 정확히 N일 남은 사람을 뽑아야 한다 | `expiringInDays` (정확값) |
| 복귀 홍보는 기간 단위 | `expiredWithinDays` (범위) |
| 헬스·락커를 구분해야 한다 | `category` 파라미터 |
| 락커는 문자 대신 화면으로 | `check-in` 응답을 카테고리별로 분리 |
| 문자는 외부 서비스로 보낸다 | **우리는 대상 목록까지만.** 발송은 범위 밖 |

## 설계에 반영할 점

| 도메인 사실 | 설계 반영 |
|------------|----------|
| 주소·생년월일을 관리한다 | User Entity 확장 (미반영) |
| 잔여일을 항상 본다 | 조회 시 계산. 성능보다 정확성 우선 |
| 시작일 변경 시 종료일 자동 계산 | 종료일은 저장하되 서버가 계산 |
| 만료 임박 시 이어붙이기 | 부여 시 같은 종류의 마지막 종료일 다음날부터 시작 |
| 복수 보유 | UserMembership은 1:N |
| 기입 방식이 제각각 | 자유 텍스트 memo |
| 홀딩 정책이 헬스장마다 다름 | MembershipType에 정책 필드 |
| 양도가 실제로 발생 | 잔여 기간 이전 기능 |
| QR·입장 정책이 헬스장마다 다름 | Gym에 설정 필드 |
| 신규 회원 판별 | 컬럼이 아니라 회원권 이력에서 계산 |
| PT는 1:1 전속, 대화로 예약 | 빈 슬롯 없음. 트레이너가 등록 |
| 수업 진행 여부를 시스템이 모름 | 확인 버튼으로 차감 |
| 만료 연락은 목록을 뽑아 문자로 | 실시간 알림이 아니라 **필터 조회** |

> **반복되는 패턴이 하나 있다.**
> 헬스장마다 다른 것은 **설정으로**, 시간이 지나면 바뀌는 것은 **계산으로** 푼다.
> 저장해야 하는 건 사람이 개입한 사건뿐이다.
